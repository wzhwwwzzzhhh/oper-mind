# 准备-1 · 现状与复用盘点

> 核查：2026-10-15；代码基线 `6706caa88c3d73c9f29f65659e033e1c89926c65`（`main`）。
> 状态：用户已于 2026-10-15 审阅确认准备-1 复用建议；这是静态盘点结论，不是正式 Design 或运行验证通过证明。
> 授权：用户已确认[准备计划](开发计划.md)，要求先推进准备-1，再继续准备-2。
> 证据范围：当前代码、测试源码与既有交付文档；本轮未运行测试、服务、模型或兼容探针，没有新增依赖、分支或 Workpack。

## 1. 结论先读

1. **有可复用底座，不是从零开始。** 会话／消息、Run 受理与幂等、事件重放、模型配置、工具网关、P10 契约及 P11 安全保护都已有资产。
2. **不能原封不动换业务。** 普通消息与调查分流、服务绑定、模型 mock、诊断结果、Trace 角色和前端结果面板仍带运维语义。
3. **“默认主 Agent + 能力”不是当前正式执行形态。** 生产调查仍进入 Coordinator 与诊断图；领域 Agent 的 ReAct 子图是复用候选，不等于主 Agent 产品化已经完成。
4. **隔离与取消有已有保护，也有边界。** 每 Run 工厂隔离、Run CAS、P11 迟到结果保护应保留；它们不等于完整同会话调度、全局 deadline、底层线程强制停止或恢复能力。
5. **三种 Capability 不能混成一个概念。** 现有服务能力绑定、Runtime 能力画像与 V2 业务能力模块职责不同；需要语义映射，不应直接重命名。
6. **首闭环应沿正式会话与 Run 接缝渐进演进。** 本报告建议先收敛一个可检查能力；不据此切换生产装配、确定新框架或重写整个前端。

上述 1–5 来自下文静态证据；第 6 是待需求与设计确认的建议。

## 3. 当前实际主链

### 3.1 普通消息链：可对话，但不是带工具主 Agent

1. `App` 根路由进入工作台；`WorkbenchPage.submit_text` 使用前端关键词预判。
2. 普通消息走独立消息请求。后端 `PlainMessageApplicationService` 仍以 `requires_database_context` 判定是否要求退回调查链。
3. 普通回复生成器按当前生效模型配置构建客户端，最多读取 `PLAIN_HISTORY_LIMIT = 8` 条最近会话消息，过滤角色和归档项后构造消息；不注入工具。
4. writer 保存 user／assistant 消息对，`run_id` 为空；不创建调查 Run、不经过 Coordinator／ToolGateway。
5. 前端遇到 `INVESTIGATION_REQUIRED` 时回退调查提交。

证据：E01、E03、E09。不能把这条真实普通对话能力误称为“当前默认主 Agent 已能统一选择 Capability”。历史消息查询也不是只限 `run_id` 为空的消息；实际过滤条件以仓储和生成器为准。

### 3.2 调查链：正式 Run、诊断图与安全结果

1. 工作台为所选服务形成发送记录／幂等键，调用 `POST /api/v1/sessions/{session_id}/runs`。
2. `accept_run` 在短事务中校验会话、服务上下文和幂等，保存输入消息、Run、幂等记录及 queued 事件。
3. 未重放的新请求在 HTTP 响应后由后台任务调用 `execute_run`；这不是 durable worker 或可恢复队列。
4. 应用服务认领 Run，以 `guard_runtime_stream` 消费 `DiagnosisExecutor`。装配的实现是 `CoordinatorDiagnosisExecutor`。
5. 执行器通过工厂创建本次 Coordinator；后者驱动诊断图。real 路由会尝试模型判断，仍有关键词与默认领域兜底；mock 使用既有确定性角色规则。
6. 领域 `BaseAgent.run` 构建本次 ReAct 子图，模型工具请求经过 `ToolGateway`，而不是直接执行 Connector。
7. 执行器与应用层进行公开投影；guard 只在有限流正常 EOF、终止协议合法时交付唯一终止结果。
8. `_complete_success` 在事务中组装诊断结果、助手消息、Run 终态和事件；固定动作提案另受既有动作规则控制。
9. 工作台读取 Run／结果并订阅可重放事件，展示诊断结果及安全 Trace。

证据：E01、E02、E04、E05、E08–E10。这里的 direct 是“直达领域 Agent”，不是 V2 设想的通用主 Agent 默认直答。

## 4. 逐项复用判断

### R01 · 会话与消息：机制沿用，边界字段适配

- **现状／证据**：E07 的 Session／Message、时间、归档与会话关联已有实现；Session 带 `service_id/service_ids`，不是纯粹业务无关对象。
- **建议**：沿用会话管理、分页、生命周期和消息归属机制；首任务不强制要求运维服务。
- **风险／待验**：持久化消息不代表每条 Agent 链都自动加载历史；V2 的历史范围、输入快照与敏感数据处理需单独明确。
- **后续验证**：普通会话、归档／恢复、消息顺序及新能力追问不串到其他 Run。

### R02 · Run／幂等／持久化：沿用事实所有权，不直接照搬诊断载荷

- **现状／证据**：E02、E07 已有受理事务、请求 fingerprint、单 Run 认领与终态 CAS、事件序号和结果唯一约束。
- **建议**：保留这些保证和单一业务写入责任；先证明现有 port 的差距，再决定兼容演进，不新建职责重叠的第二套 Run 控制面。
- **风险／待验**：当前 query 上限 4000、可选服务上下文和诊断型返回值不能直接充当任意结构化 Capability 输入输出。
- **后续验证**：相同请求重放不重复消息／工具执行，换输入复用幂等键应冲突；取消与完成竞争仍只提交一个终态。

### R03 · LangGraph／ReAct：已有内核，主 Agent 产品职责需要适配

- **现状／证据**：E04、E05 分别承担跨 Agent 诊断编排和领域 Agent 内部循环；`BaseAgent` 还保存实例状态。
- **建议**：优先评估复用已存在循环／接口；把能力选择、结构化结果和上下文控制接入正式链，保留原运维实现。
- **风险／待验**：候选 `create_agent`／Deep Agents 尚未做准备-3 兼容验证；不能宣称已选中，也不能只换工厂就声称完成主 Agent。
- **后续验证**：受控模型替身下的直答、能力选择、调用上限、安全失败与工具白名单。

### R04 · 语义路由：旧规则保留兼容，新链路需迁移语义分流

- **现状／证据**：E03、E09 使用数据库关键词分普通／调查；E04 的诊断图还使用关键词兜底及正则提取模型文本 JSON。
- **生效边界**：当前 V1 仍按既有规则运行。本报告指出 V2 的迁移差距，不将旧规则自动判为失效，也不授权删除兼容路径。
- **建议**：V2 新语义选择使用有校验的结构化模型决策；格式、权限与注册项继续由程序校验。
- **风险／待验**：不能把新能力文本中的“表／查询／SQL”误触发成数据库调查；也不能因 V2 目标直接删除 V1 兼容路径。
- **后续验证**：同义表达得到相同能力选择；无效模型输出明确失败／追问，不偷偷按关键词转向 DB。

### R05 · ToolRegistry／ToolGateway：保留强制接缝，补足能力专属校验

- **现状／证据**：E05 有显式注册、JSON 解析、required／顶层类型／部分额外字段校验、限时等待、脱敏和安全调用记录。
- **建议**：所有模型提出的工具调用仍经现有受控入口；按具体能力补强输入与输出规则。
- **风险／待验**：当前 schema 校验是子集，不是完整 JSON Schema 引擎；注册成功不等于已有通用身份、Policy、Grant 或租户权限。
- **后续验证**：未注册／越界参数拒绝时工具执行次数为零，结果与审计摘要不带原始异常、凭据或原文。

### R06 · 超时与取消：沿用诚实保护，不扩大保证

- **现状／证据**：E02、E05、E11–E13 保留 Run 终态保护；Gateway 区分等待、接纳与底层状态，排队取消及迟到隔离已有实现与探针资产。
- **建议**：V2 不削弱这些保证；对用户仍明确“本次任务已取消／停止等待”不必然意味着底层网络／线程已停止。
- **风险／待验**：无限／阻塞流的全局 deadline、完整取消传播、跨进程恢复仍不是现有保证。
- **后续验证**：取消胜出后迟到结果不得写入结果、成功消息、第二终态或提案。

### R07 · 并发与上下文：有每 Run 隔离，未证明所有共享状态安全

- **现状／证据**：E04 的执行器每次构建 Coordinator；E05 的 ReAct 图按本次调用构建，闭包直接操作 Agent 的记忆与审计字段。
- **建议**：初版保留清晰的每 Run 实例／输入归属；若要缓存图或共享客户端，逐项核对可变状态。
- **风险／待验**：Run CAS 保护的是一个 Run，不是整个会话的历史串行语义；没有依据宣称所有图内分支或外部资源已隔离。
- **后续验证**：同会话／不同会话两个已受理任务使用不同原文，输出、引用、事件、取消互不污染；并发额度与历史读取策略由后续 Design 明确。

### R08 · 模型与凭据配置：沿用解析和加密，不新增旁路

- **现状／证据**：E01、E04 每 Run 解析模式、参数、默认配置与角色配置。当前产品定义明确模型 Key 及动态服务凭据按已确认方案加密存储。
- **建议**：沿用 Provider、生效解析、参数与安全密钥机制；新角色如何映射现有配置需明确。
- **风险／待验**：新增主 Agent 不自动获得新的角色配置、认证体系或无条件真实调用授权；旧文档“凭据永不落库”不能覆盖当前已确认的加密密文方案。
- **后续验证**：mock／real、未配置、模型不可用、参数生效与密钥不回显；本轮不读取或调用真实配置。

### R09 · mock：原则复用，具体运维白名单不能原样通用化

- **现状／证据**：E06 的 `ROLE_TOOL_ALLOWLISTS` 限于 db／server／log／knowledge；陌生或混合菜单失败关闭，依赖显式场景事实。
- **建议**：保留确定性、角色受限、无证据不伪造的规则；给新能力设计独立且明确的测试事实与模型替身。
- **风险／待验**：直接把新工具塞入现有菜单会触发不支持，不应放宽旧白名单制造通过。
- **后续验证**：新能力 mock 可复现、不会读场景外数据；V1 mock 基线不变。

### R10 · 用量与成本：统计机制沿用，不等于 Run 预算系统

- **现状／证据**：E06 的 `UsageRecord` 记录模型、输入／输出／总 token 和时间；无 Run／Task 标识。mock 不采集真实用量，缺 usage 不伪造；金额是估算口径。
- **建议**：保留当前聚合统计与诚实表达；新增模型调用若换 SDK，必须明确如何继续记录实际用量。
- **风险／待验**：父子任务成本归因、Run 预算 ledger、可审计逐任务账单不能写成已具备。
- **后续验证**：真实 usage 替身的采集不重复，缺失／mock 表达正确；逐 Run 归因若不在首范围，应明确延期而非暗中补字段。

### R11 · 记忆：复用会话存储，不激活旧文件型长期记忆

- **现状／证据**：E01 的普通聊天加载有限历史；E04 正式 Coordinator 工厂默认关闭长期记忆；E05 的短期记忆属于 Agent 实例。
- **建议**：首任务依赖本次明确给定材料与必要会话上下文，冻结输入；历史消息作为非证据上下文时要标明范围。
- **风险／待验**：不能将“上一轮有文档”默认当成本轮授权材料，也不能把旧文件记忆或框架 checkpoint 变成业务事实源。
- **后续验证**：缺材料时追问，原文选择、消息编辑、重跑与并发各自绑定正确输入。

### R12 · 事件／SSE／Trace：复用传输与安全投影，扩展词汇需设计

- **现状／证据**：E02、E07、E10 已有按 Run 序号重放与前端去重；E04 的公开角色白名单只有四个领域角色，前端事件列表与图标也有现有词汇。
- **建议**：保留 Run 归属、去重、安全投影；新主 Agent／能力信息如何投影需要协议与 UI 同步。
- **风险／待验**：不是后端写个 `main` 字符串就会完整展示；不得把任意工具 detail／原文／Prompt 直接送入 Trace。
- **后续验证**：重连不重复显示，不丢安全状态；Trace 仅展示允许元数据与摘要。

### R13 · 结果与证据：诊断语义需适配，事实来源规则保留

- **现状／证据**：E07、E08 的结果含严重度、置信度、根因、风险；结构化诊断事实来自确定性调查结果，不从 Markdown 反推。固定索引动作还会匹配特定事实。
- **建议**：新能力结果应有独立可检查语义与明确来源；沿用“正文不是结构化事实证明”的原则，不硬塞进根因或风险字段。
- **风险／待验**：模型比较结论不是天然可信；引用必须能回指本次输入，失败／未执行不能显示成能力成功。
- **后续验证**：合法新结果正确展示，非法结构／引用被拒绝；不触发旧索引动作或伪造诊断严重度。

### R14 · 前端与服务资产：渐进适配，不整体搬走

- **现状／证据**：E09、E10 的会话壳、消息恢复、发送幂等、事件卡可复用；诊断结果面板、服务选择和部分文案绑定现业务。
- **建议**：首版只调整正式会话中的能力输入、结果与安全过程展示；模型管理与服务中心原路径保留。
- **风险／待验**：资源接入不能只把“数据库服务”改名就成为任意业务；连接、凭据、服务能力仍按原安全范围。
- **后续验证**：新能力无需强行选择数据库；旧服务入口、普通消息、取消／重跑与诊断结果不回归。

### R15 · P10／P11：复用保证与证据，不将所有目标协议激活

- **现状／证据**：E11、E12 的 `RuntimeAdapterContract` 仍是目标测试协议；P11 生产 guard 已复用其中 signal 类型，但没有让整个目标 Adapter 接管 Run。
- **建议**：保持七类状态正交、typed failure、版本化能力画像和历史基线；新增兼容映射只按已确认差距实施。
- **风险／待验**：旧 v1 fixture 描述的是历史缺口；v2 已升级有限流终态和意外异常保护，不能据旧描述说今天仍取最后结果。反过来，v2 也没解决所有 deadline／control gap。
- **后续验证**：新增适配不能删除 expected gap、刷新历史 baseline 或放宽白名单“修绿”。

## 5. 交给准备-2 的需求输入

这些是本报告建议收敛的产品行为，不是已批准实现：

- 在正式会话中完成默认主 Agent 的普通交付、追问与一次能力调用，能力选择不依赖运维关键词分流。
- 本次能力输入、资源范围、完成／失败与结果来源可检查；不直接扩展为任意技能文件加载。
- 复用 Run 与工具安全边界；任何通用结果或输入协议变化必须有对应需求与 Design。
- 首版结果展示不伪装诊断；文本原文只进入明确的输入／结果范围，不进入 Trace、日志或审计摘要。
- 用真实代码差距确定是否适配现有循环；官方组件比较留给准备-3，当前不宣称通过兼容验证。
- 延后长期记忆、恢复、分布式协作和父子成本账本；两种协作方向保持平行，不成为首闭环的硬前置。

首任务的用户选择及具体输入／结果边界由 [准备-2 需求收敛](最小契约与首切片范围.md)记录；正式需求唯一正文放在 PRD 中，不在本报告另维护验收条款。
