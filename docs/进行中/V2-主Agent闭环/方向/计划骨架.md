# OperMind V2 · 主 Agent 平台计划骨架

> 状态：方向已确认；阶段划分待用户确认。
> 更新：2026-10-26（按“一契约 + 两轴”重写；V2 替换 V1）。
> 前置基线：[V1 项目与开发进度](../../../归档/V1-项目与开发进度.md)。
> 图解入口：[八张分图的阅读目录](图解/README.md)。
> 首切片记录：[首闭环 PRD](../首闭环/PRD.md) / [Design](../首闭环/Design.md) / [Workpack](../首闭环/Workpack-计划.md)。首闭环是过渡验证，不是 V2 的目标执行形态。

V2 是 OperMind 的目标形态，替换 V1。V1 保留为过渡基线：首切片不删除 V1 实现；V2 达到能力对等后，V1 调查入口与 Coordinator 路径逐步下线。

一句话：**主 Agent 用 ReAct 循环执行；所有外部能力收口到一份 Capability 契约；子 Agent 和多主 Agent 是按需启用的协作轴，不是默认形态。**

## 1. 目标与取舍

建设目标从深入运维业务转向可组合的 Agent 项目底座：以主 Agent 为基本执行单元，通过 Capability 扩展能力，并支持子任务委派与独立业务主 Agent 协作。

现阶段优先验证能力装配、执行与协作机制。具体商业业务、目标用户和 To B / To C 定位留待后续验证；不用开源项目星数、厂商宣传或少数案例代替需求验证。

业务可扩展是需要验收的目标。底座降低新业务接入成本；新业务的数据语义、数据源、权限、结果表现和正确性评测仍需专门建设。

## 2. 一个契约：Capability

Capability 是主 Agent 唯一看到的能力单元。它对外声明：

- 身份与版本（`capability_id` + `version`）；
- 类型：知识型或执行型；
- 输入与输出契约；
- 所需资源与权限；
- 允许使用的 Tool；
- 完成条件与失败语义；
- 模型可见的说明与使用指引。

内部实现由三种材料组成：

| 材料 | 负责什么 | 是否直接对外 |
|---|---|---|
| Skill | 知识、操作指引、任务步骤、注意事项 | 否 |
| Tool | 一个受控操作，经 ToolGateway 校验参数、资源、权限、超时 | 否 |
| Workflow | 围绕一个业务目标组织多步流程，可组合确定性程序、模型调用、Tool 与 Agent | 否 |

两类 Capability：

- **知识型**：内部只有 Skill。选中后把知识装入本次上下文，由模型基于知识回答；不调用外部工具，交付标注为“知识辅助回答”，不声称事实核验。
- **执行型**：内部包含 Tool 或 Workflow。选中后经网关执行，结果必须通过 typed 校验后才能交付；可绑定外部资源与权限。

模型提出能力选择，程序校验注册、版本和适用范围后，再装入知识或调用工具。装入与调用都由程序执行，模型不直接读取资源。

注册表是进程内显式注册：按 `capability_id + version` 解析，不做扫描、自动发现、热加载或市场。一个能力版本只注册一次。

“Capability”在本仓库有三个不同所指，不要混用：

| 名称 | 含义 | 现状 |
|---|---|---|
| `ServiceCapability` | 某个已接入服务允许提供哪些只读操作 | V1 已有 |
| `RuntimeCapability` | 执行协议（Harness 契约）支持到什么程度 | V1 已有（P10） |
| **V2 Capability** | 用户能完成的一项任务 | 首闭环仅一个：`text.literal_compare@1` |

## 3. 两条轴

### 3.1 执行轴：单个主 Agent 内部

```text
直答
→ 知识型 Capability（装 Skill）
→ 执行型 Capability（装 Tool / Workflow + 资源权限）
→ ReAct 多轮：决策 → 受控工具 → 观察结果 → 再决策
```

主 Agent 的正式执行内核是 ReAct 循环，不是一次性决策图。循环受程序预算限制：

- 最大模型调用次数；
- 最大工具调用次数；
- 单次模型与工具超时；
- 取消与终止条件；
- 成本与用量记录。

模型负责语义决策：理解目标、选择能力、决定是否需要工具、判断是否可以交付。程序负责执行资格：能力是否注册、资源是否绑定、参数是否符合 schema、权限是否允许、预算是否足够、状态是否合法。模型提出调用或协作请求，不等于授权执行。

### 3.2 协作轴：跨 Agent

```text
单主 Agent
→ 子 Agent 委派（上下文隔离、长任务、并行调查）
→ 多主 Agent 协作（业务独立，各自负责完整任务，复用同一 Capability 注册表）
```

两条协作轴平行，可分别启用或组合：

- **任务复杂度与上下文隔离**决定是否派子 Agent；
- **业务独立性**决定是否采用多个主 Agent。

任务复杂不自动意味着必须增加 Agent，多个 Agent 也不保证更准确。子 Agent 与多主 Agent 都不默认启用；单主 Agent + 完整能力面是默认形态。

### 3.3 四种组合

| 组合 | 属于哪条轴 | 用途 |
|---|---|---|
| 单主 Agent | 执行轴的基础形态 | 基于会话上下文完成任务 |
| 主 Agent + 能力包 | 执行轴 | 在同一上下文内装配知识或执行受控能力 |
| 主 Agent + 子 Agent | 协作轴 | 委派边界明确的子任务，隔离上下文 |
| 主 Agent ↔ 主 Agent | 协作轴 | 多个独立业务主体协作 |

这四种是同一底座的组合方式，不是四套运行时，也不是能力等级。每个主 Agent 都可以挂载能力包并委派子 Agent；主 Agent 之间共享必要的任务信息、结果和证据引用，默认不共享完整会话、记忆或权限。

## 4. 复用 V1 与替换 V1

复用 V1 的会话/消息、Run/SSE/事件、ToolGateway、安全 Trace、审计、受控动作、服务注册/Connector、知识库和模型管理。先对实际生产调用链做差距检查；P9 研究中出现的某个目标类型，不等于它已经实现。

替换范围：Coordinator + 领域 Agent 的固定路由，逐步由“主 Agent + Capability”取代。审批、监控、知识库、模型管理、审计和受控动作是共享产品模块，不随 V1 退役；V2 继续复用。迁移按里程碑推进：

| 里程碑 | 条件 | 默认入口 |
|---|---|---|
| V2-0 / V2-1 | 首切片收口；契约与 ReAct 内核可用 | V1 默认，V2 显式 |
| V2-2 | 首批高频只读调查达到 V1 对等 | 用户确认后切 V2 |
| V2-3 / V2-4 | 子 Agent、多主协作可用 | 新会话走 V2，V1 路径只保留读历史 |
| 稳定期后 | V2 无回退 | 删除 V1 运行路径，历史数据只读保留 |

不承诺“换业务零改动”。新业务仍需要自己的数据语义、数据源、权限、结果表现与评测。

## 5. 前后端演进方向

前端以会话为主入口，围绕主 Agent、能力、资源连接和任务记录组织体验。需要逐步具备：

- 能力目录与状态（已启用 / 未启用 / 不可用）；
- 本次使用的能力、参与 Agent、执行步骤、结果与安全 Trace；
- 服务上下文与资源绑定；
- 失败、取消、超时和不可用状态。

先确认页面职责与契约，再逐页迁移；会话、模型、Trace 等已有组件按适配情况复用。页面清单、视觉方案和交互细节待 Design 定稿。

后端渐进复用。服务管理中的连接、凭据引用与状态机制可以作为资源接入资产；“数据库服务”不能直接改名就成为任意业务资源模型。迁移同时关注 `DiagnosisRunData`、`DiagnosisResultData.root_causes`、Evidence 的服务绑定、固定 intent 路由及对应前端渲染。

## 6. 阶段计划

以下是建议阶段，不代表已批准实施队列。每阶段进入前仍须完成 Design → Review → 用户确认。

### V2-0 · 首闭环收口（不是新能力）

状态：已收口，随 PR #135 合入 main（2026-10-26）。

三项遗留已裁决：失败码拆分、损坏行安全不可用投影、V1 默认入口。首切片作为过渡能力合入；它是一次性决策图，不进入 V2 目标内核。

出口：

- [x] 首切片作为过渡能力合入；
- [x] 明确它是一次性决策图，不进入 V2 目标内核；
- [x] 文档、分支和 worktree 状态一致。

### V2-1 · 单主 Agent 地基

内容：

1. Capability 契约 v1：统一知识型与执行型的输入、输出、资源、权限、失败语义与版本规则。
2. Capability 注册表：显式注册、按 id + version 解析、未知能力安全失败。
3. 迁移 `text.literal_compare@1` 到新契约，作为回归样本。
4. ReAct 主循环：替换一次性 DAG，加入步数、工具调用数、超时、取消和预算限制；定义 typed 终态与交付。
5. 一个知识型 Capability：装一份只读排查手册（Skill），选中后装入上下文，指导主 Agent 组织排查步骤；不调用外部工具。

出口：用户在会话中提问，主 Agent 通过 ReAct 循环使用排查手册组织步骤；有执行型能力时调用工具，没有时给出标注清楚的“知识辅助回答”；界面能看到使用的能力、执行步骤和失败/不可用状态；`text_compare` 回归通过。

### V2-2 · 执行型能力与插件性

内容：

1. 新增至少两个不同领域的执行型 Capability，复用现有服务中心 Connector 与只读工具（例如服务健康摘要、知识检索问答、日志只读扫描）。
2. 验证资源绑定、权限范围、证据引用、超时、不可用和安全降级。
3. 加能力只允许修改注册、配置和 handler；如果必须改内核，先停下来修契约。

出口：两个能力在同一内核上运行；新增能力没有改主循环、会话或工具网关；首批高频只读调查场景达到 V1 对等，未覆盖项在 PRD 中列明。

### V2-3 · 子 Agent 委派

内容：主 Agent 发起边界明确的子任务，使用隔离上下文获取结果并负责汇总。

验证：父子关联、工具范围、取消、超时、成本和失败传播。

出口：复杂或长任务可以按需委派；单主 Agent 仍是默认路径。

### V2-4 · 多主 Agent 协作

内容：两个独立业务主 Agent 各自完成本职任务，按需请求对方结果，复用同一 Capability 注册表。

验证：请求归属、响应关联、超时、重复请求处理、协作深度限制、结果交付责任。

出口：不要求分布式系统，先在同一后端内验证。多主 Agent 不因为“更复杂”而默认启用。

### V2-5 · 业务深化（不属于平台阶段）

在平台能力通过验证后，结合可接触的用户、实际任务和效果选择业务。按业务补充数据源、前端结果表现与评测。平台通用性不替代业务研究。

## 7. 完成判断

平台初版至少能证明：

- 同一底座支持知识型能力、执行型能力、子任务委派和独立主 Agent 协作，后两者可组合。
- 第二个不同领域的执行型能力通过正式会话链路运行，新增它没有修改内核。
- 主 Agent 以 ReAct 循环执行，步数、工具调用、超时和预算由程序限制。
- 语义决策来自结构化模型判断，执行资格由后端确定性边界裁决。
- 前端展示实际使用的能力、参与 Agent、任务状态、结果与安全 Trace，不展示未执行能力或隐藏推理。
- 多 Agent 相比单 Agent 的质量、延迟与成本按具体任务测量，不把“更多 Agent”当作通过条件。

具体样例、阈值和测试方法在对应 PRD 与 Design 中确定。

## 8. 开放问题

- Capability 契约的字段与版本迁移规则；
- 知识型能力的交付语义：如何标注“知识辅助回答”，如何避免被当成事实核验；
- 上下文管理：会话历史、材料快照、检索结果如何组装与限额；
- 资源与权限模型：Capability 如何声明服务绑定与最小权限；
- 子 Agent 的最小任务契约与结果交付责任；
- 多主 Agent 的通信形态：同进程、消息还是外部协议；
- V1 退役窗口与历史数据兼容；
- 评测方法：单 Agent 与多 Agent 的质量、延迟、成本如何对比。

本骨架不新增真实连接、权限、审批动作、API 或迁移。涉及这些边界的切片，按 [开发规范](../../../事实源/开发规范.md) 完成 Design、Review 与用户确认后实施。
