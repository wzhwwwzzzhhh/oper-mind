# 会话 DBAgent 工具接入真实 PostgreSQL · PRD 工程审查建议

## 背景

目标 PRD 计划把会话工作台中的 `explain_sql`、`show_index`、`show_create_table` 从 mock 数据源接到真实 PostgreSQL，并复用 P4 已验证的只读连接能力。

方向本身与 OperMind 的产品主脊基本一致：能力发生在会话工作台，通过受控 Tool/Connector 读取事实，不新增写操作，也保留 mock 评测路径。

但当前文档之间存在会直接影响开工资格的冲突。本建议只记录需要 PM 处理的事项，不直接修改 PRD、Design 或路线图。

## 当前结论

**结论：FAIL（存在阻塞项，暂不建议按当前状态实施）**

当前不是 PRD 写作质量问题，而是“是否已经获准实施”的工程治理问题。

## 目标

本建议的目标是让 PM 能够明确回答以下问题：

1. P4.2 现在是否真的排在当前工作之前？
2. P4.2 的 Design 是否已经完成 Review 并获得用户确认？
3. P4.2 是一次暂时的 PostgreSQL 技术切片，还是正式服务模型的一部分？
4. 执行 AI 可以依据哪些稳定、唯一的模式判定和服务边界实现？

## 范围

### 需要 PM 处理

- PRD、Design、路线图的状态和排期一致性；
- mock/真实模式的唯一判定口径；
- 真实 PostgreSQL 的服务上下文与访问边界；
- `show_index`、`show_create_table`、`explain_sql` 的输入和降级语义；
- PRD 通过后的验收证据和实现范围。

### 不在本建议中解决

- 不直接修改后端 Tool、Connector、数据库访问代码；
- 不直接修改路线图或产品定义；
- 不新增 DSN、凭据、数据库迁移、公开 API 或前端能力；
- 不将当前技术切片扩展成 MySQL、Redis 或通用多服务执行器；
- 不把本建议文档当成产品事实源。

## 问题清单

### 1. [阻塞] PRD 与 Design 的确认状态冲突

**证据：**

- `docs/prd/session/P4.2-db-agent-real.md:3`：`status: 已确认`；
- `docs/prd/session/P4.2-db-agent-real.md:115-116`：把 Design 描述为“已确认”；
- `docs/P4.2DBAgent真库Design.md:3`：状态仍是“草案，待 Review 与用户确认后实施”。

**影响：**

执行 AI 无法判断这个工作包是否已经通过 Design → Review → 用户确认闸门。若直接实现，可能把尚未确认的真实外部访问、连接边界和工具行为固化进产品代码。

**建议修改：**二选一，不能保持当前混合状态。

- **方案 A：确认现在实施 P4.2**
  - 完成 Design Review；
  - 明确记录用户确认；
  - 将 Design 顶部状态改为“已确认”；
  - 保留 PRD 的“已确认”状态；
  - 在 PRD 中引用确认记录或确认日期。
- **方案 B：确认暂不实施 P4.2**
  - 将 PRD 状态改为“待确认”或“待排期”；
  - 将 `docs/prd/README.md` 中的当前进展改为待排期；
  - Design 保持草案；
  - 禁止本阶段进入代码实现。

### 2. [阻塞] PRD 当前阶段与已确认路线图冲突

**证据：**

- `docs/prd/README.md:22`：P4.2 标记为“已确认”；
- `docs/prd/README.md:32`：P4.2 标记为“当前”；
- `docs/路线图.md:80`：当前优先是“前端整体重构”；
- `docs/路线图.md:87`：原定“接真 PostgreSQL”已延后，待前端重构定稿后再启动。

**影响：**

当前不能从文档判断 P4.2 是：

- 路线图已经被新的 PM 决策覆盖；还是
- PRD 目录提前登记了下一阶段需求；还是
- 路线图本身已经过期但尚未更新。

三种情况的实施顺序、工作包拆分和用户确认范围都不同。

**建议修改：**

- 如果 P4.2 确实提前：先更新 `docs/路线图.md` 的当前优先级和阶段说明，再让 PRD 状态保持“已确认”；
- 如果前端重构仍然优先：将 P4.2 PRD 标记为待排期，不要让执行 AI 将其视为当前开发任务；
- 不要只改 `docs/prd/README.md`，因为它不能单独覆盖高层产品路线。

### 3. [高] mock/真实模式的判定口径没有统一

**证据：**

- PRD 目标中用“`api_key == mock`”描述 mock 模式；
- PRD 功能需求 1 中改用 `get_active_scenario() is not None` 判定 mock 模式；
- Design 也同时出现了 API Key 和 active scenario 两种表达。

**影响：**

执行 AI 可能实现出两套互不一致的模式判定：目标层面认为由 API Key 决定，代码层面却由 scenario 状态决定，导致真实模式、mock 评测和降级路径之间出现边界漂移。

**建议修改：**

在 PRD 中增加一个唯一决策：

- 明确唯一运行时判定入口；
- 明确 API Key 与 scenario 的初始化关系；
- 明确两者不一致时谁优先；
- AC1、AC2 和 DoD 全部使用同一口径。

建议的需求层表达可以是：

> mock/真实模式由现有运行时模式状态唯一决定；API Key 只负责初始化该状态，不作为工具内部的第二套判定来源。

最终以当前代码和已确认 Design 为准，不要由执行 AI 自行猜测。

### 4. [高] 真实服务上下文和授权边界没有写成可验收行为

**现状：**

PRD 允许真实模式读取 `OPERMIND_PG_DSN`，背景使用固定的 `postgres-production`，但没有明确说明该 DSN 与哪个服务实例、哪个会话上下文、哪个权限边界绑定。

**风险：**

当前 P4 技术切片可能被误实现成正式产品语义：用户只要进入真实模式，就能访问一个全局数据库。这样会绕过产品定义中的服务身份、服务上下文和服务级隔离要求。

**建议修改：**

在 PRD 的“范围 / 边界与约束 / 完成定义”中明确：

- P4.2 仅复用 P4 已批准的单一 PostgreSQL 技术切片；
- 本阶段不提供用户选择任意 DSN、任意服务或任意数据库的能力；
- 不新增凭据保存、凭据展示或服务绑定模型；
- 不将 `OPERMIND_PG_DSN` 解释为未来正式多服务产品的完整服务上下文；
- 真实访问只能经过既有后端受控 Tool/Connector 和既有权限边界；
- 未配置、无权限、连接失败和服务不可用必须分别有诚实状态，不得统一伪装成“查询结果为空”。

建议补一条 AC，证明工具不会绕过服务上下文或访问未授权目标。

### 5. [高] `explain_sql` 的输入安全规则仍然过于宽松

**现状：**

当前 PRD 的规则是：`sql.strip().upper()` 以 `SELECT` 开头即可继续执行 EXPLAIN。

**风险：**

仅检查字符串前缀无法完整表达以下边界：

- 多语句输入；
- 尾随分号和注释；
- `WITH` 查询是否支持；
- 含写入语义的 CTE 是否拒绝；
- 不支持的 PostgreSQL 语句形态如何降级。

**建议修改：**

PRD 不必规定具体 SQL 解析库，但需要把行为边界写清楚：

- 只允许单条、只读、可被 EXPLAIN 的查询；
- 多语句、写入 CTE、无法确认安全性的输入必须拒绝；
- `WITH ... SELECT` 是否支持必须明确；
- 拒绝时不得触库，并返回稳定的用户可见文案；
- 至少增加对应 AC 和“拒绝后不触库”的测试证据。

### 6. [建议] 表名和 Schema 语义需要收敛

**现状：**

`show_index` 和 `show_create_table` 当前只接受简单标识符，没有说明 Schema 处理方式。

**需要 PM/Design 明确：**

- 只支持默认 Schema，还是支持 `schema.table`；
- 同名表存在于多个 Schema 时如何选择；
- 表不存在、Schema 不存在、无权限时分别返回什么；
- 是否允许大小写敏感或带引号的 PostgreSQL 标识符。

如果 P4.2 只支持一个已知 Schema，应在 PRD 的“不做什么”中明确写出，避免执行 AI 自行扩展成通用表定位器。

### 7. [建议] `show_create_table` 不应暗示生成完整 DDL

**现状：**

PRD 使用“仿 PostgreSQL 建表语句”，但没有定义覆盖范围。

**风险：**

从系统目录拼接的结果可能无法完整表达默认值、序列、复合约束、分区、继承、扩展类型、索引、注释或权限。若 UI 或 Agent 把它解释成完整建表 DDL，容易产生错误结论。

**建议修改：**

二选一：

- 明确支持的结构子集，并将输出命名为“表结构摘要”；
- 或补充完整性边界，未支持的结构必须标记“未展开”，不能伪装成可直接执行的完整 DDL。

## 建议的 PRD 修改结构

如果 PM 决定继续推进 P4.2，建议按以下顺序整理 PRD：

1. **背景**：保留当前问题描述，但说明这是 P4 技术切片的延伸，不是产品范围扩张；
2. **目标**：加入“只在已确认的服务访问边界内读取真实 PostgreSQL”；
3. **范围**：增加“本阶段不提供正式多服务选择和凭据生命周期能力”；
4. **功能需求**：统一模式判定、SQL 输入规则、Schema 语义、真实服务上下文；
5. **非功能需求**：补充不触库拒绝、服务隔离、错误分类、输出脱敏；
6. **验收标准**：每个边界至少有一个确定性 mock 测试或 API 测试；
7. **边界与约束**：明确单一技术切片不能升级为产品服务模型；
8. **已确认决策**：只有在 Design Review 和用户确认后才能保留；
9. **完成定义**：增加“路线图状态、Design 状态、PRD 状态三者一致”；
10. **开放问题**：保留所有未决项，不要用执行 AI 的实现假设代替决策。

## 建议验收标准

以下不是要求立即加入的最终 AC，而是 PM 整理 PRD 时应覆盖的验收方向：

- [ ] PRD、Design、路线图对 P4.2 的阶段、状态和实施顺序一致；
- [ ] Design 已完成 Review，并留下用户确认记录；
- [ ] mock/真实模式只有一个唯一判定入口；
- [ ] 多语句、写入 CTE、非法输入被拒绝且不触库；
- [ ] 无 DSN、无权限、连接失败、超时、空结果和对象不存在都有稳定降级；
- [ ] 真实访问不会绕过后端 Tool/Connector、服务上下文和权限边界；
- [ ] Schema 和表名语义有明确限制；
- [ ] `show_create_table` 对未支持结构诚实标记，不伪装成完整可执行 DDL；
- [ ] mock S1–S4 行为和既有接口契约保持不变；
- [ ] 测试证据、改动文件和 PRD AC 逐条可追溯。

## 边界与约束

- 本文档只提供审查建议，不授权实现；
- 不得以“代码能跑”替代 Design Review、路线确认或用户确认；
- 不得因为 P4 已有真实 PostgreSQL，就自动推导出正式多服务、任意服务访问或凭据持久化能力；
- 不得把 mock 评测结果描述成真实数据库执行结果；
- 不得把工具输出直接升级成完整诊断结论或完整 DDL 能力；
- 所有新增公开 API、迁移、Connector、真实外部访问和权限行为仍需单独过工程闸门。
