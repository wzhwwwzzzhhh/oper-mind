# P4.3 及之后 PRD 工程审查工作规则

## 背景

从 P4.3 开始，PRD 审查不再回溯 P4.2，也不对 P4.2 的路线、Design 或实现状态做结论。

本规则的任务是：在每个新的 P4.3+ 工作包进入实现前，确认 PRD 能够约束执行 AI，避免产品方向、工程边界和验收范围在实现过程中漂移。

## 目标

- 保持 PRD 与 OperMind 产品定义、路线图和开发规范一致；
- 让 PM 能快速看到需要补充、改写或确认的需求；
- 让执行 AI 可以逐条映射功能需求、边界和 AC；
- 在真实外部访问、高风险能力或公开契约变更前及时阻塞；
- 保持建议文档与 PRD 的域结构一致，方便 PM 回写整理。

## 范围

### 做什么

- 审查 P4.3 及之后 PRD 的背景、目标、范围、功能需求和验收标准；
- 检查 PRD 与产品事实源、路线图、开发规范和关联 Design 的一致性；
- 检查实现工作包是否越过“不做什么”或新增未确认能力；
- 为每条阻塞项提供具体文档位置、影响和修改建议。

### 不做什么

- 不审查 P4.2 及之前的历史工作包；
- 不直接替 PM 做产品排期、服务优先级或用户确认决策；
- 不把建议文档当作正式 PRD 或 Design；
- 不因为代码已经实现，就反向把越界行为合理化为需求；
- 不代替后端测试、前端测试或正式 Code Review。

## 工程审查结构

### 1. 背景

确认 PRD 说明的是用户/运维问题，而不是某个技术切片、demo 或临时脚本本身。

### 2. 目标

目标必须能映射到正式产品主链：会话工作台、服务中心、多 Agent、受控 Tool/Connector、安全 Trace、调查、审批或验证中的一个或多个明确能力。

### 3. 范围

必须分别列出：

- 做什么；
- 不做什么；
- 本阶段允许修改的产品边界；
- 明确留给后续阶段的能力。

### 4. 功能需求

每条需求描述行为、输入、输出、权限和降级，不把实现文件、类名或临时查询方案误写成产品需求。

### 5. 非功能需求

至少检查：

- 只读/最小权限；
- 参数校验和超时；
- 脱敏与审计摘要；
- 无配置、失败、超时、空数据和不可用状态；
- mock 与真实能力的诚实区分；
- 并发、恢复和回归行为。

### 6. 数据与接口影响

如果涉及公开 API、数据库迁移、Connector、真实服务、凭据、权限、监控或持久化，必须确认 Design → Review → 用户确认是否完成。

### 7. 验收标准

每条 AC 都要能回答：

```text
在什么条件下
系统执行什么行为
用户或测试能观察到什么结果
失败/拒绝时是什么稳定结果
```

### 8. 边界与约束

检查 PRD 是否明确禁止：

- 任意 SQL、Shell、DDL、DML 或网络访问；
- 前端直连用户服务；
- 凭据进入日志、Trace、响应、截图或数据库普通字段；
- 将 demo、mock、快照或历史数据伪装成正式能力；
- 未确认的高风险动作自动执行。

### 9. 已确认决策

只有经过 Design → Review → 用户确认的内容才能标为“已确认决策”。草案、讨论意见和实现猜测必须放到“开放问题”或关联 Design 中。

### 10. 完成定义

DoD 至少包含：

- PRD 全部 AC 有证据；
- 相关测试通过；
- 实际改动没有越过“不做什么”；
- 新增工程闸门已经完成确认；
- 需求、代码、测试和变更文件可追溯。

## 建议输出格式

```text
# PRD 工程审查建议：<标题>
结论：PASS / PASS WITH FOLLOW-UPS / FAIL
PRD：<路径>
阶段：P4.3 或之后的具体阶段

阻塞项：
- [阻塞] <文档冲突、范围越界、未确认能力或安全问题>

高风险项：
- [高] <可能造成实现漂移或后续返工的问题>

建议项：
- [建议] <可在本阶段或后续整理的问题>

建议修改：
- <对应 PRD 章节和可执行的修改方向>

验收证据：
- <AC、测试、文件或 Design 依据>

PM 处理结果：
- <待 PM 填写>
```

## 审查结论规则

- 存在 `[阻塞]`：FAIL，不允许直接进入实现；
- 只有 `[高]`：PASS WITH FOLLOW-UPS，必须登记后才能进入实现；
- 只有 `[建议]`：PASS，可进入实现，但建议纳入 PRD 整理；
- 所有问题处理完后，PM 应把最终决策回写到正式 PRD/Design。

## 开放问题

> P4.3 具体 PRD 产生后，在对应域目录创建专项建议文件，不在这里提前替 PM 决定具体产品方案。

## PM 处理结果

> 待 PM 填写：启用日期、适用阶段、评审责任人、正式文档回写位置。
