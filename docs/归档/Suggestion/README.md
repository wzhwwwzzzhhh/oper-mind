# PRD 工程建议索引（docs/Suggestion/）

> 本目录用于记录 **P4.3 及之后** `docs/prd/` 的工程化审查、范围纠偏和待 PM 决策事项。
> P4.2 及之前的内容不属于当前流程；历史审查材料仅保存在 `archive/`，不作为当前工作依据。

## 当前流程范围

- **起始阶段：P4.3**；
- 只审查 P4.3 及之后的新 PRD、Design 和实现工作包；
- 每个建议文件尽量与 `docs/prd/` 的域结构一致，例如会话相关建议放在 `session/`；
- 建议不是产品事实源，也不替代 PRD、Design、路线图或开发规范；PM 处理后，应回写到正式文档。

## 使用规则

1. 新 PRD 进入评审前，先确认它属于 P4.3 及之后的工作范围。
2. 建议按对应 PRD 建立一份同域审查文档，并尽量复用 PRD 的章节：背景、目标、范围、功能需求、非功能需求、数据与接口、验收标准、边界与约束、已确认决策、完成定义、开放问题。
3. `[阻塞]` 表示不能安全开工或不能判定为通过，必须先由 PM 处理或取得用户确认。
4. `[高]` 表示容易造成实现漂移、错误产品承诺或后续返工，应在本工作包内处理。
5. `[建议]` 表示可以不阻塞当前工作，但应在 PRD 定稿或阶段验收时处理。
6. 建议处理完成后，PM 应在对应 PRD 或 Design 中留下明确决策，不以本目录中的建议文本作为最终决策。

## P4.3 起步检查

任何 P4.3 工作包开始前，先回答：

- 对应的 PRD 文件是哪一个？
- 它是否与 `docs/产品定义.md`、`docs/路线图.md`、`docs/开发规范.md` 一致？
- 关联 Design 是否已经完成 Design → Review → 用户确认？
- 本工作包的“做什么”和“不做什么”是否清楚？
- 每个实现项是否能映射到 PRD 功能需求或 AC？
- 是否触及新服务类型、Connector、真实连接、凭据、公开 API、迁移、监控、权限、审批/执行或破坏性改动？

任一问题无法回答时，先写建议，不直接进入代码实现。

## 建议文档模板

建议文档应至少包含：

```text
背景
当前结论
目标
范围
  做什么
  不做什么
问题清单
建议修改
验收标准建议
边界与约束
完成定义
开放问题
PM 处理结果
```
