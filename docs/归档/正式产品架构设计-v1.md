# OperMind 正式产品架构设计 v1（待确认）

> 状态：**Design 草案，等待产品确认；不得据此直接实施数据库迁移、真实服务连接、凭据保存或公开 API 变更。**  
> 设计日期：2026-07-31  
> 依据：当前 Python 代码、当前产品文档，以及 Java 参考项目 `devops-copilot` 的现有实现。

## 0. 这份设计解决什么问题

OperMind 要做的是一个正式的 Web 产品，而不是“把多个 Agent 串起来做演示”。用户应把它当作面向运维场景的对话系统使用：

1. 在类似 DeepSeek 的会话界面中提问、追问，或下达受控指令；
2. 选择一个已接入的 PostgreSQL、MySQL、Redis 等服务作为上下文；
3. 系统按问题需要调度多个专业 Agent，读取受控的监控和诊断事实；
4. 以可读的结论、证据和简要 Trace 回答；
5. 对风险操作生成提案，经过人工审批、白名单执行和验证；
6. 在会话和服务详情页留下可追溯记录。

**第一个要真正跑通的问题仍是“数据库慢查询”。** 但“订单表缺少某个索引”只能作为研发验证场景，不能继续成为产品模型、服务模型和前端信息架构的边界。

## 1. 调研结论：多 Agent 结构还在，但目前是两套尚未统一的资产

### 1.1 当前 Python 项目已有的可复用资产

| 资产         | 当前位置                                                                    | 结论                                                                           |
| ---------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 多 Agent 调度 | `backend/src/core/bootstrap.py`、`coordinator.py`、`graph.py`             | 已有协调器和 LangGraph 路由/串行/并行编排能力。                                               |
| 专业角色       | `backend/src/agents/`                                                   | 已有 DB、Log、Server、Report Agent。它们是后续正式 Agent Runtime 的起点。                     |
| Tool 基础    | `backend/src/core/tool_registry.py`、`backend/src/tools/`                | 已有 Tool 注册、调用和 mock 数据，但目前接口偏实验性，不能直接等同正式受控工具网关。                             |
| 会话与运行留痕    | `backend/src/api/v1/`、`application/`、`domain/records.py`、`persistence/` | 已有 Session、Message、DiagnosisRun、RunEvent、结构化 Result、SSE、审批/执行/Verify 的持久化骨架。 |
| 证据模型       | `backend/src/domain/evidence.py`                                        | 已有 Pydantic 化的 Evidence、RootCause、Risk、AgentSummary，适合作为正式事实输出基础。            |
| 第一个诊断纵切面   | `backend/src/infrastructure/diagnosis/demo_orders/`                     | 已有 PostgreSQL 慢查询的受控采集、固定动作和验证实现，可迁入新的 Connector/Tool 体系。                    |
| 现有前端       | `frontend/src/features/workbench/`、`frontend/src/features/services/`    | 已有会话工作台、结果、提案和服务中心页面基础。                                                      |

### 1.2 当前缺口：不是“没有多 Agent”，而是“多 Agent 尚未产品化”

目前代码实际分成两半：

```text
旧多 Agent Runtime
Coordinator + LangGraph + DB/Log/Server/Report Agent + 本地 Tool/Memory
                 │
                 │ 尚未正式接入
                 ▼
新产品 API / 持久化骨架
Session + Run + SSE + Evidence + Proposal/Approval/Execution/Verify + 前端工作台
```

其中旧 Runtime 仍包含 `thinking`、进程内状态和本地 JSON 长期记忆等实验性实现；旧 `/diagnose` 接口甚至可以按参数返回思考链路。这与正式产品“只展示安全 Trace、不展示 CoT”的要求冲突。另一方面，新 v1 产品层已经具备较好的会话、Run、事件、审批和持久化骨架，但服务仍是静态的 `order-service`，诊断执行器也仍是固定场景路由。

因此，后续不是推倒重写，也不是继续堆旧工作包；而是把两套资产**收敛为同一条正式运行主链**。

### 1.3 MCP、知识库和记忆的真实现状

- **MCP：当前没有 MCP Client、MCP Server 或 MCP Tool Adapter。** 现有 `ToolRegistry` 是项目内部工具注册，不是 MCP。
- **会话记忆：已有。** 持久化的 Session 和 Message 是正式产品应优先使用的会话记忆。
- **任务记忆：已有基础。** Run、RunEvent、Evidence、Result、Proposal/Execution/Verify 是一次调查的可审计任务上下文。
- **长期记忆：现有 `data/memory.json` 关键词匹配实现仅是旧实验资产。** 它不能作为多用户、可治理的正式“经验记忆”方案。
- **知识库 / RAG：当前未实现。** 不能在页面或文档中伪装为已有能力。

## 2. 从 Java 参考项目学习什么，而不照搬什么

Java 参考项目已经验证了一个 DevOps Copilot 产品应具备的模块感：会话与消息、服务连接、数据库/Redis 等服务面板、模型设置、工具调用记录、图编排、风险动作审批、知识库入口。这些都是 OperMind 应继承的**产品模块视角**。

Python 版本的升级方向如下：

| Java 项目中的做法                     | OperMind 的继承与升级                                             |
| ------------------------------- | ----------------------------------------------------------- |
| 单个编排图驱动 ReAct、工具调用、审批和执行        | 保留图编排，但采用“协调 Agent + 专业 Agent + 非 Agent 安全策略层”的职责分离。        |
| 会话、消息、连接、工具日志是独立实体              | 继续采用持久化会话、服务、Run、Trace、证据、提案和执行记录。                          |
| 每类中间件有专门 Controller / Dashboard | 改为统一的 Service / Connector / Capability 模型，避免每增加一种服务就复制一套系统。 |
| 可填写服务连接参数                       | 前端仍提供服务接入，但密码不能以明文持久化或回显，必须使用加密凭据引用。                        |
| 有审批节点                           | 审批、白名单、执行和 Verify 继续保留，但它们属于确定性安全工作流，不属于 LLM 自由决策。          |
| 有模型、RAG、经验记忆入口                  | 作为后续独立能力包；先不把它们和首条慢查询主链混在一起。                                |

一句话：**借鉴 Java 项目的“完整产品模块”，用 Python 重建更清晰的多 Agent 与安全边界。**

## 3. 目标产品体验与信息架构

### 3.1 默认页面：会话，而不是服务列表或实验控制台

根路由应进入会话工作台。整体视觉与交互接近现代对话产品：

```text
┌──────────────┬─────────────────────────────────────────┬──────────────────────┐
│ 左侧栏       │ 会话主区                                  │ 可展开上下文栏       │
│ - 新建会话   │ - 当前会话消息                            │ - 已关联服务         │
│ - 会话列表   │ - 回答 / 证据 / 建议                      │ - 简要 Trace         │
│ - 服务中心   │ - 输入框、服务选择、受控操作状态          │ - 审批 / 执行 / 验证 │
│ - 设置（后） │                                         │                      │
└──────────────┴─────────────────────────────────────────┴──────────────────────┘
```

- 用户可在“无服务上下文”的会话里先问通用问题；需要真实调查时，系统要求选择已接入服务。
- 会话支持关联一个或多个服务。首个界面可优先展示一个“当前服务”，但领域模型不要把会话永久限制为单服务。
- 服务中心是一级入口，但不是默认首页；服务详情页可直接“在此服务中发起调查”。
- 当前前端根路由跳转到 `/services`、标题带旧阶段标识、右栏说明固定订单靶场，这些都与目标体验不一致，后续应在产品壳重构工作包中移除。

### 3.2 会话里的 Trace：可理解，不暴露模型隐藏推理

默认折叠展示：

```text
已理解问题 → 已分派数据库与日志角色 → 已完成 3 项只读读取
→ 已汇总 4 条证据 → 已生成诊断结论
```

展开后只能看到结构化审计事实：

| 字段      | 示例                       |
| ------- | ------------------------ |
| 阶段      | 证据收集                     |
| 角色      | 数据库诊断 Agent              |
| 工具类别    | PostgreSQL 只读计划分析        |
| 状态 / 耗时 | 完成 / 182 ms              |
| 摘要      | 已识别索引使用情况；未返回原始 SQL 或参数。 |
| 证据引用    | `evidence-xxx`、观察时间、来源状态 |

**禁止展示：** Prompt、模型原始 CoT、工具原始入参、密码、完整连接串、原始日志、原始 SQL、堆栈和未脱敏异常。

### 3.3 服务中心与监控页

服务中心管理的是用户真实接入的“服务实例”，而不是硬编码业务服务卡：

```text
服务中心
├── PostgreSQL：订单库（已连接 / 降级 / 未启用）
├── MySQL：业务库
└── Redis：会话缓存
```

每个服务详情页分为：

1. **概览**：类型、标签、连接状态、权限边界、最后检查时间；
2. **当前监控**：由对应 Connector 给出的当前快照和来源状态；
3. **可用调查能力**：例如“慢查询调查”“连接异常调查”；
4. **调查与操作留痕**：从该服务发起的 Run、提案、审批、执行、验证；
5. **设置**：名称、标签、连接参数、凭据更新、禁用/删除（受权限控制）。

首版监控必须诚实地标为“当前快照”。在尚未实现后台采集、历史库存储和告警规则之前，不能把前端轮询伪装为完整时序监控平台。

## 4. 正式领域模型：从静态靶场服务迁到可管理服务

### 4.1 核心对象

| 对象                                                           | 责任                                     | 当前资产的处理方式                              |
| ------------------------------------------------------------ | -------------------------------------- | -------------------------------------- |
| `Conversation`                                               | 用户持续对话的容器                              | 复用现有 Session 概念，逐步统一命名。                |
| `Message`                                                    | 用户、助手、系统的可见消息                          | 复用现有持久化消息。                             |
| `ManagedService`                                             | 用户接入的 PostgreSQL / MySQL / Redis 等服务实例 | 新建，替代静态 `ORDER_SERVICE_ID` 注册表。        |
| `ServiceCredential`                                          | 加密的凭据密文或安全密钥引用                         | 新建；永不向 API 回显明文。                       |
| `ServiceCapability`                                          | 某服务当前真正可用的只读调查、监控和动作能力                 | 新建；由 Connector 和策略共同决定。                |
| `ServiceSnapshot`                                            | 一次有时间戳、来源状态明确的监控快照                     | 从现有固定快照模型泛化。                           |
| `InvestigationRun`                                           | 一次消息触发的 Agent 调查生命周期                   | 复用并泛化现有 `DiagnosisRun`。                |
| `AgentTask` / `AgentOutput`                                  | 一个角色在某次 Run 中的受控输入与结构化输出               | 新建；替代进程内 `agent_results` / `thinking`。 |
| `Evidence` / `DiagnosisResult`                               | 可审计事实和用户可读结论                           | 复用现有 Evidence / Result 模型。             |
| `ActionProposal` / `Approval` / `Execution` / `Verification` | 风险操作闭环                                 | 保留现有强约束模型，取消任何通用执行路径。                  |

### 4.2 服务、会话和 Run 的关系

```text
Conversation 1 ── * Message
Conversation 1 ── * InvestigationRun
Conversation * ── * ManagedService       （通过 ConversationServiceBinding）
ManagedService 1 ── * ServiceSnapshot
InvestigationRun * ── * ManagedService   （本次实际使用的服务上下文）
InvestigationRun 1 ── * AgentTask
InvestigationRun 1 ── * TraceEvent
InvestigationRun 1 ── * Evidence
InvestigationRun 0..* ── ActionProposal ── Approval / Execution / Verification
```

这解决两个当前限制：

- Session 不再只允许 `order-service`；
- 一次复杂调查可以在同一 Run 中使用多个已授权服务，但每一次工具调用仍要明确目标服务和能力边界。

### 4.3 凭据方案（推荐，待确认）

为支持“用户在页面接入服务”，推荐 v1 使用以下边界：

1. 接入表单通过 HTTPS 发送连接信息；
2. 后端只将**加密后的密码/Token**保存在应用元数据数据库中；加密主密钥仅存在部署环境变量或专用 Secret Provider；
3. API 返回连接配置时只返回掩码值和 `credential_configured`，绝不返回明文；
4. Connector 在真正调用时短暂解密，日志、RunEvent、Trace、错误响应全部不得写入凭据；
5. 支持“测试但不保存”和“保存后测试”；删除服务时删除其凭据密文，不对外部服务执行清理；
6. 后续若部署到团队环境，再抽象为 Vault / 云 Secret Manager 的 `secret_ref` 实现。

不能照搬 Java 参考项目中把 `password` 作为普通连接实体字段的方式。

## 5. 多 Agent 运行时：Agent、Connector、Tool、策略层必须分开

### 5.1 角色划分

```text
用户消息 + 会话历史 + 已绑定服务
                 │
                 ▼
        Coordinator / Supervisor Agent
        - 理解意图、选择角色、形成受控任务计划
                 │
       ┌─────────┼──────────────────┐
       ▼         ▼                  ▼
数据库诊断 Agent  日志诊断 Agent      服务/指标诊断 Agent
Redis 诊断 Agent（接入 Redis 后）
       │         │                  │
       └─────────┴───────┬──────────┘
                           ▼
                  Synthesis / Report Agent
                           │
                  结构化结论、建议、提案候选
                           ▼
             Policy Engine（非 Agent，最终裁决）
                 ├── 只读：允许受控 Tool 执行
                 └── 动作：提案 → 审批 → 白名单执行 → Verify
```

- **Coordinator / Supervisor Agent**：只负责理解任务、选择已注册角色和排序/并行策略，不能自行访问数据库、Shell 或网络。
- **专业 Agent**：只基于本次 `AgentTask` 中允许的服务、能力、工具和已有事实开展工作；输出结构化 Findings、Evidence 引用和下一步建议。
- **Synthesis / Report Agent**：负责把多个专业输出整合成用户可读的结论和建议；不能发起未授权工具调用。
- **Policy Engine / Action Executor**：不是 Agent。它以确定性代码校验身份、服务归属、工具能力、输入模式、风险级别、审批状态和动作白名单。

多 Agent 不等于每个问题强行调用所有角色：

- “Redis 当前是否健康？”可以只由 Redis Agent 完成；
- “接口变慢，帮我定位”可以并行调度服务指标、日志和数据库角色；
- 服务未绑定、能力未启用或证据不足时，系统必须追问或明确说明，而不是猜测或伪造读取。

### 5.2 统一运行链路

```text
发送消息
→ 创建 Message 与 InvestigationRun
→ SSE: run_started
→ Coordinator 生成结构化任务计划
→ SSE: task_planned / agent_dispatched
→ 专业 Agent 经 Tool Gateway 调用受控 Connector
→ Connector 返回脱敏、Pydantic 化 Evidence
→ SSE: tool_completed / evidence_collected
→ Synthesis 汇总诊断结果
→ SSE: result_ready
→ 写入 Assistant Message、Result、Trace、服务活动
→ 如有风险操作：仅创建 Proposal，等待人工审批
```

这条链路应以现有 v1 的 Session、Run、RunEvent、Result 和 SSE 为唯一产品主线。旧 `/diagnose` 及其可返回 `thinking` 的调试接口不再是正式前端调用入口，应在迁移后废弃或仅保留为内部开发接口。

### 5.3 Agent 输入输出契约

每个 Agent 不再拿到全局可变 `thinking_log` 和任意 Tool Registry，而是接收显式任务：

```text
AgentTask
- run_id / task_id
- role
- objective
- conversation_context（已裁剪、脱敏）
- bound_service_ids
- allowed_tool_ids
- input_evidence_refs
- deadline / retry_policy

AgentOutput
- status
- findings（结构化判断）
- evidence_refs
- recommended_next_tasks
- recommended_action_template（仅候选，不可执行）
- safe_summary
```

现有 `BaseAgent`、LangGraph `DiagnosisState`、`agent_thinking` 和文件型 LongTermMemory 都是可迁移代码资产，不是最终运行契约。新的 `BaseAgent` 应在后续实现中收敛到上述显式输入输出接口，并删除生产路径的 `print` 与 CoT 暴露能力。

## 6. Connector 与 Tool 网关

### 6.1 三层职责

| 层                       | 做什么                                                            | 不做什么                          |
| ----------------------- | -------------------------------------------------------------- | ----------------------------- |
| `Connector`             | 管理某种服务的驱动、连接测试、健康读取、能力发现和底层超时                                  | 不理解用户问题，不决定是否执行风险操作。          |
| `Tool`                  | 一个可审计的小能力，例如 `postgres.slow_query_summary`、`redis.info_memory` | 不接收模型任意 SQL/Shell，不返回未脱敏原始数据。 |
| `Tool Gateway / Policy` | 根据 Run、服务、角色、Tool schema、权限和风险策略批准或拒绝调用                        | 不把控制权交给模型文本。                  |

每个 Tool 都必须具备：明确 ID、目标服务类型、风险等级、Pydantic 入参/出参、超时、脱敏规则、mock fallback、审计摘要和测试。

### 6.2 第一阶段支持的能力边界

产品框架面向 PostgreSQL、MySQL、Redis 三类服务，但首个真正完成的诊断问题仅聚焦：

```text
数据库慢查询：现象确认 → 查询/计划/索引相关受控事实 → 根因 → 建议
→（仅命中明确白名单时）提案 → 审批 → 执行 → Verify
```

推荐落地顺序：

1. 先实现统一 Connector / Tool / ServiceCapability 框架；
2. 将现有 PostgreSQL 慢查询纵切面迁入该框架，作为第一条真实端到端能力；
3. 再增加 MySQL 的同类“慢查询”只读能力；
4. 再增加 Redis 的健康、内存、连接、慢日志等**只读**能力；
5. 每种动作（建索引、清缓存、重启等）都按服务类型和动作模板单独设计，不因为已有审批框架就自动开放。

因此，首版不会出现“页面上显示 PostgreSQL / MySQL / Redis 都已可连接，但实际只有 mock 或硬编码服务”的假能力。未完成的 Connector 必须显示“未启用”。

### 6.3 关于 MCP

MCP 不是当前主链的前置条件。先把项目内的 Tool Gateway 和 Connector 接口做稳定；以后如果要接入 MCP，MCP 应只是一个受同样策略约束的 Adapter：

```text
Agent → Tool Gateway / Policy → MCP Adapter（允许列表）→ 已授权 MCP Server
```

不能让模型直接获得任意 MCP Server、任意工具或任意网络能力。

## 7. 监控、记忆、知识库与模型设置的演进边界

### 7.1 监控

| 阶段   | 能力                 | 产品表达                      |
| ---- | ------------------ | ------------------------- |
| 当前快照 | 用户打开服务页或调查触发一次受控读取 | 显示“最后检查时间、来源状态、当前值”。      |
| 历史监控 | 后台采集、保留策略、趋势图      | 需要单独设计任务调度、存储、成本和租户隔离。    |
| 告警   | 规则、去重、通知、确认/恢复     | 需要单独设计，不能由 LLM 自动报警或自动恢复。 |

推荐先把“当前快照 + 从服务进入调查”做扎实，再增加历史和告警。

### 7.2 记忆

正式产品将记忆拆成四类：

1. **会话记忆**：持久化 Message，按会话裁剪后给 Coordinator；
2. **调查记忆**：本次 Run 的 AgentTask、Evidence、Result、Proposal 与执行记录；
3. **服务运营记忆**：ServiceSnapshot、调查和操作留痕；
4. **知识记忆（后续）**：受允许目录中的 Markdown 文档检索结果，带来源引用和权限边界。

这比一个 Agent 自己写 `memory.json` 更适合正式产品。文件型长期记忆可暂时保留在旧代码中作为开发资产，但不能接入正式主链。

### 7.3 知识库 / RAG

第一版知识库的推荐方案是：

```text
允许目录内 Markdown → 后端程序全文检索 → 返回带路径/片段/更新时间的受控引用
```

先不做用户文件上传、向量库、Agentic RAG、知识图谱或所谓“Gbrain 知识库”。这些能力可以在慢查询主链稳定之后单独设计；尤其文件上传和外部知识源涉及权限、索引、删除与数据隔离。

### 7.4 用户自带模型 API Key

这是目标能力，但不应插入第一个慢查询纵切面。推荐分两步：

1. **基础阶段**：部署方通过环境配置默认模型，保留确定性 mock fallback；
2. **模型设置阶段**：用户可新增兼容 Provider 的配置和 Key，采用与服务凭据相同的加密、掩码、连接测试、作用域和删除策略。

模型 Key 绝不写入浏览器持久化存储、普通日志、Trace 或数据库明文字段。

## 8. 现有代码的迁移策略：保留有价值的，不让旧边界继续支配产品

### 8.1 可直接复用或重构复用

- v1 API 的请求关联、错误包络、SSE、Session / Message / Run / Event / Result 持久化；
- Evidence、RootCause、Risk、Proposal、Approval、Execution、Verify 等强类型模型；
- 前端 Workbench、Service Center、提案与结果面板；
- PostgreSQL 慢查询的受控 Collector、mock 与 Verify 测试资产；
- Coordinator、DB / Log / Server / Report Agent 的角色概念和 LangGraph 的并行编排能力。

### 8.2 必须替换或隔离的旧边界

- `SessionData.service_id` 对静态 `ORDER_SERVICE_ID` 的校验；
- 静态服务注册表和只支持一个固定场景的路由；
- `/diagnose` 对前端暴露 `show_thinking` / `thinking` 的旧接口；
- 全局可变 `agent_thinking`、进程内 `StateManager`、文件型 LongTermMemory；
- 允许 Agent 从任意全局 Tool Registry 自由取工具的模式；
- 旧前端中以旧阶段、固定靶场为中心的路由、文案和右侧栏。

这些不会在没有设计确认的情况下直接删除。实现时应通过兼容层和测试把正式路径迁过去，再删除已不再调用的旧路径。

## 9. 已确认的高层实施路线：按四个产品阶段推进

> 这四个阶段已经获得用户确认。每个阶段内仍需先完成相应详细 Design → Review → 用户确认，才可实施。

### 第一阶段：正式会话与多 Agent 内核整合

将会话、Run、SSE、结果持久化与现有多 Agent 图接成一条正式产品请求链：

```text
会话消息 → Coordinator → DB / Server / Log Agent
→ Debate / Reflection → Report Agent
→ 正式回答 + 安全 Trace + 会话留痕
```

目标是使用户能从正式会话页面使用多 Agent 协作能力。多 Agent 图是产品智能内核；Trace 仅展示安全摘要，不展示 CoT。

### 第二阶段：搭全正式产品骨架，并以简单慢查询验证通路

建立会话、服务上下文、服务中心、PostgreSQL / MySQL / Redis 服务实例、基础监控入口、Connector / Tool 统一框架，以及风险操作的提案与审批框架。

慢查询在这一阶段只是一个简单验证问题：它用于验证“选择服务 → DB Agent 调用受控 Tool → 结果 / Trace / 服务留痕”这条通路，而不构成一个需要单独深挖的大阶段。

### 第三阶段：逐步丰富和深化运维问题能力

在统一框架中渐进加入数据库、Redis、服务/主机、日志和跨来源联合排障能力。每项能力复用会话、服务、Agent、Tool、Trace、结果和留痕，不另起产品流程。

### 第四阶段：逐步增强动作、知识与平台能力

在主链稳定后，按真实需求扩展受控动作闭环、Markdown 知识检索、模型设置、正式记忆、历史监控、告警、认证、团队与 RBAC 等能力。

每个工作包可包含 1–3 个紧密切片，结束时集中 Test → Review → Commit；不再为每一小步单独审查和提交。

## 10. 本设计明确不做的事情

- 不恢复或继续以旧实验文档、演示脚本、固定阶段名称驱动产品；
- 不把所有 Agent 都强行用于每一个问题；
- 不把 Agent 的隐藏思考、Prompt 或完整原始工具数据展示给用户；
- 不让模型生成并直接执行任意 SQL、Shell、DDL、DML 或网络命令；
- 不把一次服务读取伪装成实时监控系统；
- 不把当前本地 JSON 记忆或内部 Tool Registry 称为 MCP、RAG 或正式知识库；
- 不在未获授权时连接、迁移、读取、写入或清理任何真实外部服务。

## 11. 当前确认状态与仍待确认的详细决策

已经确认：

1. OperMind 是会话式多 Agent DevOps Copilot 正式产品，不是实验或演示脚本集合；
2. Coordinator → 领域 Agent → Debate / Reflection → Report Agent 是需要保留并产品化的智能内核；
3. 慢查询只是第二阶段用于验证产品通路的简单问题，不是独立的大型产品阶段；
4. 产品按本设计第 9 章的四个阶段推进。

仍待在具体实施前逐项完成 Design / Review / 用户确认：

- 服务接入表单、服务实例模型、凭据保存与连接测试；
- PostgreSQL、MySQL、Redis 的真实 Connector 范围和先后顺序；
- 当前快照、历史监控、告警等监控深度；
- 用户模型 Provider / API Key 与知识库的具体方案；
- 身份、多用户、团队和 RBAC 的引入时机；
- 每一种高风险动作的白名单、审批、执行和 Verify 规则。

在用户恢复开发指令前，本设计只保存已确认方向，不据此自行实施上述详细决策。
