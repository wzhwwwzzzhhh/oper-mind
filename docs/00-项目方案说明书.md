## 一、项目概述

### 1.1 背景与问题

现代运维体系中，一次故障排查通常涉及多个数据源：

| 数据源 | 工具                            | 排查内容        |
| --- | ----------------------------- | ----------- |
| 服务器 | `top`, `htop`, `ps`           | CPU、内存、进程   |
| 数据库 | `EXPLAIN`, `SHOW PROCESSLIST` | 慢 SQL、锁、连接池 |
| 日志  | `grep`, `ELK`                 | 错误日志、异常模式   |

工程师需要**在多个平台间切换**，手动关联信息才能定位根因。本项目的目标是让多个 AI Agent 自动完成"全面排查 → 辩论共识 → 反思复审 → 输出报告"的闭环。

### 1.2 项目定位

| 维度     | 内容                             |
| ------ | ------------------------------ |
| 毕业设计方向 | 大模型与多智能体                       |
| 核心贡献   | 多 Agent 协作模式（直达/链式/并行）的设计与对比实验 |
| 项目类型   | 框架 + 应用，以运维诊断为落地场景             |

### 3.2 Layer 1：Coordinator Agent（协调器）

**职责**：理解用户问题，动态决定路由策略。

**三种路由策略**：

| 策略     | 触发条件        | 流程                                  | 示例                           |
| ------ | ----------- | ----------------------------------- | ---------------------------- |
| **直达** | 问题明确指向某个领域  | 直接路由到目标 Agent → Reflection → Report | "这个SQL为什么慢？" → DB Agent      |
| **链式** | 问题模糊，需要逐层排查 | Server → 中间件 → Log 逐层推进             | "系统很慢" → 先查Server，再查DB，再查Log |
| **并行** | 需要全面检查      | 同时分发到多个 Agent → 汇总                  | "大促结束，全链路体检"                 |

**路由策略由 LLM 根据用户输入动态决策，写死在 Coordinator 逻辑中。**

### 3.3 Layer 2：领域 Agent

#### Server Agent（服务器诊断）

| 工具                | 说明                            | 数据来源   |
| ----------------- | ----------------------------- | ------ |
| `check_cpu()`     | CPU 使用率、load average、高 CPU 进程 | psutil |
| `check_memory()`  | 总/已用/剩余/Swap                  | psutil |
| `check_disk()`    | 磁盘空间、IOPS、inode               | psutil |
| `check_process()` | 异常进程（僵尸、高内存、高 CPU）            | psutil |
| `check_thread()`  | 线程数异常、上下文切换                   | psutil |
| `check_network()` | 连接数、TIME_WAIT 堆积、带宽           | psutil |

#### 中间件 Agent — DB 模块（数据库诊断）

**已有的工具（直接复用）**：

| 工具                    | 说明             | 数据来源              |
| --------------------- | -------------- | ----------------- |
| `explain_sql()`       | EXPLAIN 分析执行计划 | MySQL JDBC / Mock |
| `show_index()`        | 查看表索引          | MySQL / Mock      |
| `show_create_table()` | 查看建表语句         | MySQL / Mock      |

**新增工具**：

| 工具                        | 说明              | 数据来源  |
| ------------------------- | --------------- | ----- |
| `show_processlist()`      | 查看运行中查询、锁等待     | MySQL |
| `check_connection_pool()` | 连接池使用率          | MySQL |
| `kill_query()`            | 终止长时间查询（高危，需审批） | MySQL |

| 工具                      | 说明       | 数据来源  |
| ----------------------- | -------- | ----- |
| `redis_slowlog()`       | 慢查询      | Redis |
| `redis_memory()`        | 内存使用、键过期 | Redis |

### 3.4 Layer 3：质量保障机制

#### Debate Arena（辩论场 — 可选）

**触发条件**：并行模式下，多个 Agent 给出不一致的诊断结论。

**流程**：

```
Agent A 说根因是 CPU 不足
Agent B 说根因是慢 SQL
         │
         ▼
  Debate Arena 列出分歧点
         │
         ▼
  Agent A 和 B 各自提供证据辩护
         │
         ▼
  Coordinator 或投票机制裁决
         │
         ▼
  达成共识 → 进入 Reflection
```

**设计意义**：当多个专家 Agent 意见不一时，单一 Agent 的结论不可信。通过辩论机制让证据说话，提升诊断可信度。

#### Reflection（反思复审 — 必备）

**触发条件**：每份诊断报告生成后。

**流程**：

```
Report Agent 出初稿
    │
    ▼
其他 Agent 交叉审核：
  • DB Agent 审核报告中的数据库部分
  • Server Agent 审核报告中的服务器部分
  • Log Agent 审核日志证据是否支持结论
    │
    ▼
有遗漏或错误 → 退回修改
验证通过 → 输出最终报告
```

**设计意义**：单一 Agent 可能有盲区或误判，交叉复审相当于"提交前让别人 Review 代码"，是质量保证的最后一道防线。

### 3.5 Layer 4：Report Agent（报告生成）

**职责**：将诊断结果转化为结构化的最终报告。

**报告格式**：

```
## 故障根因（一句话总结）

## 诊断依据
  - Server 证据：...
  - 数据库证据：...
  - 日志证据：...

## 根因链
  缺索引 → 全表扫描 → CPU飙升 → 请求超时

## 优化建议
  - 短期：加索引（ALTER TABLE ADD INDEX）
  - 长期：SQL 审核流程

## 预期效果
  - 扫描行数 50000 → 8000
  - CPU 使用率 80% → 20%

## 相关指标（图表数据）
  - CPU 趋势图
  - 查询响应时间分布
```

## 四、完整协作流程示例

### 直达模式

```
用户："帮我分析这个SQL：SELECT * FROM orders WHERE status = 'PENDING'"
         │
         ▼
Coordinator：路由策略=直达，目标=DB Agent
         │
         ▼
DB Agent：
  ① explain_sql → 发现 type=ALL 全表扫描
  ② show_create_table → status 字段无索引
  ③ show_index → 确认没有 idx_status
  ④ 综合判断：缺索引导致全表扫描
         │
         ▼
Reflection：Server Agent 审核 → DB Agent 自审 → 通过
         │
         ▼
Report：生成诊断报告 → 返回用户
```

### 链式模式

```
用户："系统很慢，经常超时"
         │
         ▼
Coordinator：路由策略=链式
         │
Step 1 ──▼──
Server Agent：
  check_cpu → CPU 80%，MySQL 进程占 50%
  check_memory → 正常
  初步判断：MySQL 负载高是瓶颈
         │
Step 2 ──▼──
Coordinator：下一个目标=中间件.DB
DB Agent：
  show_processlist → 大量 SELECT ... WHERE status='PENDING'
  explain_sql → 全表扫描 50000 行
  判断：status 字段缺索引
         │
Step 3 ──▼──
Coordinator：最后确认日志
Log Agent：
  search_logs("timeout") → 大量连接超时日志
  query_slow_log → 同一条 SQL 反复出现
  判断：慢 SQL 导致了连锁反应
         │
         ▼
Reflection → Report
```

### 并行模式

```
用户："明天大促，帮我检查一下系统整体健康度"
         │
         ▼
Coordinator：路由策略=并行，分发到所有 Agent
         │
         ▼
Server Agent → CPU/内存/磁盘 全部正常
DB Agent → 有慢查询风险（status 缺索引）
Log Agent → 无明显异常
         │
         ▼
Coordinator：三个 Agent 结论一致 → 无需 Debate
         │
         ▼
Reflection → Report
报告：系统整体健康，建议上线前给 status 字段加索引
```
