# Agent 经典工程问题学习地图

> 建立：2026-10-19。状态：学习主题已整理，逐题待讨论；未认定用户已经掌握。
> 用途：理解常见故障、原因和解法，结合 OperMind 开发逐步解决问题。
> 这是学习地图，不是开发检查清单或新增门禁；六类主题是我们的整理方式，不是行业统一分类，也不代表项目已经出现这些故障。

## 如何使用

我们从“Agent 死循环怎么办”开始意识到，需要学习经典工程问题。一次风险发现足以开启研究，但不能直接推出项目必须增加一整套治理系统。

每次选一个与当前开发相关的问题，按下面的顺序讨论：

1. 看一个具体故障，解释它为什么发生。
2. 查官方机制与工程案例，理解常见解法及其代价。
3. 对照项目，区分已有机制、已确认但未实施的设计、尚未验证的假设。
4. 判断现在需要解决、以后遇到再处理，还是当前不适用。

讨论记录放在[学习路线与问题记录](学习路线与问题记录.md)。只有明确影响当前开发的结论才转入对应 PRD／Design；反复出现且值得统一约束的事项，再考虑纳入工程规范。无需每一步重查所有主题，也不要求学完再开发。

## T01 · Agent 一直执行，却没有推进任务

**典型故障**：反复调用同一个工具、持续修改计划不交付、失败后原样重试，或多个 Agent 相互委派同一个问题。

**需要理解**：缺少退出条件、观察没有带来进展、工具反馈不清楚、任务完成标准不明确，可能产生相似表现。另有一种“卡住”是单次调用始终不返回，它与多轮循环不同。

**常见解法与代价**：能确定步骤时采用有界流程；开放循环设置合理的迭代／调用上限；单次阻塞使用相应 timeout。必要时再研究无进展检测。硬上限可能打断合理的长任务；重复调用也可能是正常轮询，不能机械判错。图步数上限无法替代单次调用的时间边界。

**项目联系**：V2 的首切片采用一次模型决策，随后直答、追问或执行一次比较；正常比较路径一次模型调用、一次 Tool。PRD 允许的 4 次模型调用是硬上限，不是正常流程必须循环 4 次。这是为验证 Run 接缝设置的有界切片；V2 的目标执行内核是 ReAct 循环，后续切片切换到多轮循环，并按步数、调用数、超时和预算治理。

已有源码参照（2026-10-19 只读核对）：[BaseAgent](../../backend/src/core/agent.py) 支持 `max_steps`（基类默认 10），并显式设置图的 `recursion_limit`；[ReAct 图](../../backend/src/core/react_graph.py)在一轮工具执行后检查步数，耗尽则结束。实际值取决于调用方配置。这证明现有实现包含步数边界，不代表已验证所有运行路径，也不保证单次阻塞调用会结束。

**资料**：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 的 Agents 章节；[GRAPH_RECURSION_LIMIT](https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT)。后者说明达到步数上限既可能源于循环，也可能源于合理的复杂流程。

## T02 · 模型会调用工具，但工具用起来不可靠

**典型故障**：选错工具、误解参数、传入不存在的资源，工具报错后继续提交相同请求。

**需要理解**：工具职责重叠、参数含义模糊、输出太长或错误反馈缺少可用信息，都可能影响模型使用。还要区分“模型建议调用”“参数合法”“有权执行”和“执行成功”。

**常见解法与代价**：简化工具职责、改进描述和参数、提供结构化结果与可用的安全错误反馈；程序校验调用资格。重试只适用于有机会恢复的错误，需理解重复执行的后果。增加工具数量或修改 Prompt 不一定解决接口问题。

**项目联系**：新增 Capability 时，用真实输入样例观察模型如何选择、如何传参，并核对 ToolGateway 的程序边界。当前文本比较的材料引用与确定性结果可作为学习样例；不因学习直接新增真实连接或权限。

**资料**：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 的 Appendix 2；已有 [A04 · Tools](官方资料/05-能力装配上下文与框架候选.md#a04)。

## T03 · 上下文越来越多，Agent 反而表现变差

**典型故障**：遗漏关键条件、沿用过时信息、混淆不同任务，或被大量工具输出干扰。

**需要理解**：上下文窗口容量与有效信息利用不同；历史、运行状态、材料、摘要和长期记忆也有不同用途。需要判断该选哪些信息、保留来源、何时更新。

**常见解法与代价**：选择相关信息、按需检索、限制工具输出、压缩或隔离上下文。摘要可能丢失事实，隔离也增加交接成本；不能把“更多历史”和“更多记忆”视为默认改进。

**项目联系**：V2 首闭环已有受理时冻结必要对话上下文的设计，且模型不接收 A/B 原文。随历史对话、第二 Capability 和子 Agent 的需要，再研究更多上下文策略。

**资料**：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)；关联学习问题 Q04、Q07。

## T04 · 中断、并发或重跑后，任务状态不再可信

**典型故障**：显示取消后又出现成功；重新提交造成重复操作；服务重启后任务悬空；多个 Run 互相覆盖结果。

**需要理解**：停止等待、取消请求、底层停止是不同事件；重试、重跑、恢复和重放也不等价。图 State／checkpoint 与应用 Run 各自负责什么，需要具体定义。

**常见解法与代价**：明确状态所有者、幂等、原子状态更新和迟到结果接纳规则；有持续运行需求时再研究持久化与恢复。checkpoint 能保存框架状态，但恢复是否安全仍涉及存储配置、节点重执行及副作用。

**项目联系**：结合既有 Run、取消、重跑学习；V2 Design 保留唯一事实写入者与取消竞争保护，并明确不做全局 deadline、线程强杀与完整恢复。文档不能把这些未提供的保证写成已实现。

**资料**：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)；[P03 · Coroutines and Tasks](官方资料/04-并发隔离与协作.md#p03)、[P06 · concurrent.futures](官方资料/04-并发隔离与协作.md#p06)；关联 Q06–Q09。

## T05 · 多个 Agent 加入后，协作成本超过收益

**典型故障**：重复调查、任务分工不清、遗漏交接信息、互相等待或委派，结果难以汇总，耗时与 token 消耗增长。

**需要理解**：哪些子任务真正独立，哪些需要共享上下文；谁承担最终交付；任务拆分收益是否足以抵消通信与协调成本。

**常见解法与代价**：先确认单 Agent 的瓶颈，再明确子任务目标、输入输出和责任，比较拆分前后的效果；协作深度和资源范围按实际流程设计。并行可能缩短时间，也可能增加总调用成本。

**项目联系**：进入 V2-D 子 Agent 或 V2-E 独立主 Agent 协作时深入研究。两者是平行方向，目前均未启用，不因为学习地图提前建分布式系统。

**资料**：[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)。这是特定研究业务的经验，不能直接作为 OperMind 应采用多 Agent 或获得同等收益的证据；关联 Q10、Q12。

## T06 · 演示能成功，却不知道整体是否可靠

**典型故障**：换个问法就失败；改模型或 Prompt 后旧任务退化；输出格式正确、文字流畅，实际结论却错误。

**需要理解**：程序测试、模型效果评测和真实业务验收回答的问题不同。结构合法不保证事实正确；一次成功也不能说明运行稳定。

**常见解法与代价**：从真实失败案例和代表性任务建立小型样例集，定义可检查的成功标准；必要时多次运行，比较质量、延迟、成本和失败。优先使用确定性校验与人工可核对样例；模型评分器本身也需要验证。

**项目联系**：从当前字面比较能力积累可手工核对的样例，分别验证决策与比较事实。确定性模型替身能测试控制逻辑，但不证明真实模型选能力的准确率；真实模型实验仍按仓库授权边界进行。

**资料**：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)；已有[评测与官方源码实例](官方资料/06-评测与官方源码实例.md)；关联 Q12。

## 从哪一题开始

先讨论 T01，用一个最小例子区分正常迭代、无进展循环和调用阻塞，再对照 V2 首闭环。每次讨论只留下：典型故障 → 原因 → 常见解法及代价 → 本项目何时需要处理。

讨论起点：如果主 Agent 已得到文本比较的完整结果，却反复要求再比较一次，这时缺少的是什么？又该由模型、图还是应用程序决定结束？这是假设案例，未复现为项目 Bug。

本页初始状态为“待讨论”，后续根据用户自己的解释和验证反馈记录理解进展。
