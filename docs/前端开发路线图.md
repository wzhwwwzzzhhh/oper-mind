# OperMind 前端开发路线图（并行演示轨）

> 创建日期：2026-07-18
> 定位：本文件是前端并行开发的**活路线图**，服务答辩演示与系统可视化；M4 实验和论文统计仍是科研主线。
> 当前后端状态：M6 已完成同步诊断、SSE 和健康检查契约；场景列表与实验结果查询仍未实现。M7 前端骨架已启动。

---

## 1. 目标与优先级

前端的目标不是复刻运维平台，而是让评委在答辩现场直观看到 OperMind 的核心价值：

```text
输入故障问题 / 选择演示场景
            ↓
路由策略差异（direct / chain / parallel）
            ↓
领域 Agent 协作、冲突检测、Debate、Reflection
            ↓
结构化诊断报告与可解释链路
```

优先级从高到低：

1. **诊断链路可视化**：体现多 Agent 协作，必须优先完成。
2. **场景化演示与最终报告**：保证答辩可稳定演示。
3. **实时 SSE 点亮效果**：提升观感；后端接口完成前允许用同步结果回放 fallback。
4. **实验结果图表**：在 M4 正式实验产物稳定后接入，不阻塞诊断演示 MVP。
5. 账户、权限、复杂运维大盘、实时主机监控等功能不在毕业设计当前范围内。

## 2. 当前基础与接口边界

### 2.1 已有后端接口

| 接口                   | 当前状态                 | 前端用途                                                                |
| -------------------- | -------------------- | ------------------------------------------------------------------- |
| `GET /health`        | 已有，返回 `status/mode/model` | 启动时检查后端连通性，展示 mock / real 状态。                                     |
| `POST /diagnose`     | 已有                   | 同步诊断 fallback；传 `show_thinking=true` 获取 result、thinking、trace、strategy。 |
| `GET /memory/stats`  | 占位                   | 前端暂不依赖。                                                             |
| `GET /diagnose/stream` | M6 已有                | SSE 实时诊断；监听 `progress/complete/error`。                                  |
| `POST /memory/clear` | 占位                   | 前端暂不依赖。                                                             |

现有同步诊断响应核心字段：

```ts
interface DiagnoseResponse {
  result: string;
  thinking?: string[];
  trace?: Array<{ node: string; detail: string }>;
  strategy: string;
}
```

### 2.2 前端联调所需后端增量

前端按下列契约开发；场景与实验接口未实现时采用本地固定数据，诊断主链路直接消费 M6 SSE。

| 接口                     | 优先级 | 目标用途            | 最小响应契约                                                       |
| ---------------------- | ---:| --------------- | ------------------------------------------------------------ |
| `GET /diagnose/stream` | ✅ 已有 | SSE 实时显示路由与节点进度 | `progress` 携带 `type/node/detail/timestamp`；`complete` 携带 `result/strategy/trace`。 |
| `GET /scenarios`       | P0  | 场景选择器           | `id`、`title`、`query`、`expected_strategy`、`domain`。           |
| `GET /health` 扩展       | P1  | 顶部状态徽章          | `status`、`mode: mock                                         |
| `GET /experiments/...` | P2  | 实验结果页           | meta、summary 或汇总图表数据；只读取已完成实验产物。                             |

**安全边界：**前端不得读取、展示或上传 API Key、`config.local.yaml`、Judge 内部对照文件或长期记忆原始文件。

## 3. 技术方案与目录结构

### 3.1 技术栈

```text
Vite + React + TypeScript
Ant Design 5：表单、布局、状态反馈、抽屉与卡片
ECharts：实验结果柱状图、雷达图、延迟/质量对比
Zustand：诊断会话与可视化状态
TanStack Query：健康检查、场景、实验结果等 HTTP 查询缓存
EventSource / fetch streaming：SSE 消费（按后端最终实现选择）
```

保持前端依赖精简：首个 MVP 不引入路由框架、复杂状态机、图数据库或服务端渲染。

### 3.2 建议目录

```text
src/frontend/
├── src/
│   ├── api/              # health、diagnose、scenarios、experiments 请求封装
│   ├── components/
│   │   ├── diagnosis/    # 输入区、策略徽章、链路图、Agent 卡片、报告面板
│   │   ├── common/       # 状态徽章、空态、错误提示
│   │   └── experiments/  # 后续实验图表组件
│   ├── pages/
│   │   ├── DiagnosisPage.tsx
│   │   └── ExperimentsPage.tsx
│   ├── stores/           # 当前诊断会话、trace 事件、播放状态
│   ├── types/            # 与 FastAPI 契约对应的 TypeScript 类型
│   ├── mocks/            # 后端未完成接口的稳定演示数据
│   ├── App.tsx
│   └── main.tsx
├── package.json
├── vite.config.ts
└── README.md
```

## 4. 分阶段路线

### F0 — 前端脚手架与同步诊断 MVP（最先启动）

**目标：**即使 SSE 尚未完成，也能通过现有 `POST /diagnose` 演示整个系统。

- 初始化 Vite React TypeScript 项目，配置开发代理到 FastAPI。
- 建立全局布局：顶部系统状态、左侧场景/输入区、中央链路区、右侧报告区。
- 接入 `GET /health` 与 `POST /diagnose`。
- 点击“开始诊断”后显示 loading；请求完成后用返回的 trace 渲染链路。
- 支持输入问题、复制报告、清空当前会话、错误重试。

**验收：**mock 模式下选择或输入一条问题，能够看到策略、trace、thinking 和最终报告。

### F1 — 诊断链路可视化（答辩核心）

**目标：**清晰区分三种路由策略，不依赖复杂图编辑器。

- 采用固定拓扑 + 状态点亮，而非可任意拖拽的流程图。
- `direct`：Route → 单个领域 Agent → Report → Reflection。
- `chain`：Route → Server → DB → Log → Report → Reflection。
- `parallel`：Route → DB / Server / Log 并行 → Conflict Check → Debate（按 trace 有无显示）→ Report → Reflection。
- 每个节点显示：状态（等待/运行/完成/跳过/失败）、detail、耗时占位或后续真实耗时。
- 右侧 Agent 面板展示对应 Agent 的 thinking 与工具调用摘要。

**验收：**对同一页面分别演示 direct、chain、parallel 三个场景时，评委无需阅读日志即可识别协作差异。

### F2 — SSE 实时诊断体验

**前置依赖：**后端 `GET /diagnose/stream` 或等价 SSE 契约完成。

- 诊断开始即建立 SSE 连接；事件到达时依次更新 trace 与节点状态。
- SSE 中断、后端错误、浏览器取消时显示明确状态，并提供回退到同步 `POST /diagnose` 的能力。
- 结束事件到达后渲染最终报告；不重复提交同一次 query。
- 开发环境提供可控 replay mock，保证没有真实模型时仍可演示“逐步点亮”。

**验收：**parallel 场景中 3 个 Agent 可并行点亮；有 Debate 的 trace 能显示分歧检测与 Debate 节点。

### F3 — 演示场景与报告体验

**前置依赖：**`GET /scenarios`；未完成前使用 `src/frontend/src/mocks/` 固定场景。

- 场景卡片至少包含：慢 SQL、服务器资源异常、日志异常、复合故障 / 大促体检。
- 报告使用 Markdown 渲染并高亮 SQL 代码块。
- 支持查看完整 trace、导出/复制报告文本、显示 mock / real 徽章。
- 对高危 SQL 只显示建议与审批提示，不提供前端直接执行入口。

**验收：**答辩时可在 30 秒内选场景、开始诊断、讲解协作链和报告结论。

### F4 — 实验结果页（M4 正式实验后）

**前置依赖：**18 组正式实验产物有效，且统计脚本产出统一汇总数据。

- 总览指标卡：root cause、key point recall、condition complete、latency。
- 对比图：single_agent vs full；no_debate / no_reflection 消融；force_chain / force_parallel 路由对比。
- 显著性结果表：Wilcoxon / Friedman 的统计量与 p 值。
- Case study：展示一条复合故障在 single_agent 与 full 下的报告差异。
- 明确标注样本数、模型、Judge、arm、replicate、是否 mock，避免图表脱离实验条件。

**验收：**论文中的核心实验图表可由该页截图或导出数据复现，且与 `meta.json` / `summary.json` 一致。

## 5. 交互与视觉原则

- 风格定位：深色或浅色均可，但以“专业运维控制台 + 可解释 AI”而非聊天机器人为主。
- 主屏只保留三个视觉焦点：**输入、协作链、最终报告**。
- 节点颜色统一：DB 蓝、Server 橙、Log 紫、Debate 红、Reflection 绿、Report 青；不得只靠颜色表达状态，需配图标/文字。
- `trace` 是前端唯一可信过程来源；前端不自行推断 Debate、Reflection 是否发生。
- 空态和 mock 状态应可演示：后端不可达、无 trace、SSE 断开、真实模型失败均有清晰提示。
- 移动端不作为答辩目标，优先优化 1366×768 及以上桌面分辨率。

## 8. 前端验收总标准

- mock 模式下可稳定演示 3 条路线：direct、chain、parallel。
- 页面能从真实后端响应渲染 trace，不硬编码“当前发生了 Debate / Reflection”。
- SSE 断线时，MVP 自动回退同步接口完成完整演示。
- 不展示任何密钥、本地配置、Judge 对照文件或敏感运行日志。
- 前端构建、类型检查与关键组件测试通过；后端 API 契约变更同步更新本路线图或接口类型。
