# OperMind 当前路线图

> 状态：当前唯一开发方向
>
> 更新：2026-07-31

## 当前阶段：正式产品架构重对齐

项目已经有会话、调查、审批、执行、验证和一个 PostgreSQL 技术切片的代码基础，但当前代码和旧文档的叙事不能继续定义产品边界。

下一步不是继续堆 RAG、知识库、演示脚本或第二个临时功能，而是先完成一份**正式产品架构 Design**，把已有能力纳入下面的产品结构：

```text
会话工作台（默认主入口）
服务中心（接入与管理服务、监控与调查入口）
多 Agent 运行与简要 Trace
受控 Connector / Tool
审批、白名单执行与验证
```

## 下一份 Design 必须回答的问题

1. 默认会话首页、服务中心、服务详情、会话服务上下文和 Trace 展开的信息架构；
2. 服务实体、服务类型、连接配置、凭据引用、连接测试和服务状态的数据模型；
3. PostgreSQL、MySQL、Redis 的 Connector 抽象，以及首批落地顺序；
4. 监控读取、当前快照、历史数据、轮询/推送、可用性与告警的范围；
5. Agent 角色、任务分派、统一 Trace 事件和前端展示边界；
6. 会话指令如何映射为只读 Tool、受控提案和高风险审批；
7. 现有 PostgreSQL 慢查询切片如何迁移为第一个正式 Connector 能力；
8. 凭据、权限、脱敏、审计和多服务隔离的安全方案；
9. API、数据库迁移和前端改造的分阶段实施顺序。

在这份 Design 完成、Review 通过并获得用户明确确认前，**不得自行决定**：

- 用户凭据如何保存；
- 直接接入 MySQL、Redis 或任何真实资源；
- 新增任意 SQL/Shell/网络执行能力；
- 选择 RAG、向量库、MCP、知识图谱或模型 Key 方案；
- 把当前单服务/单故障实现泛化为可写配置的服务平台。

## 工作原则

- 每个工作包都应服务于正式产品，不为“展示技术名词”单独造页面或脚本。
- 可以复用现有技术资产，但不能让旧实现和旧文档替代新的产品决策。
- 新功能先完成 Design → Review → 用户确认，再实现。
- 实现完成后集中执行测试、Review 和精确提交；研发 smoke 只用于验证，不是产品功能或产品入口。
