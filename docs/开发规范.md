# OperMind 开发规范

> 本文档是项目开发的完整规则集；`AGENTS.md` 与 `CLAUDE.md` 是内容一致的精简硬约束镜像，并链接至此。
> 适用于人类开发者与 AI 协作。新增代码前请先对照本规范。
> 最后更新：2026-07-25

---

## 1. 代码风格

- **注释、文档、日志用中文**；标识符用英文。
- **命名**：类名大驼峰（`ServerAgent`），函数/变量小写下划线（`build_system`、`agent_results`），常量全大写（`MAX_REVISION`、`HIGH_RISK_KEYWORDS`）。
- **类型标注**：所有公开函数/方法必须带参数与返回值类型标注。优先用 `list[str]`、`dict`、`X | None`（Python 3.10+ 语法）。
- **结构化数据用 Pydantic / TypedDict**，不裸传 dict。跨节点/跨层传递的状态用显式模型（如 `DiagnosisState`）。
- **单一职责**：一个函数只做一件事；一个文件一个核心类。
- **禁止裸 `except:`**；捕获具体异常并返回结构化错误信息，不吞掉堆栈。
- **禁止用 `print` 做生产日志**（当前 `agent.py` 的 `print` 追踪属技术债，新代码用 logging 或写入 `trace`）。

## 2. 架构约定

### 新增 Tool 的标准套路
1. 继承 `core.tool_registry.Tool`，实现 `execute(self, **kwargs) -> ToolResult`。
2. `__init__` 里声明 `name` / `description` / `parameters`（JSON Schema）。
3. 在对应 Agent 的 `__init__` 里 `registry.register(YourTool())`。
4. 高危操作在工具元数据里声明 `risk_level`，不在 `tool_registry` 里硬编码判断。

### 新增 Agent 的标准套路
1. 继承 `core.agent.BaseAgent`，复用其 ReAct 循环，**不重写 `run()`**（除非有充分理由）。
2. 构建自己的 `ToolRegistry` + 领域 `system_prompt`，传给 `super().__init__`。
3. 在 `bootstrap.build_system()` 里实例化并 `coordinator.register_agent(name, agent)`。
4. 领域 prompt 优先放 `backend/src/scenarios/`（参考 DBAgent），便于实验时替换。

### 结构化输出契约（M1 之后强制）
- 工具返回 `ToolResult { tool_name, status, metrics, evidence[], summary_text, raw }`。
- Agent 产出 `AgentDiagnosis { agent, conclusion, confidence, evidence[], raw_reasoning }`。
- `summary_text` 保留向后兼容；下游（debate/reflection/report）逐步切换到读 `evidence`。

### LangGraph 节点接线
- 状态统一走 `DiagnosisState`（`TypedDict, total=False`）。
- 新节点写成闭包，捕获注入的依赖；改图结构后**必须**让 `CoordinatorAgent` 重编译（`register_agent`/`set_quality` 已置 `_graph=None`）。
- 循环节点必须有上界（参照 `MAX_REVISION`）。

### HTTP API 与 SSE 契约
- 当前 HTTP 请求、响应、错误体和 SSE payload 统一放 `backend/src/api/`，使用 Pydantic 模型；`backend/src/app.py` 仅负责路由、依赖装配与协议适配。
- 公开 trace 事件类型以 `backend/src/api/schemas.py` 为准。Graph 内部 trace 可保留节点信息，但进入 API 前必须标准化为受控 type 并补齐时间戳。
- 阶段二产品 API 统一向 `/api/v1` 演进；会话、持久化、事务、权限和审计放在 Application Service / Repository 边界，不直接塞入 Agent 节点。正式产品结果必须使用稳定的 Pydantic 契约，Markdown 仅可作为展示补充。
- P0.3 的 `docs/开发/P0-V1产品化基线/api-v1-contract.md` 是 P1/P2 实现 API v1 前的契约基线：单租户 MVP 使用 UUID、UTC ISO 8601、cursor 分页与统一 `meta`/错误体；`RunEvent.sequence` 一一映射 SSE `id`，断线恢复只重放已持久化事件；`DiagnosisResult` 是 Run 成功后的最终结构化事实。实现若需调整字段或语义，必须先更新该契约、TypeScript 对应类型和 Review。
- SSE 使用 `event: progress|complete|error`：`progress` 推送节点进度，`complete` 带最终报告和完整 trace，`error` 只能返回安全错误码与通用信息，禁止泄露内部异常或配置。
- 新增/修改 SSE 行为必须覆盖正常完成、参数校验和异常终止；演示环境未接入鉴权时必须在开发日志写明，禁止直接公网部署。

## 3. Mock 模式纪律

- **`api_key="mock"` 是一等公民**，不是测试残留。所有开发、CI、答辩演示默认走 mock。
- **每个外部依赖都必须有 mock fallback**：
  - LLM 调用失败 → 退回模板/mock 响应。
  - 真实 MySQL 连不上 → 退回 `data/mock_db.py`。
  - psutil 不可用或 mock 模式 → 退回 `data/scenarios.py` 的激活场景（`server_tools` 在有激活场景时读场景指标，而非真机 psutil）。
- **mock 世界的单一真相源是 `data/scenarios.py`**（S1–S4 多故障场景 + 激活状态机）；日志 / 服务器工具在 mock 模式读「激活场景」，`bootstrap` 在 `api_key=="mock"` 时默认激活 S1。已删除散落重复的 `data/mock_logs.py`、`data/mock_server.py`。
- mock 输出必须**确定性**（固定数据，不随机），保证可复现与可排练。
- **评测运行必须隔离长期记忆**：用例不得读取前序样例记忆，也不得写入 `data/memory.json`；日常 CLI/API 可继续启用长期记忆。
- 新增真实数据源时，**先写 mock 版再写真实版**，二者返回同一结构。
- 接入真实数据库、外部数据源或前后端联调前，开发、产品和相关接口负责人必须共同确认：连接目标与环境、最小权限和脱敏边界、可用数据或种子数据、请求/响应/SSE 契约、确定性 mock fallback、失败回退和验收场景。确认结论写入对应 P 阶段 Step 日志；未确认时不得将真实依赖设为唯一运行路径。

### 项目路径与配置

- `backend/src/project_paths.py` 是仓库资源路径的唯一来源：`PROJECT_ROOT`、`BACKEND_ROOT`、`CONFIG_DIR`、`DATA_DIR`、`EXPERIMENTS_DIR` 均不得由 `Path.cwd()`、`backend/data` 或复制的 `parents[n]` 推导。
- 配置按根 `config/config.local.yaml`、根 `config/config.example.yaml` 的顺序加载，再由 `OPERMIND_*` 环境变量覆盖；`config.local.yaml`、凭据、运行时数据和实验产物不得提交。`api_key="mock"` 是可验证的 fallback，不得因为路径收口而失效。
- 从仓库根启动 API 使用 `python -m uvicorn --app-dir backend src.app:app --reload`；后端脚本通过 `python backend/scripts/<name>.py` 直接执行。脚本和测试可以从非根目录运行，但必须通过集中式路径模块或其唯一启动引导定位资源，不得以全局 `PYTHONPATH` 作为长期路径方案。

## 4. 安全规则（血的教训，最高优先级）

- **密钥绝不进代码库**。只从环境变量读取（`os.environ`），`config.local.yaml` 只做本地占位且必须在 `.gitignore` 且 `git rm --cached`。
- 提交前自查：`git status` 里不得出现 `.env`、`*.local.yaml`、`credentials.*`、任何含 `sk-` 的文件。
- 一旦密钥泄露：**先去控制台吊销**（删文件/停跟踪都撤销不了已泄露凭证），再洗历史。
- **真实数据库连接**：只读账号 + 参数化查询 + 连接超时；诊断工具**禁止**执行 DDL/DML。真实连接信息只从环境变量读取，不在日志、响应、截图或前端状态中回显。
- 高危 SQL（drop/truncate/kill/alter 等）必须过审批门；审批用非阻塞机制（见路线图 M6），不用阻塞 `input()`。
- 网络暴露的端点若无鉴权，须在文档/PR 里显式标注该风险。

## 5. Git / 提交约定

- **Commit message 格式**：`<类型>: <中文描述>`，类型取 `feat / fix / refactor / docs / test / chore`。示例：`feat: 实现 SSE 流式诊断端点`。
- **禁止直接提交到 `main`**；功能在分支开发，PR 合并。
- **不提交敏感文件**（见第 4 节自查清单）。
- 只在明确需要时提交；一次 commit 聚焦一件事，`git add` 指定文件而非 `git add .`。
- 破坏性操作（force push、reset --hard、filter-repo 洗历史）需明确确认，且提前通知已 clone 仓库的人。

---

## 6. 测试约定

- **三条路径回归**：direct / chain / parallel 各至少一个 mock 冒烟测试（参照 `scripts/smoke_pipeline.py`，它是 trace 节点名的权威来源）。
- **改机制必跑回归**：动了 graph / debate / reflection / approval，提交前跑通冒烟测试。
- 新增 Agent/Tool 时补对应单测，断言结构化输出的关键字段（如 `evidence`）。
- 高危操作用例（审批分支）必须有专门测试（参照 `data/test_cases.json` 的高危 DELETE 用例）。
- 测试默认 mock 模式，不依赖真实网络/DB/LLM。

---

## 7. 实验 / 复现规则（服务论文）

- **主实验跑 mock 模式**——确定性是相对「调 API 随机波动」的核心优势，论文中须强调。
- **固定全局随机种子**；真实 LLM 温度设 0；Real-LLM 子集每配置跑 3–5 次报均值±标准差。
- **一次实验 = 一个配置 × 全数据集**，结果落盘到带时间戳 + config hash 的目录（逐条 `results.jsonl` + 聚合 `metrics.json`），并在 meta 中记录实验组标签（`arm`）。
- 消融只改一个开关，其余变量固定（同模型、同数据、同 prompt、同工具）。
- 准确率用 LLM-as-judge（独立模型 + 固定 prompt）+ 人工抽检校准，口径在论文交代。
- `requirements.txt` 锁版本；记录模型 ID / 温度 / 种子，保证可复现。

## 8. 文档与工作流约定

### 规则真相源与同步

- `docs/开发规范.md` 是完整开发规则的唯一真相源；`AGENTS.md` 与 `CLAUDE.md` 是同一份精简硬约束的镜像，内容必须逐字一致。
- `docs/开发/_A-Plan-总览.md` 是项目总进度、执行顺序和唯一下一步的真相源：阶段一 M0–M7 已完成/冻结，阶段二 P0–P7 是当前主线。`docs/开发/_B-V1产品化开发计划.md` 是阶段二范围、产品决策和里程碑明细的详细计划，不替代总览中的状态。
- `docs/开发路线图与规划.md`、`docs/初始开发/`、M 阶段日志和 `docs/前端开发路线图.md` 中的 M7 路线均为历史材料；`report/` 承载研发/实验/Trace 可观察性，`frontend/` 承载 V1 主产品。
- 动了目录结构、节点流、Agent-Tool 关系、HTTP API/SSE 契约、真实数据源接入或工作流，必须同步更新 `AGENTS.md`、`CLAUDE.md` 与本规范；影响阶段状态时同步更新 A-Plan 总览，影响阶段二范围时同步 `_B-V1产品化开发计划.md`。
- 面向答辩的材料（架构图、对比图、演示脚本）放 `docs/`，生成脚本放 `scripts/`。

### 重要改动工作流

重要改动统一按以下顺序推进，任何阶段都不得以后续阶段替代：

```text
Design → Step → Code → Test → Review → Commit
```

- 每个 step 收尾即做 Review，不把审查拖到里程碑末尾。
- 架构调整、删文件和非平凡 bug 必须由独立 code-review agent 审查；发现问题后修复并复验，再提交。
- 测试、审查、Git 是完成的必要条件；Review 结论为「通过」前，该 step 不算完成。
### 上下文交接与恢复

长任务不得把进度只留在对话上下文中。每个 step 应小到能在一次工作上下文中完成 **Design → Code → Test → Review → Commit**；如果预计超出这一范围，应继续拆分并独立提交，而不是混合多个后续步骤。

出现任一情况时，**先更新交接点，再继续或切换上下文**：预计跨上下文、实现已涉及 3–5 个文件、发现 P1/P2 审查问题、准备执行长时间联调/验收、或上下文接近上限。交接点为当前里程碑目录下的 `HANDOFF.md`，至少包含：

- 阶段/分支/稳定基线提交和明确状态（进行中、待修复、待 Review、已完成）；
- 已完成项、未完成或阻塞项，以及“禁止提交”等约束；
- 唯一优先级的下一步、必跑验证命令和本次提交边界；
- 当前未提交 diff 的性质，避免把后续 step 或无关文件混入提交。

恢复任务的固定入口顺序：`git status --short` → 最近提交 → `docs/开发/_A-Plan-总览.md` → 当前 `HANDOFF.md` 与 `design.md` → 未提交 diff。交接记录与工作区不一致时，先核对原因，禁止猜测、跳过验证或直接提交。`HANDOFF.md` 是当前 step 的临时恢复入口；step 提交后须回填最终状态或删除，长期历史仍以 step 日志和提交为准。

## 9. 文档驱动开发流程（DDD 日志）

> 重要开发以「分层开发日志」记录，服务三个目的：答辩时可辩护的过程证据、论文实验的可追溯性、给他人的细致学习材料。

### 定位：日志，不是活文档

这些 md 是**带日期与 commit 的开发快照**，记录「某时间点做了什么、为什么」。要看最新状态去源码和 A-Plan 总览；日志只记录当时的设计、实现、验证和审查结论。

配套两条硬纪律：

- **贴关键片段，不贴整文件**。整文件快照最易腐烂、且淹没重点。
- **用 `文件路径:行号` 锚点指向真实源码**；完成后回填关联 commit。

### 什么时候写日志（重要修改阈值）

满足**任一**即写：

- 改动了**架构或接口契约**（新增 Agent/Tool、改结构化输出格式、动 graph 节点接线、HTTP API/SSE 事件变化）
- 涉及**安全**（密钥、审批、真实 DB）
- 对应**一个里程碑或论文实验**的产出
- 修了一个**非平凡 bug**（根因值得讲清）

错别字、格式调整、小重构不写日志，进 commit message 即可。

### 存放与命名

- **阶段一历史开发日志**：保留在 `docs/开发/M<N>-<名称>/`，不重写其历史结论。
- **阶段二 P 阶段开发**：放 `docs/开发/P<N>-<名称>/`，默认扁平两级：
  - `design.md`：目标、范围、关键决策、step 分解、验收，带 `状态:` 字段；
  - `stepN-<名称>.md`：该 step 的 Design / Step / Code / Test / Review 快照，可覆盖多个相关文件；
  - `review.md`：里程碑验收、已知限制、关联提交。
- **跨里程碑规则/流程治理**：放 `docs/开发/治理-<名称>/`，用一个带日期的快照记录 Design / Step / Code / Test / Review；仅用于不归属具体 M<N> 的规则治理，避免篡改已完成里程碑的历史日志。
- **历史归档**：`docs/初始开发/` 保留已有编号文档，不再新增。
- **对外材料**：pitch、面试应答放 `docs/A-Plan/`，与开发日志分离。

### Step 日志模板

```markdown
# M<N> Step<N> — 特性名称
> 日期：YYYY-MM-DD　|　状态：进行中 / ✅ 通过　|　关联 commit：待提交 / <hash>

## Design
- 问题、目标、取舍、受影响契约

## Step
1. …

## Code
- `backend/src/xx.py:行号`：关键逻辑和原因

## Test
- mock 场景 / 回归命令 / 关键结果

## Review
- 审查人 / 日期
- 发现的问题与处置
- 结论：通过 / 待改
```

### 与多 Agent 协作的配合

派 agent 调查、实现或审查时，其产出分别进入 Design / Code / Test / Review 层；主持整合者负责复验、更新日志和提交。对于必须独立审查的改动，实现 agent 不得自行替代 code review。
