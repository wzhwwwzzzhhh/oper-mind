# OperMind 开发规范

> 本文档是项目开发的完整规则集；`AGENTS.md` 与 `CLAUDE.md` 是内容一致的精简硬约束镜像，并链接至此。
> 适用于人类开发者与 AI 协作。新增代码前请先对照本规范。
> 最后更新：2026-07-30（单问题端到端 DevOps Copilot、受控靶场、文档治理与工作包流程）

---

## 1. 代码风格

- **注释、文档、日志用中文**；标识符用英文。
- **命名**：类名大驼峰（`ServerAgent`），函数/变量小写下划线（`build_system`、`agent_results`），常量全大写（`MAX_REVISION`、`HIGH_RISK_KEYWORDS`）。
- **类型标注**：所有公开函数/方法必须带参数与返回值类型标注。优先用 `list[str]`、`dict`、`X | None`（Python 3.10+ 语法）。
- **结构化数据用 Pydantic / TypedDict**，不裸传 dict。跨节点/跨层传递的状态用显式模型（如 `DiagnosisState`）。
- **单一职责**：一个函数只做一件事；一个文件一个核心类。
- **禁止裸 `except:`**；捕获具体异常并返回结构化错误信息，不吞掉堆栈。
- **禁止用 `print` 做生产日志**（当前 `agent.py` 的 `print` 追踪属技术债，新代码用 logging 或写入 `trace`）。

## 2. 架构约定

### 新增 Tool 的标准套路
1. 继承 `core.tool_registry.Tool`，实现 `execute(self, **kwargs) -> ToolResult`。
2. `__init__` 里声明 `name` / `description` / `parameters`（JSON Schema）。
3. 在对应 Agent 的 `__init__` 里 `registry.register(YourTool())`。
4. 高危操作在工具元数据里声明 `risk_level`，不在 `tool_registry` 里硬编码判断。

### 新增 Agent 的标准套路
1. 继承 `core.agent.BaseAgent`，复用其 ReAct 循环，**不重写 `run()`**（除非有充分理由）。
2. 构建自己的 `ToolRegistry` + 领域 `system_prompt`，传给 `super().__init__`。
3. LLM Agent 在 `bootstrap.build_system()` 里实例化并 `coordinator.register_agent(name, agent)`。确定性、只读的外部来源采集器属于 Infrastructure Collector，不得伪装成 Agent；它们必须通过显式 Application port/Executor 注入，并返回 Pydantic 结构化事实。
4. 领域 prompt 优先放 `backend/src/scenarios/`（参考 DBAgent），便于实验时替换。

### 结构化输出契约
- 工具返回 `ToolResult { tool_name, status, metrics, evidence[], summary_text, raw }`。
- Agent 产出 `AgentDiagnosis { agent, conclusion, confidence, evidence[], raw_reasoning }`。
- `summary_text` 保留向后兼容；下游（debate/reflection/report）逐步切换到读 `evidence`。

### LangGraph 节点接线
- 状态统一走 `DiagnosisState`（`TypedDict, total=False`）。
- 新节点写成闭包，捕获注入的依赖；改图结构后**必须**让 `CoordinatorAgent` 重编译（`register_agent`/`set_quality` 已置 `_graph=None`）。
- 循环节点必须有上界（参照 `MAX_REVISION`）。

### HTTP API 与 SSE 契约
- 当前 HTTP 请求、响应、错误体和 SSE payload 统一放 `backend/src/api/`，使用 Pydantic 模型；`backend/src/app.py` 仅负责路由、依赖装配与协议适配。
- 公开 trace 事件类型以 `backend/src/api/schemas.py` 为准。Graph 内部 trace 可保留节点信息，但进入 API 前必须标准化为受控 type 并补齐时间戳。
- 产品 API 统一使用 `/api/v1`；会话、持久化、事务、权限和审计放在 Application Service / Repository 边界，不直接塞入 Agent 节点。正式产品结果必须使用稳定的 Pydantic 契约，Markdown 仅可作为展示补充。
- 产品分层：`application/` 负责短事务、幂等、状态迁移和执行编排；`domain/` 仅放状态、值对象、端口与应用异常；`infrastructure/persistence/` 的 Repository 只执行 staged add/read/条件更新，不得 commit/rollback；`infrastructure/diagnosis/` 仅适配既有 Coordinator，禁止 Agent/适配器写数据库。
- 当前 API v1 的契约事实以 `backend/src/api/v1/` 的 FastAPI 路由、Pydantic schema、生成的 TypeScript 类型与回归测试为准：单租户 MVP 使用 UUID、UTC ISO 8601、cursor 分页与统一 `meta`/错误体；`RunEvent.sequence` 一一映射 SSE `id`，断线恢复只重放已持久化事件；`DiagnosisResult` 是 Run 成功后的最终结构化事实。实现若需调整字段或语义，必须先完成公开契约 Design → Review，并同步后端、前端类型与测试。
- 旧 `/diagnose/stream` 仅作为研发兼容接口保留；主产品使用 `/api/v1/runs/{run_id}/stream` 的 `event: run_event`，其 SSE `id` 必须一一映射已提交 `RunEvent.sequence`，只重放持久化事件并在终态事件后关闭。两套 SSE 不得互相改写。
- 新增/修改 SSE 行为必须覆盖正常完成、参数校验和异常终止；演示环境未接入鉴权时必须在开发日志写明，禁止直接公网部署。

## 3. Mock 模式纪律

- **`api_key="mock"` 是一等公民**，不是测试残留。所有开发、CI、答辩演示默认走 mock。
- **每个外部依赖都必须有 mock fallback**：
  - LLM 调用失败 → 退回模板/mock 响应。
  - 真实诊断数据库不可用 → 退回同契约的确定性 mock；不得自动改连其他真实库。
  - psutil 不可用或 mock 模式 → 退回 `data/scenarios.py` 的激活场景（`server_tools` 在有激活场景时读场景指标，而非真机 psutil）。
- 历史 mock 场景可继续服务研发与测试；每个新的产品 Connector/Collector 必须拥有同契约、确定性的 fixture，不得将旧场景设为新产品事实的唯一来源。
- mock 输出必须**确定性**（固定数据，不随机），保证可复现与可排练。
- **评测运行必须隔离长期记忆**：用例不得读取前序样例记忆，也不得写入 `data/memory.json`；日常 CLI/API 可继续启用长期记忆。
- 新增真实数据源时，**先写 mock 版再写真实版**，二者返回同一结构。
- 接入真实数据库、外部数据源或前后端联调前，必须确认连接目标与环境、最小权限和脱敏边界、可用数据/种子数据、请求/响应/SSE 契约、确定性 mock fallback、失败回退和验收场景；确认结论写入当前 P 工作包 Design/Review。未确认时不得将真实依赖设为唯一运行路径。

### 项目路径与配置

- `backend/src/project_paths.py` 是仓库资源路径的唯一来源：`PROJECT_ROOT`、`BACKEND_ROOT`、`CONFIG_DIR`、`DATA_DIR`、`EXPERIMENTS_DIR` 均不得由 `Path.cwd()`、`backend/data` 或复制的 `parents[n]` 推导。
- 配置按根 `config/config.local.yaml`、根 `config/config.example.yaml` 的顺序加载，再由 `OPERMIND_*` 环境变量覆盖；`config.local.yaml`、凭据、运行时数据和实验产物不得提交。`api_key="mock"` 是可验证的 fallback，不得因为路径收口而失效。
- 从仓库根启动 API 使用 `python -m uvicorn --app-dir backend src.app:app --reload`；后端脚本通过 `python backend/scripts/<name>.py` 直接执行。脚本和测试可以从非根目录运行，但必须通过集中式路径模块或其唯一启动引导定位资源，不得以全局 `PYTHONPATH` 作为长期路径方案。
- 应用元数据数据库（Session、Run、Event、Result、幂等与审计）与 P4 诊断数据源严格隔离，使用独立 URL、账号和连接池；`api_key="mock"` 仅降级外部诊断依赖，`/api/v1` 不得在持久化不可用时静默改用内存。
- 应用数据库 URL 优先级固定为 `OPERMIND_APP_DATABASE_URL`、被忽略的 `persistence.database_url`、根 `data/opermind.sqlite3`；运行时 `data/*.sqlite3` 必须忽略，真实连接串不得写入模板、日志或提交。
- 应用 schema 只通过 Alembic 显式迁移；服务启动不得调用 `create_all()` 或自动 `upgrade head`。Application Service 管理短事务与 commit/rollback，Repository 不自行提交；RunEvent 只有提交后才能进入 SSE，`sequence` 与 SSE `id` 必须一一对应。

## 4. 安全规则（血的教训，最高优先级）

- **密钥绝不进代码库**。只从环境变量读取（`os.environ`），`config.local.yaml` 只做本地占位且必须在 `.gitignore` 且 `git rm --cached`。
- 提交前自查：`git status` 里不得出现 `.env`、`*.local.yaml`、`credentials.*`、任何含 `sk-` 的文件。
- 一旦密钥泄露：**先去控制台吊销**（删文件/停跟踪都撤销不了已泄露凭证），再洗历史。
- **真实数据库连接**：只读账号 + 参数化查询 + 连接超时；诊断工具**禁止**执行 DDL/DML。真实连接信息只从环境变量读取，不在日志、响应、截图或前端状态中回显。
- **受控靶场执行例外**：只有独立执行器在用户明确授权的隔离靶场、人工审批和严格白名单同时满足时，才可执行预定义修复动作。动作必须限制目标、参数和超时，记录审批/执行/验证事实；LLM 不得直接执行任意 SQL 或 Shell。
- **P4 PostgreSQL 靶场硬边界**：Work 1 只允许连接 `127.0.0.1:5433` 上的 `opermind_demo`，且只允许变更 `opermind_demo.orders` 的预定义索引 `idx_orders_user_created`。连接前后均须验证目标；`clean` 只能删除该 schema 和项目运行时文件，不得删除数据库。任何其他数据库（包括 `gongkar`）、schema、表、端口或凭证缺失均必须 fail-closed。凭证只从当前进程环境读取，禁止写入代码、配置样例、日志、文档、截图或 Git。
- 高危 SQL（drop/truncate/kill/alter 等）必须过审批门；审批用非阻塞机制，不用阻塞 `input()`。
- 网络暴露的端点若无鉴权，须在文档/PR 里显式标注该风险。

## 5. Git / 提交约定

- **Commit message 格式**：`<类型>: <中文描述>`，类型取 `feat / fix / refactor / docs / test / chore`。示例：`feat: 实现 SSE 流式诊断端点`。
- **禁止直接提交到 `main`**；功能在分支开发，PR 合并。
- **不提交敏感文件**（见第 4 节自查清单）。
- 只在明确需要时提交；一次 commit 聚焦一件事，`git add` 指定文件而非 `git add .`。
- 破坏性操作（force push、reset --hard、filter-repo 洗历史）需明确确认，且提前通知已 clone 仓库的人。

## 6. 测试约定

- **图编排回归**：改动 legacy Coordinator 的 direct / chain / parallel 路径时，各至少保留一个 mock 冒烟测试；`scripts/smoke_pipeline.py` 是该研发图节点名的权威来源。
- **改机制必跑回归**：动了 graph / debate / reflection / approval，提交前跑通冒烟测试。
- 新增 Agent/Tool 时补对应单测，断言结构化输出的关键字段（如 `evidence`）。
- 高危操作与审批分支必须有专门测试，覆盖未审批拒绝、白名单校验、执行失败与 Verify 失败。
- 测试默认 mock 模式，不依赖真实网络/DB/LLM。

## 7. 实验 / 复现规则（服务论文）

- **主实验跑 mock 模式**——确定性是相对「调 API 随机波动」的核心优势，论文中须强调。
- **固定全局随机种子**；真实 LLM 温度设 0；Real-LLM 子集每配置跑 3–5 次报均值±标准差。
- **一次实验 = 一个配置 × 全数据集**，结果落盘到带时间戳 + config hash 的目录（逐条 `results.jsonl` + 聚合 `metrics.json`），并在 meta 中记录实验组标签（`arm`）。
- 消融只改一个开关，其余变量固定（同模型、同数据、同 prompt、同工具）。
- 准确率用 LLM-as-judge（独立模型 + 固定 prompt）+ 人工抽检校准，口径在论文交代。
- `requirements.txt` 锁版本；记录模型 ID / 温度 / 种子，保证可复现。

## 8. 文档与工作流约定

### 规则真相源与同步

- `docs/开发规范.md` 是完整开发规则的唯一真相源；`AGENTS.md` 与 `CLAUDE.md` 是同一份精简硬约束的镜像，内容必须逐字一致。
- `docs/开发/_A-Plan-总览.md` 是项目总进度、执行顺序和唯一下一步的真相源。当前主线是 DevOps Copilot MVP；`docs/开发/_B-V1产品化开发计划.md` 只展开工作包范围与验收，不替代总览状态，也不得维护第二个“当前唯一下一步”。
- `docs/README.md` 与 `docs/开发/README.md` 是文档导航和层级入口；当前产品定位与 P4.0 设计以 `docs/开发/治理-DevOps-Copilot-MVP重定位/` 为入口。目录必须明确文件是当前决策、已发布契约、技术事实还是历史快照。
- 已被替代的教程、阶段计划、旧产品路线、旧对外材料与治理快照已从工作树删除，避免误导后续开发；需要追溯时查 Git 历史。可继承的技术事实收敛到 `docs/开发/历史技术基线.md`、当前代码与测试；`report/` 承载研发/实验/Trace，`frontend/` 承载 DevOps Copilot 主产品。
- 动了目录结构、节点流、Agent-Tool 关系、HTTP API/SSE 契约、真实数据源接入或工作流，必须同步更新 `AGENTS.md`、`CLAUDE.md` 与本规范；影响项目状态时同步更新 A-Plan 总览，影响工作包范围时同步 `_B-V1产品化开发计划.md`。
- 面向答辩的材料（架构图、对比图、演示脚本）放 `docs/`，生成脚本放 `scripts/`。

### 工作包流程与审查门

重要开发以**可验收的纵向工作包**推进，而不是要求每个微步骤都独立 Design、Review 和 Commit。一个工作包通常包含 1–3 个紧密相关切片，能独立展示用户价值并在一次或少数几个工作上下文中收口。

```text
必要时 Design → 连续实现 / 增量测试 → 工作包 Test → Review → Commit
```

- 工作包开始前明确目标、范围、验收、风险和提交边界；小的样式、文案、测试补充或局部重构不单独写 Design/日志。
- 工作包内部可以连续完成多个相关步骤和多次本地测试；不得为了机械流程拆出无价值的 commit 或 Review。
- 工作包完成时必须集中运行相关测试，完成代码 Review，必要时做人工验收，再提交一个可回滚、可说明的 commit；Review 不可后置到多个工作包之后。
- 以下改动是**强制设计 + 独立审查门**：架构/Graph 主链路、公开 HTTP/API/SSE 契约、数据库迁移、真实数据源/网络连接、审批或执行安全、凭据/权限、删除文件、破坏性操作和高影响非平凡 bug。实现前必须说明边界，提交前由独立审查者复核。
- 常规功能工作包可由实现者自查并在收口时做一次 Review；触发强制门的改动不得以“工作包较小”为由跳过独立审查。

### 上下文交接与恢复

长任务不得把进度只留在对话上下文中，但也不以文件数或每个 step 机械触发交接。出现任一情况时，**先更新交接点，再继续或切换上下文**：工作包预计跨上下文、目标/安全/契约边界尚未收口、存在未解决的审查问题、准备进行长时间联调或破坏性操作、或上下文接近上限。

交接点为当前工作包目录下的 `HANDOFF.md`，至少包含：

- 分支、稳定基线、当前状态和工作包目标；
- 已完成项、未完成/阻塞项和不可跨越的安全边界；
- 唯一下一步、必跑验证和预计提交边界；
- 当前未提交 diff 的性质，避免混入无关工作。

恢复顺序：`git status --short` → 最近提交 → `docs/开发/_A-Plan-总览.md` → `docs/开发/README.md` → 当前定位/工作包 `design.md` 与 `HANDOFF.md`（如有）→ 未提交 diff。交接记录与工作区不一致时，先核对原因，禁止猜测、跳过验证或直接提交。工作包提交后须关闭或更新 `HANDOFF.md`；已完成里程碑保留的交接文件必须明确标为历史，且不得保留过期“当前下一步”。

## 9. 文档驱动开发流程（DDD 日志）

> 重要开发以「分层开发日志」记录，服务三个目的：答辩时可辩护的过程证据、论文实验的可追溯性、给他人的细致学习材料。

### 定位：日志，不是活文档

这些 md 是**带日期与 commit 的开发快照**，记录「某时间点做了什么、为什么」。要看最新状态去源码和 A-Plan 总览；日志只记录当时的设计、实现、验证和审查结论。

配套两条硬纪律：

- **贴关键片段，不贴整文件**。整文件快照最易腐烂、且淹没重点。
- **用 `文件路径:行号` 锚点指向真实源码**；完成后回填关联 commit。

### 什么时候写日志（重要修改阈值）

满足**任一**即写：

- 改动了**架构或接口契约**（新增 Agent/Tool、改结构化输出格式、动 graph 节点接线、HTTP API/SSE 事件变化）
- 涉及**安全**（密钥、审批、真实 DB）
- 对应**一个里程碑或论文实验**的产出
- 修了一个**非平凡 bug**（根因值得讲清）

错别字、格式调整、小重构不写日志，进 commit message 即可。

### 存放与命名

- **当前产品开发**：放 `docs/开发/P<N>-<名称>/`；一个目录可包含多个工作包：

  - `design.md`：里程碑或工作包的目标、范围、关键决策、验收与状态；
  - `workN-<名称>.md`（或历史 `stepN-*.md`）：一个完整工作包的关键取舍、实现、测试和审查快照，可覆盖多个相关文件；
  - `review.md`：工作包或里程碑的收口审查、已知限制与关联提交。
  新文档优先用 `work*.md`，避免暗示每个微步骤必须独立提交。
- **跨工作包治理**：放 `docs/开发/治理-<名称>/`，仅记录当前仍有效的产品定位、规则或架构决策；被替代后按历史治理规则删除。
- **历史治理**：已被替代、只会干扰当前决策的教程/计划/快照从工作树删除；不得删除仍在用的代码、测试、公开契约、安全事实或真实验收结论。历史追溯使用 Git；长期有效的压缩事实写入 `历史技术基线.md`。
- **对外材料**：秋招 pitch、演示脚本和面试应答必须基于当前产品蓝图和已验收事实；需要产出时在对应 P6+ 工作包创建，禁止复活旧路线文档。

### 工作包日志模板

```markdown
# P<N> Work<N> — 特性名称
> 日期：YYYY-MM-DD　|　状态：进行中 / ✅ 通过　|　关联 commit：待提交 / <hash>

## 目标与边界
- 用户价值、范围、非目标、受影响契约与风险

## 实现
- 关键取舍；`backend/src/xx.py:行号` 等源码锚点

## 验证
- 自动化测试、靶场/Mock 场景、人工验收与关键结果

## Review
- 审查范围、审查人/日期、发现与处置、结论
```

一个工作包可记录多个内部小步骤；不要求为每个文件或每次修改单独建立日志。
### 与多 Agent 协作的配合

派 agent 调查、实现或审查时，其产出分别进入 Design / Code / Test / Review 层；主持整合者负责复验、更新日志和提交。对于必须独立审查的改动，实现 agent 不得自行替代 code review。
