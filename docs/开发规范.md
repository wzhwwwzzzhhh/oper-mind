# OperMind 开发规范

> 状态：当前工程规则
>
> 更新：2026-08-09（新增 §7 完善类改动的流程）

## 1. 通用工程规则

- 中文注释、文档和用户可见日志；公开函数必须有类型标注。
- 跨层数据使用 Pydantic 或 TypedDict；禁止裸 `except`、新增生产 `print` 和隐式跨层字典协议。
- 前端和后端都是正式产品代码：API 契约明确、错误可安全展示、状态可恢复、测试覆盖关键用户路径。
- 一个工作包可包含 1–3 个紧密切片；完成后集中 Test → Review → Commit。
- 架构、公开 API、数据库迁移、Connector、外部连接、凭据、监控、权限、审批/执行安全和破坏性改动必须先 Design → Review → 用户确认。
- 不直推 `main`；commit 使用 `<类型>: <中文描述>`；只暂存指定文件，禁止 `git add .`。

## 2. 会话、Agent 与 Trace

- 会话是产品主入口，服务上下文、消息、调查、提案和执行结果必须可被安全地关联和恢复。
- LLM Agent 继承 `BaseAgent` 并复用约定运行接口；Tool 继承 `Tool` 并实现受控 `execute`；状态图使用显式状态模型。
- 确定性 Connector / Collector 不是任意可调用 Agent，必须通过显式 Application port 或 Executor 注入，并返回结构化事实。
- 前端 Trace 只展示角色、阶段、状态、耗时、工具类别和脱敏证据摘要；禁止展示 CoT、系统 Prompt、原始工具输出、原始异常或凭据。

## 3. 服务与 Connector

- 前端不得直接连接 PostgreSQL、MySQL、Redis、日志系统或任何用户服务；所有访问必须经后端 Connector / Tool。
- 每种服务类型必须有明确的身份、允许资源、只读能力、超时、参数化方式、脱敏规则、mock 策略、监控语义和错误映射。
- 未经过 Design/Review/用户确认的 Connector、端口、协议、服务类型和真实资源不得接入。
- 当前已有技术切片可以保留和复用，但不得因为其硬编码限制而阻止正式多服务模型的设计。

## 4. 凭据、隐私与隔离

- 凭据只能从当前进程环境或经设计批准的安全密钥引用取得；不得写入仓库、文档、日志、数据库普通字段、事件、Trace、结果、截图或 Git。
- API 和 UI 不返回密码、连接串、原始 host/port 等敏感连接细节，除非未来 Design 明确必要展示与脱敏规则。
- 所有服务访问必须有服务级隔离、权限校验和目标边界；不得因为诊断或监控需求枚举、探测或访问未授权资源。
- 应用元数据、用户服务数据和测试/演示资源必须隔离；清理动作只允许清理专用项目资源，不能删除用户数据库或服务。

## 5. 调查、行动与监控

- 默认调查为只读、参数化、限时、可审计、可 mock；模型不能自由生成并执行 SQL、Shell、DDL、DML 或网络命令。
- 高风险动作必须由服务器生成受控提案，经过人工审批、严格白名单执行和独立验证；禁止自动批准、通用执行器和由聊天文本直接执行。
- 监控必须区分当前快照、历史记录、模拟数据、不可用与未知；不得将一次读取伪装为长期实时监控，也不得将历史验证伪装为当前健康。
- 未实现能力必须如实标注“未启用”，不能制造虚假的产品承诺。

## 6. 测试与提交

- 每个新增关键路径应有后端单元/API 测试和前端交互测试；迁移必须验证 upgrade/downgrade 与约束。
- 对真实外部依赖必须提供确定性 mock，但 mock 不得冒充真实执行或真实监控。
- 真实资源测试只在用户明确授权、边界经过校验的情况下运行；凭据不进入测试输出或 Git。
- 提交前必须运行相关测试、`git diff --check`，检查暂存范围和敏感字面量；不得提交 `.env`、`*.local.yaml`、凭据或 `sk-` 内容。

## 7. 完善类改动的流程

当前阶段（体验驱动完善）的改动分两类，走不同流程。工作地图见 `docs/完善清单.md`。

### 7.1 走轻流程（无需 Design 门）

满足**全部**条件才算完善类：不新增公开 API、不新增数据库迁移、不新增 Connector 或服务类型、
不扩大执行/审批能力、不新增真实外部连接、不改变产品对用户的能力承诺。

典型范围：修 bug、接线已存在的路由与按钮、补渲染已返回但被丢弃的字段、
删除死代码、更新过时注释、把假数据改为诚实降级、UI 打磨。

轻流程：`完善清单.md` 认领条目 → worktree 开发 → 相关测试 + 前端 `typecheck`/`test`/`build`
→ 回写清单状态与验证方式 → PR。

### 7.2 仍须 Design → Review → 用户确认

只要触及以下任一项，即使被登记在完善清单里，也必须先出 Design：

- 审批与执行边界（如 P0-5 高危 SQL 是否接入 ToolGateway 执行链）；
- 结构化结果的事实来源变更（如 assembler 是否从报告正文提炼结构化字段）；
- 记忆、检索、向量或 MCP 相关方案（如 P1-8 长期记忆存储与检索）；
- 多 Agent 编排语义变更（如 P1-10 knowledge 是否进 chain 顺序）；
- 页面从"展示"变为"控制后端行为"（如 P1-7 模型设置页开关真接后端装配）。

### 7.3 状态标注纪律

- 清单状态只有三种：`—` 未修、`⏳` 在修或部分修、`✅` 已修复。
- 标 `✅` 必须同时写明日期与验证方式；**代码改完但端到端未复验的，只能标 `⏳`**。
- 修复涉及 `docs/跑通验证.md` 的卡点时，同步更新该卡点状态，不留两处矛盾记录。
