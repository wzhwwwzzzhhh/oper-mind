# P4.3 会话服务上下文贯通与服务选择 Design

> 状态：已确认
> 更新：2026-08-06
> 关联：`docs/prd/session/P4.3-service-context.md`（已确认）、`docs/design/session/P4.2DBAgent真库Design.md`（真实模式 DBAgent 接真库）、`docs/design/service-center/P4.4服务中心接入与凭据Design.md`（多实例注册、凭据命名空间）、`docs/产品定义.md` §2.1/§4、`docs/开发规范.md` §3/§4、`docs/路线图.md`。

## 1. 目标与范围

把服务上下文从「会话表字段」贯通到诊断执行链路：会话关联的 `service_id` 一路带到 Run → 执行器 → 内核 → DBAgent 工具，工具按绑定服务从注册表取只读 Connector 连接；会话工作台与服务中心都能选择已接入服务发起只读调查。只贯通 DB Agent；Server/Log 不假装按服务连接。

### 做什么
- 修复 service_id 白名单：合法值集从静态服务注册表派生，放开 `postgres-production`/`postgres-staging`。
- 服务上下文贯通 Run 执行链路：会话 service_id 带入 Run → 执行器 → 内核 → DBAgent 工具。
- 会话工作台首页发起调查时提供服务选择入口；服务中心「发起调查」入口保留。
- mock 模式（`api_key == mock`）行为完全不变，S1–S4 评测确定性不受影响。

### 明确不做
- 不做 Server/Log Agent 的服务上下文贯通（无真实服务 Connector，不假装按服务连接）。
- 不做跨服务联合调查（P6+）。
- 不做会话中途切换服务 / 服务上下文编辑。
- 不做服务选择权限管理与多租户（后续阶段）。
- 不改 mock 数据源（`data/mock_db.py`、`data/scenarios.py`）与 S1–S4 评测路径。
- 不新增凭据/配置（复用 P4.4 命名空间 DSN `OPERMIND_SERVICE_<INSTANCE_ID>_DSN`）。

## 2. 设计决策

### 2.1 service_id 合法值集
- 合法值由静态服务注册表（已注册 Connector 的 id）派生，不再以 `order-service` 为校验基线。
- 未注册 service_id 建会话被拒绝；`create_service_session("postgres-production")` 成功。
- `sessions.service_id` 的 CHECK 约束随白名单放开，与注册表保持一致。

### 2.2 服务上下文贯通
- `DiagnosisRunData` 新增 `service_id`（可空），Run 持久化来源会话的 service_id。
- 执行器按 `service_id` 从 `ServiceRegistry.get_connector(service_id)` 解析只读 Connector（支持任意已注册实例）；解析失败安全降级，不抛异常炸会话。
- DBAgent 工具按会话绑定服务连接真实库（真实模式），从对应实例命名空间 DSN 取连接；mock 模式行为不变。
- 未绑定 service_id 的会话发起 DB 相关调查 → 拒绝并提示先选择目标服务；Server/Log 调查不依赖服务上下文，行为不变。
- 未配置（无 DSN）→「未配置」降级；连接失败/超时 →「不可用」，不暴露异常详情。

### 2.3 前端服务选择入口
- 会话工作台首页发起调查时可选择已接入服务；选定后会话绑定该 service_id。
- 会话页展示本次调查针对的服务；未绑定不展示假服务。
- 接口：普通会话创建请求可携带 `service_id`；`Run` 资源新增 `service_id` 字段。

### 2.4 诚实降级
| 场景 | 行为 |
|---|---|
| 服务未注册 | 建会话拒绝 |
| 绑定服务无 DSN | 「未配置」 |
| 连接失败/超时 | 「不可用」，不暴露异常详情 |
| 未绑定服务 + DB 调查 | 拒绝并提示先选择目标服务 |

## 3. 文件改动面
- `backend/src/domain/records.py`：`DiagnosisRunData` 新增 `service_id`（可空）；`SessionData` 校验器与白名单逻辑改由注册表派生。
- `backend/src/application/`：`CreateRunCommand` 与执行器按会话 service_id 解析 Connector。
- `backend/src/core/graph.py` / 内核：service_id 上下文传至 DBAgent 工具。
- `backend/src/api/v1/`：普通会话创建请求可携带 `service_id`；`Run` 资源新增字段。
- `backend/src/persistence/`：`diagnosis_runs` 迁移新增 `service_id` 列；`sessions` CHECK 约束调整。**含数据库迁移。**
- 前端：会话工作台首页服务选择入口；会话页展示调查针对的服务。
- 测试：`test_p4_service_center.py`、`test_postgres_connector.py`、`test_agent_gateway.py`、`test_tool_gateway.py` 回归 + 新增覆盖。

## 4. 切片与验证（指引，不写死）
- 建议拆 2 片：S1 后端服务上下文贯通（白名单修复 + Run 携带 service_id + 执行器按服务取 Connector + 迁移）；S2 前端服务选择入口与展示（含 mock 模式回归）。每片独立可验收。
- 门禁项：数据库迁移、会话/Run 契约变更 → 需 Design → Review → 用户确认（本 Design 即满足）。
- 验证命令由 dev-plan 的 plan.md 落定（pytest / 前端 typecheck/build / git diff --check）。

## 5. 风险、回滚与门禁
- 风险集中在白名单放开后的越界访问与迁移破坏既有会话：已由「注册表派生 + 只读 Connector + mock 模式回归 + 迁移双向」防护。
- 回滚：`diagnosis_runs.service_id` 与 CHECK 约束迁移 downgrade；前端入口回退；DBAgent 仍按绑定服务取连接，未绑定则拒绝 DB 调查。
- 门禁：数据库迁移、Run 契约变更均需 arch-review PASS + 用户确认后放行 dev-plan。
