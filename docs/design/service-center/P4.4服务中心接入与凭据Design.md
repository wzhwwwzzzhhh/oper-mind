## 1. 目标与范围

把服务中心从「代码内静态注册 1 个 PostgreSQL 实例」扩展为「**多个服务实例可接入、可管理**」，
并明确凭据方案。解决运维「接入第二个数据库实例」的硬需求。

### 范围（做什么）
- 服务实例从**代码内写死**改为**配置/元数据声明**（多实例，PG 优先）。
- 凭据方案定稿：多实例的凭据来源、存储、脱敏边界。
- 服务能力声明沿用 `ServiceDefinitionData`（id/title/kind/supported_investigations/action_boundary），
  每实例一份。
- 连接状态沿用 `ServiceSnapshotData`（快照机制已在 P4 验证，多实例复用）。
- 连接测试能力：对已声明实例发起只读连通性检查。

### 不做什么（明确排除）
- 不新增 MySQL / Redis 的真实 Connector（后续按同一模式复制，本阶段只做框架 + PG 多实例）。
- 不做运行时动态增删实例的完整 CRUD（第一版配置/元数据驱动，重启生效；动态 UI 见"分阶段"）。
- 不做凭据编辑表单的前端（第一版凭据只走环境变量，不在 UI 保存）。
- 不做历史监控趋势 / 告警（P6+）。
- 不引入 DML/DDL/写操作（纯只读）。

## 2. 现状与问题

P4 已确认并交付：
- `PostgresServiceConnector` 单实例，`OPERMIND_PG_DSN` 单一环境变量。
- `ServiceRegistry((PostgresServiceConnector(...),))` 在 `dependencies.py` 代码内注册。
- `ServiceDefinitionData` / `ServiceSnapshotData` / `ServiceConnector` 协议已就位。

**扩展多实例的硬问题**：
1. **凭据**：多实例不能再各自硬编码一个 `OPERMIND_PG_DSN`；需要"实例 → 凭据"的映射，
   且不得落库/落代码/落文档/进日志/Trace/前端（P4 硬规则）。
2. **实例元数据**：实例身份（id/title/kind）放哪？代码？配置？应用库？——直接决定"动态接入"可行性。
3. **能力驱动**：`ServiceRegistry` 现在靠代码内显式传 Connector；多实例要按"类型 → Connector 工厂"派生。

## 3. 凭据方案（核心决策，分阶段）

### 原则（沿用 P4，不变）
- 凭据**绝不进入**：仓库、文档、日志、Trace、事件、结果、截图、Git、前端响应、应用库普通字段。
- 缺凭据 → `availability=not_configured`，不崩溃、不伪造。

### 方案分层：实例元数据与凭据分离

把"服务实例是什么"（身份/能力）和"服务实例怎么连"（凭据）**拆成两层**：

| 层 | 内容 | 存放位置 |
|---|---|---|
| 实例元数据 | id / title / kind / supported_investigations / action_boundary | 代码内定义（类型模板）或应用库只读表 |
| 凭据 | host / port / user / password / dsn | **只走环境变量**（命名空间化）或外部 Secret Provider |

### 凭据存储选型（决策点 D1，推荐 A）

- **方案 A（推荐，首版）：环境变量命名空间化**，零新增落库风险
  - 每个实例一个凭据命名空间：`OPERMIND_SERVICE_<INSTANCE_ID>_DSN`（或拆分 HOST/PORT/USER/PASSWORD）。
  - 实例 id 固定（如 `postgres-production`、`postgres-staging`），凭据 env 名 = `OPERMIND_SERVICE_POSTGRES_PRODUCTION_DSN`。
  - 未设置对应 env → 该实例 `not_configured`。
  - **优点**：零凭据落库，完全继承 P4 安全边界；实现轻。
  - **代价**：新增实例需要改代码（id 声明）+ 配 env；重启生效，非运行时动态。
- **方案 B：加密后落库（应用库 + 主密钥）**
  - 实例凭据 AES 加密存应用库，主密钥走 `OPERMIND_SECRET_KEY` 环境变量。
  - **优点**：运行时动态接入、UI 可编辑凭据。
  - **代价**：引入密钥管理、密文存储、前端脱敏回显的复杂度；主密钥泄漏=全量泄漏；
    与"凭据不落库"的既有硬规则冲突，需用户明确批准放宽。
- **方案 C：外部 Secret Provider（Vault 等）**
  - 凭据存 Vault，服务读引用。
  - **优点**：最安全、可轮换。
  - **代价**：引入外部基础设施依赖；本阶段过重。

**推荐：第一版走方案 A（环境变量命名空间化），把 B（加密落库）作为后续阶段，并在本 Design 里把 B 的边界先钉死。**

## 4. 实例模型与注册

### 类型模板（代码内声明，能力驱动）

每种服务类型一个"模板"定义（id 前缀、kind、支持的调查、动作边界），**实例 = 模板 + 实例身份 + 凭据 env 引用**：

```
PostgreSQL 模板：kind="postgres"
  ├─ 实例 postgres-production  → 凭据 env: OPERMIND_SERVICE_POSTGRES_PRODUCTION_DSN
  └─ 实例 postgres-staging     → 凭据 env: OPERMIND_SERVICE_POSTGRES_STAGING_DSN
```

- `ServiceRegistry` 支持按类型工厂派生实例，而不是每个实例手写一个 Connector 类。
- 实例 id 必须在注册表内唯一（现有约束保留）。

### 连接测试

- 对已声明实例发起 `health_snapshot()`（复用 P4 只读快照机制 = 连接测试 + 有限指标）。
- 结果复用 `availability`（healthy/unhealthy/unavailable/not_configured）。
- 前端可触发"重新检查"（现有 `ServiceDetailPage` 已有该按钮，行为复用）。

## 5. 装配与前端影响

### 后端装配（示意）
```python
# src/api/v1/dependencies.py
ServiceRegistry(tuple(
    create_instance("postgres-production"),
    create_instance("postgres-staging"),
    # 后续: MySQL/Redis 类型工厂
))
```
- `create_instance(instance_id)` 按类型模板 + 实例 id 解析对应 env 凭据，构造只读 Connector。

### 前端影响
- 接口契约**基本不变**：`GET /services`、`GET /services/{id}`、`/services/{id}/activities` 结构照旧。
- 服务中心列表自动显示多个实例；详情页复用。
- 若未配置某实例凭据 → 该实例显示"未配置"空态（诚实）。

## 6. 测试策略

- **单元测试**（不连真库）：用假连接/注入验证各分支：
  - 实例无对应 env → `not_configured`
  - 连接失败 / 超时 → `unavailable`
  - 正常 → `healthy` + 指标填充
  - 脱敏：快照不含 SQL / 对象名 / 凭据 / env 名
  - 多实例：注册表 id 唯一；两个实例各读各的 env，互不串扰
- **现有回归**：P4 的 `test_p4_service_center.py`、`test_postgres_connector.py` 全绿。
- **不做**：连真实 PG 的集成测试（本地手动验证）。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 凭据泄露（多实例更易散） | 只环境变量；实例名不出现在快照/前端；脱敏硬约束；新增实例先 Review |
| 实例 id 冲突 | 注册表 id 唯一校验（已有） |
| env 名拼写漂移 | 实例 id 与 env 名映射集中在单一工厂，单元测试覆盖 |
| 方案 B 密钥管理泄漏 | 本阶段不上 B；B 需用户批准放宽"不落库"规则 |
| 无凭据环境炸 | 缺 env → not_configured，不崩 |

回滚：移除多实例工厂，回到 `ServiceRegistry((单实例,))`，接口不变。

## 8. 已确认决策

1. ✅ 凭据存储：**方案 A（环境变量命名空间化）** 作为首版；方案 B（加密落库）钉边界后作为后续阶段。
2. ✅ 实例管理：首版**配置/元数据驱动，重启生效**；运行时动态增删 UI 为后续阶段。
3. ✅ 首版服务类型：仅 **PostgreSQL 多实例**；MySQL/Redis 框架预留，不实现 Connector。
4. ✅ 连接测试：复用 P4 `health_snapshot()`，不新增独立接口。

## 9. 开放问题（后续阶段待确认）

- **方案 B 边界**：若未来要运行时动态接入 + UI 编辑凭据，是否批准"加密落库"放宽"凭据不落库"硬规则？
  若批准，主密钥管理（`OPERMIND_SECRET_KEY`）与轮换策略需单独细化。首版不启动。
- **实例命名与 env 映射**：`OPERMIND_SERVICE_<INSTANCE_ID>_DSN` 的命名规则在实施时定稿（首版已接受该形态）。

## 10. 回滚与验收提示

- 回滚点：`dependencies.py` 回退到单实例注册，接口不变。
- 验收锚点：两个实例各自健康状态正确、互不串扰；无实例暴露凭据/env 名；P4 测试全绿。
