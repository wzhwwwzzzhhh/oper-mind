# 会话工作台生命周期闭环——归档浏览与恢复 · PRD

## 背景

会话工作台是 OperMind 的产品主入口。以下会话能力已经交付，本 PRD 不重复建设：

- `docs/prd/session/P8-workbench-loop-closure.md`：独立消息、取消 Run、全局提案列表；
- `docs/prd/session/P8-session-management.md`：会话搜索与全局 Run 列表；
- `docs/prd/session/P8-rerun-investigation.md`：调查重跑；
- `docs/prd/session/P8-message-edit-delete.md`：普通消息编辑与删除；
- `docs/prd/session/P8-session-export.md`：会话导出；
- 线上 `main` 的 [PR #95](https://github.com/wzhwwwzzzhhh/oper-mind/pull/95)：active 会话重命名、逻辑归档、归档确认和归档详情只读展示；现有接口事实同时见 `docs/接口清单.md` 会话工作台部分。

当前服务端会话列表已经支持按 `active / archived` 状态、标题关键词和 cursor 分页读取；归档后的消息、Run、提案、服务关联和审计关联也仍然保留。现有工作台只读取 active 会话，用户虽然可以归档，却没有产品入口浏览归档记录；通过直接地址进入 archived 会话时，也只能看到“当前版本不能恢复”。`docs/完善清单.md` P2-4 已记录这一缺口。

因此当前生命周期是单向的：

```text
创建 active → 使用 / 重命名 → 归档 archived → 只能凭直接地址只读查看
```

本 PRD 只补齐最后一段：接线既有 archived 列表能力，并允许用户把同一个 archived 会话原地恢复为 active，使“归档 → 找回 → 恢复使用”形成可逆、诚实、可恢复的闭环。

### 既有基线（只做回归保护）

- active 会话可重命名和逻辑归档；重复归档保持幂等。
- 归档前明确提示历史保留、会话录入只读、进行中的 Run 继续执行。
- archived 会话通过直接地址仍可读取历史并导出。
- 归档不取消、重跑或复制 Run，不改变提案审批、审计活动或消息接口的既有服务端语义。
- “会话录入只读”只约束工作台中的会话重命名、消息编辑/删除、新消息和新调查入口；Run 取消/重跑与提案审批仍按各自既有状态和入口规则处理，不由会话归档状态重新定义。

## 目标

1. 用户能在会话工作台中明确切换 active 与 archived 会话，不依赖记住直接地址找回历史。
2. 用户能把 archived 会话原地恢复为 active，并继续使用原有消息、调查与服务上下文。
3. 恢复后的会话状态在侧栏、搜索结果和详情中立即一致，失败或并发状态变化时不产生假成功。

## 用户故事

- 作为研发或运维人员，我误归档了一个仍需跟进的故障会话，希望能在归档列表中找到并恢复它，以便继续沿用原有上下文调查。
- 作为需要回看历史的用户，我希望归档会话有明确入口和“已归档”标识，以便查阅结论和留痕，而不会误以为还能直接继续对话。
- 作为管理多个会话的用户，我希望恢复后的状态立即在侧栏、搜索和详情中一致更新，以免重复恢复或进入过期状态。

## 范围

### 做什么

- 在会话侧栏提供“最近会话 / 已归档”切换；两种视图分别只展示 active 或 archived 会话。
- 归档视图复用既有标题搜索和分页能力，并提供加载、空列表、无匹配和失败状态。
- 在 archived 会话列表项和详情中提供“恢复会话”入口，确认后将同一个会话恢复为 active。
- 恢复成功后同步刷新 active 列表、archived 列表、搜索结果和当前会话详情；恢复会话进入 active 最近会话顶部。
- 对恢复中的重复提交、恢复失败和状态冲突提供明确且可重试的反馈。

### 不做什么（明确排除）

- 不重新实现或改造 active 会话重命名、归档、搜索、分页和直接地址读取；这些只作为回归基线。
- 不做会话永久删除、清空历史、定时清理或归档保留期限；归档仍是可恢复的逻辑状态。
- 不做批量归档、批量恢复、批量删除或批量导出。
- 不做文件夹、标签、收藏、置顶、自定义排序或跨会话合并。
- 不做消息全文搜索；归档视图只沿用会话标题搜索。
- 不改变消息编辑/删除、Run 取消/重跑、会话导出、提案审批和审计活动的既有服务端语义。
- 不新增归档/恢复生命周期业务审计事件；只保证既有 Run、提案和审计关联在状态切换后不丢失。既有通用请求日志与安全审计不因本 PRD 被关闭或改写。
- 不做跨用户归档箱、所有权转移、审批恢复或 RBAC；身份、租户和角色模型仍属未决事项。
- 不在归档或恢复时取消、重跑、复制或重新执行任何 Run，也不触发 Connector、Tool 或真实外部连接。
- archived 会话在工作台中不提供重命名、消息编辑/删除、新消息和新调查入口；本 PRD 不扩展为后端消息接口的会话状态权限改造。

## 功能需求

### 1. 归档会话入口、浏览与搜索

- **输入**：用户在会话侧栏切换“最近会话 / 已归档”，可选输入标题关键词并继续加载后续页面。
- **行为**：
  - “最近会话”只展示 active 会话；“已归档”只展示 archived 会话，切换后保留明确的当前视图标识。
  - 两种视图的标题搜索只在各自状态范围内生效；清空关键词恢复当前视图的默认列表。
  - archived 列表按最近更新时间倒序展示并沿用既有分页边界。
  - 无归档会话、无搜索结果、加载失败时分别展示诚实状态，不伪造记录，也不回退展示 active 会话。
  - 从 archived 列表进入详情后，继续展示既有消息、Run、结果、安全 Trace、提案状态和导出入口，并明确标识“已归档”。
- **输出**：可搜索、可分页、状态明确的 archived 会话列表及既有只读详情。

### 2. 恢复 archived 会话

- **输入**：用户从 archived 列表项或 archived 会话详情发起“恢复会话”并确认。
- **行为**：
  - 确认信息说明会话将重新进入 active 列表并恢复会话录入能力；恢复不会复制内容、创建 Run 或启动调查。
  - 恢复将同一个 session id 从 archived 变为 active；原标题、服务上下文、消息、Run、提案和审计关联保持不变。
  - 恢复后当前 `archived_at` 清空，`updated_at` 反映本次生命周期操作，使会话进入 active 最近会话顶部。
  - 恢复后的工作台重新提供 active 会话既有的重命名、消息和调查入口。
  - 对已经 active 的会话重复恢复保持幂等：返回服务器当前 active 事实，不创建重复资源，也不再次改变 `updated_at`。
- **输出**：恢复后的 active 会话、明确成功反馈及一致的导航状态。

### 3. 状态一致性与失败恢复

- **输入**：用户提交恢复，或操作期间会话状态已被其他请求改变。
- **行为**：
  - 恢复提交期间禁用同一入口的重复提交并展示进行中状态。
  - 成功后刷新 active 列表、archived 列表、当前搜索结果和会话详情，无需整页刷新。
  - 收到明确的服务端拒绝时保留操作前 archived 状态，展示安全错误并允许重试。
  - 网络中断、超时或响应丢失导致结果不确定时，先重新读取服务器会话事实：若已是 active，按幂等成功收敛；若仍是 archived，再保留原状态并提示重试。
  - 若恢复请求返回时服务器已经是 active，应按幂等成功处理并刷新到 active 状态。
  - 若会话不存在或出现其他不可恢复冲突，应以服务器错误为准，不在前端伪造恢复成功。
- **输出**：跨入口一致的服务器最新状态，以及可理解、可重试的反馈。

## 非功能需求（按需）

- **安全**：生命周期操作只修改 OperMind 应用元数据，不触发用户服务连接，不暴露凭据、原始工具输出、原始异常、Prompt 或 CoT。
- **可靠性**：恢复支持安全重试；并发或重复请求只有首次 `archived → active` 转换可以更新 `updated_at`，其余请求只观察当前 active 事实，不得创建重复资源或生命周期业务审计事件。
- **一致性**：恢复成功后所有相关会话查询都以服务器事实为准；失败时不得仅依赖前端乐观状态宣称成功。
- **性能**：active 与 archived 列表均沿用既有 `limit` 上限、cursor 分页和标题搜索输入上限，不新增无界列表。
- **可访问性**：用户可用 Tab 聚焦视图切换与恢复入口、用 Enter/Space 触发、用 Escape 关闭恢复确认框；进行中和错误反馈具有可识别文本。
- **诚实性**：状态、空数据、请求失败和 queued/running Run 的真实进度必须如实展示；会话录入只读不等于停止后台 Run。

## 数据与接口影响（按需）

- 数据：复用既有 Session 的 `active / archived` 状态、`archived_at` 与 `updated_at`，不新增会话副本、字段、表或审计事件；恢复时清空当前 `archived_at` 并更新 `updated_at`，所有关联记录保持原样。
- 接口：归档列表复用既有会话列表状态过滤、标题搜索和分页契约；恢复扩展既有会话更新契约的状态转换语义，允许 `archived → active`。不新增旁路恢复接口。
- 迁移：无数据库迁移。若 Design 发现现有状态模型无法满足上述语义，必须退回 PRD 重新确认范围，不能由执行阶段擅自新增迁移。

## 验收标准

- [ ] AC1: 当用户打开会话侧栏时，应能在“最近会话 / 已归档”之间切换，两个视图分别只展示 active 或 archived 会话。
- [ ] AC2: 当用户在“已归档”视图搜索标题或加载下一页时，应只返回匹配的 archived 会话，并沿用既有搜索输入与分页边界。
- [ ] AC3: 当没有归档会话、搜索无匹配或列表读取失败时，应分别展示明确空态或错误态，不展示 active 会话充数。
- [ ] AC4: 当用户从 archived 列表进入会话详情时，应能读取既有历史、Run 状态、提案状态和导出入口，并看到明确的“已归档”标识。
- [ ] AC5: 当用户查看 archived 会话时，工作台不应提供重命名、消息编辑/删除、新消息和新调查入口；Run 取消/重跑与提案审批仍遵循各自既有状态和入口规则。
- [ ] AC6: 当 archived 会话仍有关联 queued/running Run 时，详情应继续刷新并如实展示 Run 状态；归档与恢复不得自动取消或重跑该 Run。
- [ ] AC7: 当用户从 archived 列表项或详情发起恢复时，应先看到“恢复录入能力、不复制内容、不启动调查”的确认信息。
- [ ] AC8: 当恢复成功时，应把同一 session id 变为 active，清空当前 `archived_at`，更新 `updated_at`，并保留原标题、服务上下文、消息、Run、提案和审计关联。
- [ ] AC9: 当恢复成功时，会话应从 archived 列表移入 active 最近会话顶部，并重新提供 active 会话既有的重命名、消息和调查入口。
- [ ] AC10: 当两个客户端并发恢复同一 archived 会话，或服务器已恢复后客户端重复提交时，只允许首次状态转换更新一次 `updated_at`；其余请求应按幂等成功观察 active，不创建资源，也不再次改变 `updated_at`。
- [ ] AC11: 当恢复收到明确拒绝时，应保留 archived、展示安全错误并允许重试；当网络失败导致结果不确定时，应先回读服务器事实并收敛到 active 或 archived；会话不存在时不得伪造成功。
- [ ] AC12: 当恢复请求进行中时，应阻止同一入口重复提交；完成后 active 列表、archived 列表、当前搜索结果和详情应以服务器状态一致刷新。
- [ ] AC13: 归档与恢复不得新增生命周期业务审计事件，也不得丢失既有 Run、提案和审计关联；既有通用请求日志与安全审计保持原行为。
- [ ] AC14: 归档浏览与恢复不得暴露凭据、DSN、原始工具输出、原始异常、Prompt 或 CoT，也不得触发 Connector、Tool 或真实外部连接。
- [ ] AC15: 既有 active 重命名/归档、会话标题搜索/分页、直接地址读取、消息编辑/删除、Run 取消/重跑、会话导出和提案审批相关自动化测试应保持通过。

## 边界与约束

- 安全边界：生命周期管理仅作用于 OperMind 应用元数据；不得读取、修改或清理用户服务中的数据。
- 降级策略：列表读取失败时展示不可用状态；无数据展示空态；恢复失败时保持 archived 并允许重试；直接地址访问 archived 会话时仍可读取历史。
- 兼容性：active 会话的既有创建、搜索、消息、Run、SSE、Trace、提案与导出契约保持兼容；本 PRD 只扩展既有会话更新契约的 `archived → active` 状态转换。
- 状态纪律：归档是可恢复状态，不等于永久删除；恢复不等于重跑，也不改变既有调查结论。
- 设计闸门：本 PRD 改变公开会话更新契约的状态转换语义，开发前必须完成 Design → Review → 用户确认。
