# 跨服务联合调查——会话多服务 + 多 Run 聚合 · PRD

## 背景

当前系统**一个会话/Run 只绑定一个服务**（service_id 贯穿全栈为单值）：
- `SessionData.service_id` / `DiagnosisRunData.service_id` 均为 `str | None` 单值可空；
- `DBAgent` / 工具按构造时单个 `service_id` 取 Connector，每次工具执行只服务一个实例；
- 会话工作台欢迎页服务选择是**单选** `select`（`WelcomePanel.tsx:46`），发起调查只带单个 service_id；
- 证据归因：`EvidenceFact` 无服务归属字段，仅在 `tool_invoked` 事件 data 层携带单 service_id。

P4.3 已明确把"跨服务联合调查"排除到 P6+。现状痛点：运维排障常要跨多个服务（如"Redis 连接池超时"同时要看 Redis 连接数 + PostgreSQL 慢查询），但产品主链只支持单服务调查。若按"每服务一个会话"拆开，一次排障会被碎片化成多个会话，违背"一个会话解决一个问题"的产品直觉——**用户希望在一个会话里查一个涉及多服务的问题**。

架构文档待决点："一个 Run 是否跨多服务（模型允许，首版 UI 先单服务）"。本 PRD 采用**会话承载多服务 + 多 Run 聚合**方案（已确认）：
- **会话层**关联多个服务（`session_services` 关联表 + 数据库迁移），一个会话可承载多服务上下文；
- **Run 层**保持单服务多 Run：会话内提问时对每个选中服务各建一个 Run，并行走既有单服务调查链路；
- **前端**在同一个对话线程内按服务分组聚合展示各 Run 结果。

关联：
- `docs/prd/session/P4.3-service-context.md`（单服务上下文贯通，本 PRD 前置）
- `docs/架构与开发路径.md`（"一个 Run 是否跨多服务"待决点）
- `docs/产品定义.md` §2.1（会话主入口）、§4（跨来源联合排障：多服务、多 Agent 的证据汇总）
- `docs/路线图.md` 第三阶段（跨来源联合排障）

## 目标

1. **一个会话承载多个服务上下文**：会话创建/运行时关联多个已接入服务，用户在一个会话内查跨服务问题，不被会话碎片化。
2. **多服务联合调查**：会话内提问对每个选中服务各建一个 Run，并行走单服务链路，产出按服务归属的证据。
3. **前端同一对话线程内按服务分组聚合展示**：各服务调查结果、Trace、证据集中可见、可对比。
4. **Run 层保持单服务**：不改 `DiagnosisRunData` 为多值，不动 DBAgent/工具链；复用 P4.3 已贯通的单服务链路。

## 用户故事

作为运维工程师，我在排查"Redis 连接池偶发超时"时，需要同时看 Redis 实例的连接数/慢日志和 PostgreSQL 主库的慢查询。我在一个会话里勾选 Redis 和 PostgreSQL 两个服务，一次提问，就能在同一对话线程里看到两个服务各自的只读调查结果与证据，并继续追问——而不是开两个会话自己对照。

## 范围

### 做什么

- **会话层多服务关联**：`SessionData` 服务上下文从单值扩展为多值，新增 `session_services` 关联表（会话 ↔ 服务），含数据库迁移。
- 会话创建时接受 `service_ids` 列表；`POST /services/{id}/sessions` 保留（单服务快捷入口），普通会话创建支持多服务。
- 会话工作台欢迎页服务选择从**单选 `select` 改为多选**（checkbox/多选标签），支持勾选 0 个或多个已接入服务。
- 勾选多个服务时，**为每个服务各建一个 Run**（复用既有单服务 `create_run` 链路），并行发起调查。
- 前端在对话线程内**按服务分组聚合展示**：每个服务一个调查结果区，含各自的诊断结论、Trace、证据。
- 服务中心"发起调查"入口支持多选服务。
- 会话页展示本次调查涉及的**服务集合**（多服务标识）。

### 不做什么（明确排除）

- **不做单 Run 跨服务**：不把 `DiagnosisRunData` / DBAgent / 工具的 service_id 改成多值集合；Run 仍单服务，多服务靠多个 Run 承载。
- 不做多服务证据的**自动交叉归因/关联分析**（各服务独立调查，前端分组展示，不做跨服务推理）。
- 不做服务选择权限管理、多租户、并行度控制（首版固定顺序或低并发并行）。
- 不做单 Run 内多 Agent 跨服务联合取证（那需要单 Run 多服务架构，P6+ 后续阶段）。
- 不改 mock 数据源、S1–S4 评测路径、既有 `GET /services` 契约。

## 功能需求

### 1. 会话多服务关联（数据模型）

- **输入**：会话创建时的 `service_ids: string[]`（0 个或多个已注册服务 id）。
- **行为**：会话关联多个服务，持久化到 `session_services` 关联表；服务 id 合法值集由静态服务注册表派生（复用 P4.3）；重复/未注册服务被拒绝；未选服务时关联空集。
- **输出**：一个会话关联多个服务的持久化记录。

### 2. 多服务选择（会话工作台）

- **输入**：用户在欢迎页勾选 0 个或多个已接入服务。
- **行为**：服务选择控件从单选改多选；已接入服务列表来自 `GET /services`；未选服务时行为与现状一致（不绑定服务）。
- **输出**：前端持有的选中服务 id 集合 `selected_service_ids: string[]`。

### 3. 多 Run 并行调查

- **输入**：用户发起调查（提交 prompt），携带会话的多个关联服务。
- **行为**：对会话关联的每个服务各建一个 Run（复用 `create_run` / 服务上下文会话链路）；多个 Run 并发或顺序发起；每个 Run 独立走既有单服务调查链路，独立产生结论与证据。
- **输出**：N 个 Run 的独立调查结果，各自绑定对应服务。

### 4. 按服务分组聚合展示

- **输入**：多服务调查的 Run 结果集合。
- **行为**：对话线程内按服务分组展示各 Run 的结果；每个服务一个调查结果区，含诊断结论、Trace、证据摘要；服务标识清晰（服务名/logo/类型）。
- **输出**：多服务聚合视图，用户可逐服务查看并对比。

### 5. 服务中心多选发起

- **输入**：服务中心选择多个服务发起调查。
- **行为**：服务选择支持多选；发起后创建关联多服务的会话，跳转会话工作台并预填多服务调查。
- **输出**：带多服务上下文的联合调查会话。

### 6. 会话页服务集合展示

- **输入**：多服务调查的会话/Run。
- **行为**：会话页展示本次调查涉及的服务集合（多服务标识），非单服务时不做假单服务展示。
- **输出**：会话页清晰展示联合调查涉及的服务列表。

## 非功能需求

- **性能**：多 Run 发起有限制并发或顺序，避免一次发起过多；单 Run 链路不变。
- **安全**：纯只读；各服务按既有单服务链路鉴权/脱敏；无凭据/DSN 外泄。
- **诚实**：未选择服务时如实；各服务结果独立展示，不做跨服务关联推理的暗示。
- **可靠**：单个 Run 失败不影响其他服务的结果展示；每个服务独立降级。

## 数据与接口影响

- 数据：**含数据库迁移**。新增 `session_services` 关联表（`session_id` ↔ `service_id`，多对多）；`sessions` 表保留 `service_id` 列（兼容单服务快捷入口）或迁移到关联表承载（需 Design 定稿）。`DiagnosisRunData` 保持单值，不改。
- 接口：普通会话创建请求可携带 `service_ids` 列表；`POST /services/{id}/sessions` 保留（单服务快捷入口）；会话详情/列表响应展示服务集合（多服务）。`GET /services` 不变。

## 边界与约束

- 安全边界：纯只读，无写路径；各服务按既有单服务链路鉴权/脱敏；无凭据/DSN 外泄。
- 降级策略：单服务失败独立降级；未选服务如实；多选时不强行跨服务关联。
- 兼容性：单服务路径与现状完全一致（`POST /services/{id}/sessions` 保留）；`DiagnosisRunData` 单值语义不变；S1–S4 评测不变。

## 开放问题

1. ~~sessions 表 service_id 列去留~~ **已确认方案一**：保留 `sessions.service_id` 单值列兼容。单服务快捷入口 `POST /services/{id}/sessions` 仍写单值列 + 关联表；普通会话只写关联表。
2. **多选 UI 形态**：欢迎页服务选择从单选 `select` 改为多选，用 checkbox 列表还是多选标签/下拉多选？——影响前端实现。建议 checkbox 列表（直观、可读性好）。
