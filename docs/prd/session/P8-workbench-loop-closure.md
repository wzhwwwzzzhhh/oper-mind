# 会话工作台闭环——独立消息、取消 Run 与全局提案列表 · PRD

## 背景

会话工作台是产品主入口（`docs/产品定义.md` §2.1），但主链路上有三个体验洞（`docs/接口清单.md` 第一大模块"缺少"表）：

1. **没有独立发消息**。当前唯一的"发消息"入口是 `POST /sessions/{id}/runs`（体 `{query, service_id}`），任何一句话都会拉起一整轮多 Agent 调查。用户说"谢谢"、追问一句澄清、或只想聊两句，都会触发整条调查链——主入口上最别扭的一处。
2. **无法取消运行中的 Run**。无 `DELETE /runs/{id}` 也无 `/runs/{id}/cancel`。Run 卡住只能等超时，界面上没有任何退出路径。
3. **没有全局提案列表**。待审批提案只能顺着某个 Run 摸进去。没有任何地方能回答"现在有几个提案等我批"——审批是产品的安全卖点，却没有入口（`docs/接口清单.md` 明确标注"审批是产品的安全卖点，却没有入口"）。

关联：`docs/接口清单.md`（第一大模块缺表）、`docs/prd/session/README.md`（会话/Run/SSE/Trace 域）、`docs/prd/approval/P5-controlled-action-real.md`（受控动作闭环已交付）、`docs/完善清单.md` P1-11（提案审批 UI 体验）、`docs/产品定义.md` §2.1（会话主入口）。

## 目标

1. 用户在会话里说普通消息（感谢/澄清/闲聊）时，系统**只回一条普通回复**，不触发多 Agent 调查。
2. 用户能**取消运行中的 Run**，看到明确的取消反馈，不再只能干等超时。
3. 用户能在一个页面看到**所有待审批提案**并进入审批流程。

## 用户故事

- 作为用户，我在调查完慢查询后说"谢谢""好的，明白了"，系统应把它作为普通对话处理，而不是又启动一轮完整调查——以便自然追问，不浪费。
- 作为用户，我发起的 Run 卡住了，应能点"停止"取消它——以便不被卡住的调查阻塞。
- 作为审批人，我想知道"现在有几个提案等我批"，应有一个列表入口——以便及时处理待审批动作。

> 边界说明：含调查意图的追问（如"那连接池呢"）**不属于**普通消息——它会命中调查关键词（`_requires_database_context` 同源，含"连接池""慢查询""索引"等），走 Run 主链路。普通消息只指不含任何调查关键词的纯社交/确认性话语（感谢、理解、打招呼）。

## 范围

### 做什么
- **独立消息通道**：会话消息与调查 Run 解耦。非调查意图的普通消息走轻量回复，不创建 Run、不启动多 Agent 图。
- **取消 Run**：新增 `POST /runs/{id}/cancel`（或 `DELETE /runs/{id}`），运行中的 Run 可被取消并留下取消状态；已结束的 Run 不可取消。
- **全局提案列表**：新增 `GET /action-proposals`（跨会话跨 Run 的提案列表，cursor 分页，支持状态过滤），前端新增"待审批"入口页。
- 前端工作台适配：消息输入框区分"普通消息"与"调查发起"；Run 进行中显示"停止"按钮；导航新增"待审批"入口。

### 不做什么（明确排除）
- 不做消息编辑/删除（接口清单欠账，优先级低，另行排期）。
- 不做全局 Run 列表 `GET /runs`（接口清单欠账，另行排期）。
- 不做会话搜索（`完善清单.md` P1-12，另行排期）。
- 不做重跑/重新生成（接口清单欠账，另行排期）。
- 不做身份/审批人模型（`docs/产品定义.md` §7 未决；`POST /approval` 无审批人身份是已知缺陷，非本 PRD 范围）。
- 不改变调查类消息的现有行为（`POST /sessions/{id}/runs` 主链路不变）。

## 功能需求

### 1. 独立消息通道
- **输入**：用户在会话输入框发送的消息文本。
- **行为**：
  - 系统判定消息是否属于调查意图（复用/对齐既有路由的关键词判定 `_requires_database_context`：慢查询、索引、连接池、`explain`、`select` 等 → 调查；其余 → 普通对话）。
  - 调查意图 → 走既有 `POST /sessions/{id}/runs` 主链路（行为不变）。
  - 普通意图 → 创建一条 user 消息 + 一条 assistant 回复（简短、诚实，不触发多 Agent 图、不创建 Run），回复内容为通用引导或简单确认，明确说明"这不会启动调查"。
- **输出**：user 消息 + assistant 普通回复，均进入会话消息列表。

### 2. 取消 Run
- **输入**：用户对运行中 Run 发起取消。
- **行为**：
  - 仅对 `queued` / `running` 状态的 Run 生效；已 `succeeded` / `failed` / `cancelled` 的 Run 返回明确错误（或 409）。
  - 取消后 Run 状态置为 `cancelled`，事件流写入取消事件；后台执行被终止（如已启动）或不再启动（如排队中）。
  - 取消是幂等的：已取消的 Run 重复取消仍返回 204（或等价成功）。
- **输出**：取消成功 204；Run 状态变为 `cancelled`；会话/消息/Trace 如实反映取消。

### 3. 全局提案列表
- **输入**：请求 `GET /action-proposals`，可选状态过滤（`pending_approval` 等）与 cursor 分页。
- **行为**：跨会话跨 Run 返回提案安全摘要列表（proposal id、来源 Run、动作、状态、创建时间、标题），不含证据原文或未脱敏字段；按状态过滤时只返回匹配项。
- **输出**：提案分页列表；点击某项进入既有提案详情/审批流程。

### 4. 前端工作台适配
- **输入**：会话工作台、运行中 Run 卡片、全局导航。
- **行为**：输入框发送普通消息走轻量回复；Run 进行中显示"停止"按钮；导航新增"待审批"入口页（列表 + 进入审批）。
- **输出**：闭环的用户界面。

## 非功能需求
- **诚实**：普通消息的回复明确说明"未启动调查"；取消反馈如实；空提案列表显示空态不伪造。
- **可靠**：取消是幂等的；单 Run 取消不影响其他 Run。
- **性能**：普通消息回复应为轻量路径（秒级），不拉起重调查。
- **安全**：提案列表返回安全摘要，不含证据原文、原始工具输出或未脱敏内容。

## 数据与接口影响
- 数据：消息与 Run 解耦后，普通消息仍落库（复用既有消息表，run_id 为空）；Run 新增 `cancelled` 状态（既有 `RunStatus` 是否含 cancelled 需确认，若不含则涉及枚举扩展）；提案列表复用既有 action 事件表。
- 接口：新增 `POST /runs/{id}/cancel`、`GET /action-proposals`；`POST /sessions/{id}/runs` 主链路不变；消息列表接口兼容。

## 验收标准
- [ ] AC1: 当用户在会话里发送普通消息（如"谢谢"）时，应返回一条 assistant 普通回复，不创建新 Run、不触发多 Agent 调查。
- [ ] AC2: 当用户在会话里发送调查意图消息（如"排查慢查询"）时，应走既有 Run 主链路（行为不变）。
- [ ] AC3: 普通消息的回复应明确说明"未启动调查"，不伪造调查结果。
- [ ] AC4: 当对 running Run 发起取消时，Run 应转为 `cancelled`，事件流写入取消事件，后台执行终止。
- [ ] AC5: 当对已结束（succeeded/failed/cancelled）Run 发起取消时，应返回明确错误（如 409），不改变状态。
- [ ] AC6: 重复取消同一 Run 应幂等（第二次仍返回成功）。
- [ ] AC7: 当请求 `GET /action-proposals` 时，应返回跨会话跨 Run 的提案安全摘要分页列表。
- [ ] AC8: 当用状态过滤提案列表（如 `pending_approval`）时，应只返回匹配状态的提案。
- [ ] AC9: 提案列表响应不得包含证据原文、原始工具输出或未脱敏字段。
- [ ] AC10: 前端导航应有"待审批"入口，列表可进入既有提案详情/审批流程。
- [ ] AC11: 回归 —— 既有 `test_api.py`、`test_p2_application_services.py`、`test_p5_controlled_action.py` 相关全绿；前端 `typecheck`/`test`/`build` 通过。

## 边界与约束
- 安全边界：普通消息轻量回复不触发任何工具/连接；提案列表脱敏；取消不产生部分执行状态（如已提审提案不受取消影响）。
- 降级策略：普通消息意图判定失败时按普通对话处理（不误触发调查）；取消冲突返回明确错误。
- 兼容性：`POST /sessions/{id}/runs` 主链路行为不变；既有消息/会话/Run 接口契约兼容；mock 模式行为一致。

## 开放问题
1. **普通消息的回复内容**：是通用引导（"我可以帮你排查慢查询/连接问题…"）还是调用轻量 LLM 生成？→ 推荐首版用模板引导（确定性、零外部依赖），LLM 轻量回复后续版本。
2. **意图判定逻辑**：复用既有路由关键词还是新增轻量分类？→ 推荐首版复用既有关键词（`_requires_database_context` 同源），保持确定性。
3. **Run 取消的实现深度**：后台执行是协作式取消（检查点检查取消标志）还是强终止？→ 推荐协作式（安全，避免中断时留下不一致状态）。
