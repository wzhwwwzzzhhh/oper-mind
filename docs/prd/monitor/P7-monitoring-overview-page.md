# 服务监控概览页——多服务监控聚合（导航"服务监控"落地） · PRD

## 背景
前端全局导航（`frontend/src/features/shell/GlobalNav.tsx`）预留了「服务监控」入口（`monitor` 键），
当前是死占位（`active: false`，点击无路由）。同时监控能力已分批交付或确认：

- P4 服务中心快照变真：单次现读快照（availability、p50/p95、慢查询计数、超时计数，3s 超时只读）；
- P5 服务监控历史趋势与页面内告警（完成）：定时采样器 + 历史趋势查询接口 +
  页面内异常高亮（"定时采样 · 每 5 分钟 · 保留最近 24 小时 · 历史记录"）；
- P6 服务主机指标监控（完成）：主机级指标（CPU/内存/磁盘/网络等）；
- P6 Redis 服务接入与只读监控（完成）。

这些能力目前分散在服务详情页（趋势卡片、主机指标）和各服务自己的页面里，**没有一个
"所有已接入服务监控概览"的视图**——用户想快速判断"现在哪个服务在恶化"，需要逐个打开服务详情页。

本 PRD 把导航「服务监控」落地为**多服务监控概览页**：一张视图聚合所有已接入服务的
连接状态、最新快照标量、近期趋势摘要与异常采样点，从概览可进入单个服务详情。

关联：`docs/prd/monitor/P5-monitor-trends.md`（历史采样与接口契约，本页面的趋势摘要数据源）、
`docs/prd/monitor/P6-host-metrics-monitoring.md`（主机指标数据源）、
`docs/prd/service-center/P4.4-service-instances.md`（多服务注册表，概览对象来源）、
`docs/产品定义.md` §5.5（监控诚实性：区分当前快照/历史/不可用/未知）、
`docs/开发规范.md` §5（不得把一次读取伪装成长期实时监控）。

## 目标
1. 导航「服务监控」落地：`/monitor` 页面聚合展示**所有已接入服务**的监控概览
   （连接状态 + 最新快照标量 + 近期趋势摘要 + 异常采样点标记）。
2. 从概览页可进入单个服务的详情页继续深挖。
3. 全程诚实：明确标注数据来源（定时采样 · 历史记录）、采样频率与保留窗口；
   未配置/不可用/无样本如实空态，不伪造实时监控。

## 用户故事
作为运维工程师，我想打开「服务监控」一眼看到所有已接入服务的健康概览——
哪个服务最近有慢查询/超时异常、哪个服务连接不可用、趋势是好转还是恶化——
然后点进异常服务看详情，以便快速定位需要介入的对象。

## 范围

### 做什么
- 新增**监控概览数据接口**（只读）：按服务聚合返回——最新快照标量（复用 P4 快照）、
  近期趋势摘要（复用 P5 历史样本：窗口内样本数、最新值、异常采样点计数）、
  主机指标摘要（复用 P6 主机指标，若该服务类型已交付）、服务连接状态。
- 前端 `/monitor` 页面：所有已接入服务的概览（服务名/类型/连接状态/最新延迟/慢查询/
  超时/异常标记/主机指标摘要），从概览可跳转服务详情页。
- 诚实标注：页面标注"定时采样 · 每 5 分钟 · 保留最近 24 小时 · 历史记录"；
  未配置/不可用/无历史样本的服务如实展示对应状态，不伪造数值。
- 数据来源组合方式（后端聚合接口 vs 前端多接口聚合）由 Design 定，PRD 只要求概览视图的
  数据能力与诚实性。

### 不做什么（明确排除）
- 不做外部告警推送（邮件/Slack/Webhook 等）：无通知渠道，如实标注未启用（与 P5 一致）。
- 不做实时/近实时监控：概览展示的是最新采样快照与历史记录，不是实时值。
- 不做跨服务对比图表、历史搜索、导出、聚合报表。
- 不新增监控凭据/连接：复用既有服务注册与快照能力，未配置服务如实展示"未配置"。
- 不新增采样器/历史采集逻辑（采样与历史数据由 P5 交付，本 PRD 只消费）。
- 不做服务管理（接入/编辑服务等，属服务中心）。
- 不改 mock 数据源（`data/mock_db.py`、`data/scenarios.py`）与 S1–S4 评测路径。

## 功能需求

### 1. 监控概览数据接口
- **输入**：无（默认返回静态注册表内全部已接入服务；分页/参数由 Design 定）。
- **行为**：
  - 对每个已注册服务聚合：最新快照标量（availability、p50/p95、慢查询计数、超时计数）、
    近期趋势摘要（窗口内样本数、最新样本值、异常采样点计数）、主机指标摘要（该服务类型已交付时）；
  - 服务未配置 DSN → "未配置"；快照/采样失败 → "不可用"；无历史样本 → "暂无历史采样"；
  - 接口只返回脱敏标量与状态，不返回 SQL、对象名、用户名、IP 或凭据。
- **输出**：服务监控概览列表（JSON）。

### 2. 前端监控概览页
- **输入**：全局导航 `monitor` 入口 → 路由 `/monitor`。
- **行为**：
  - 渲染所有已接入服务的概览表格/卡片：服务名、类型、连接状态、最新延迟（p50/p95）、
    慢查询/超时计数、异常采样点标记、主机指标摘要；
  - 异常标记规则与 P5 一致（slow_query_count>0、timeout_count>0、可用性状态变化；
    Redis 服务为 slowlog_count>0——与 P5 已交付的前端 Redis 异常判定一致）；
  - 页面标注"定时采样 · 每 5 分钟 · 保留最近 24 小时 · 历史记录"，不得标注"实时监控"；
  - 无数据/未配置/不可用保持诚实空态；请求失败可重试，不崩溃；
  - 每行可点击进入对应服务详情页（`/services/:id`）。
- **输出**：监控概览视图 + 详情跳转。

### 3. 诚实与降级
- **输入**：任意服务集合（含未配置/不可用/无样本服务）。
- **行为**：各服务独立降级——未配置 → "未配置"；不可用 → "不可用"；无样本 → "暂无历史采样"；
  单个服务失败不影响其他服务展示。
- **输出**：逐服务状态如实呈现。

## 非功能需求
- **性能**：概览接口限时（复用网关超时模式）；单服务快照/采样失败不阻塞整体概览；
  概览数据可短暂缓存（Design 定），避免页面打开触发大量真实查询。
- **安全**：只读；接口只返回脱敏标量；复用既有快照/采样安全边界；无新增凭据/连接。
- **诚实**：区分当前快照 / 历史记录 / 未配置 / 不可用 / 未知；标注采样频率与保留窗口。
- **可靠**：P5 采样器未运行或历史为空时页面仍可用（显示"暂无历史采样"），不崩溃。

## 数据与接口影响
- 数据：无新增持久化、无数据库迁移（消费 P5 历史样本与既有快照）。
- 接口：**新增监控概览接口**（公开 API，只读）；数据源依赖 P5 历史趋势接口与 P6 主机指标接口
  （均已交付，契约见 `P5-monitor-trends.md` 与 `P6-host-metrics-monitoring.md`）。
- 兼容性：既有服务接口与详情页契约不变；mock 评测（S1–S4）行为不变。

## 验收标准
- [ ] AC1: 当静态注册表内存在已接入服务时，概览页展示全部服务（服务名/类型/连接状态），
      无遗漏、无未注册服务混入。
- [ ] AC2: 每个服务显示最新快照标量（availability、p50/p95、慢查询/超时计数），
      数据来自只读快照/采样，不伪造。
- [ ] AC3: 当服务有历史样本时，显示近期趋势摘要与异常采样点计数；当无样本时，
      显示"暂无历史采样"诚实空态，不画假趋势。
- [ ] AC4: 当服务未配置 DSN 时，显示"未配置"；当快照/采样失败时，显示"不可用"，
      均不显示伪造数值，单个服务失败不影响其他服务展示。
- [ ] AC5: 概览页标注"定时采样 · 每 5 分钟 · 保留最近 24 小时 · 历史记录"，
      不出现"实时监控"表述。
- [ ] AC6: 存在慢查询>0、超时>0 或可用性状态变化的服务时（Redis 服务为 slowlog>0，与 P5 前端
      异常判定一致），概览页对该服务做异常标记，标记为"采样点异常"而非"正在告警"。
- [ ] AC7: 概览每行可进入对应服务详情页（`/services/:id`）。
- [ ] AC8: 概览接口与页面只返回脱敏标量，不含 SQL、对象名、用户名、IP 或凭据。
- [ ] AC9: 概览接口请求失败时页面显示失败空态并可重试，不崩溃。
- [ ] AC10: 回归 —— mock 评测（S1–S4）路径不受影响；既有服务接口契约不变；
       相关后端测试、前端 typecheck/test/build 全绿。

## 边界与约束
- 安全边界：只读；概览对象只能是静态注册表内已注册服务；只返回脱敏标量；
  无新增凭据/连接/写路径。
- 降级策略：未配置 → "未配置"；不可用 → "不可用"；无样本 → "暂无历史采样"；
  请求失败 → 失败空态可重试；均不抛异常、不伪造。
- 兼容性：mock 评测（S1–S4）行为不变；既有服务快照/详情接口契约不变；
  P5/P6 交付前概览接口可先返回快照 + 空态（实施前确认交付顺序）。
- 工程闸门：本 PRD 涉及**新增公开 API 与前端页面**，按开发规范须先 Design → Review →
  用户确认才能实施；本 PRD 是需求层，不替代 Design 文档。
