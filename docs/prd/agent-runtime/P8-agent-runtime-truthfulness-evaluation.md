# Agent 运行真实性与评测基线 · PRD

## 背景

OperMind 已具备 Coordinator、DB / Server / Log / Knowledge 领域 Agent、受控 Tool、Debate、Reflection、Report 与安全 Trace，正式会话也已接入这条运行链路。但现有 mock 模式只能证明“流程跑完”，不能证明“各 Agent 按角色正确工作”：不同领域 Agent 可能产出相同的固定结论，非数据库 Agent 可能尝试调用数据库工具，质量复核节点在 mock 下可能被无条件视为通过。

这会产生两个直接问题：用户可能把模拟结果误认为真实调查结论；研发在修改路由、工具或报告时，也缺少一套能发现 Agent 行为回归的确定性基线。与此同时，现有 Server 工具在真实采集依赖不可用时仍存在返回固定指标的历史占位，与产品“不可用就如实降级”的原则冲突。

本 PRD 属于 P8“体验驱动完善”的收口工作，只修复现有 Agent 链路的失真、误导和不可验证问题，不增加新的 Agent 能力。关联事实与约束：

- `docs/产品定义.md` §2.2、§4、§5：多 Agent 是内部能力，公开 Trace 只展示安全摘要；未实现或不可用能力不得伪装成已启用。
- `docs/路线图.md`“当前阶段：体验驱动完善”：P8 不新增能力，只做修复、接线与如实降级。
- `docs/开发规范.md` §2、§6、§7：Tool 必须受控，mock 不得冒充真实执行；多 Agent 编排语义变化须经 Design → Review → 用户确认。
- `docs/完善清单.md` P0-3、P1-2 与 `docs/跑通验证.md` C3：已记录 mock 多 Agent 失真、跨角色工具调用和 Server 假指标问题。
- `docs/prd/session/P4.2-db-agent-real.md`、`docs/prd/knowledge/P6-knowledge-retrieval.md`、`docs/prd/monitor/P6-host-metrics-monitoring.md`：分别规定数据库、知识与主机数据的真实来源、mock 边界和诚实降级要求。

## 目标

1. mock 模式下，不同领域 Agent 只在自己的能力和工具边界内工作，输出与角色、场景和证据一致的确定性结果。
2. 当工具、数据源或质量复核步骤不可用、未触发或失败时，系统如实表达状态，不伪造指标、证据或“已通过”结论。
3. 建立可重复执行的 Agent 行为评测基线，使路由、工具选择、证据归属、质量节点与公开输出的回归可以被自动发现。

## 用户故事

- 作为运维用户，我在 mock 模式体验多 Agent 调查时，希望明确获得与所选场景和 Agent 角色一致的模拟结论，而不是把同一段数据库结论套到所有角色上，以便正确理解产品能力边界。
- 作为运维用户，当某项指标或证据无法采集时，我希望看到“不可用”“未配置”或“未执行”，而不是一个看似真实的固定数值或成功状态，以免据此做出错误判断。
- 作为研发与评审人员，我希望每次修改 Agent 运行层后都能执行同一组确定性场景，确认路由、工具边界、证据和安全输出没有回归。

## 范围

### 做什么

- 修正 mock 模式下 DB、Server、Log、Knowledge Agent 的角色语义，使其只调用当前角色已获准的工具，并产出与角色和场景匹配的结果。
- 为单领域、跨领域、知识检索、无匹配、工具不可用和工具拒绝等现有路径建立确定性评测基线。
- 让 mock 下的冲突检查、Debate、Reflection 等质量节点根据实际前置条件产生可复现结果；未触发或无法执行时如实标为未执行或不可用，不得无条件伪装为通过。
- 修复现有 Server 工具中的假数据降级：真实采集依赖不可用或采集失败时返回明确的不可用状态；只有明确处于 mock 场景时才允许返回标注清楚的确定性场景数据。
- 对公开 Trace、诊断结果和错误投影补充回归约束，确保只展示角色、阶段、状态、耗时、工具类别与脱敏证据摘要。
- 在交付时同步更新 `docs/完善清单.md` P0-3、P1-2 和 `docs/跑通验证.md` C3 的状态与验证证据。

### 不做什么（明确排除）

- 不进入 P9，不新增 Redis Agent、领域 Tool、Connector、服务类型或真实外部数据源。
- 不改变现有 real 模式的路由策略、Agent 顺序或跨 Agent 编排语义；不把 Knowledge Agent 加入现有 chain 顺序。
- 不接线或重设计 `judge_llm`，不新增独立裁判模型调用，不改变模型 Provider 或调用策略。
- 不从报告正文推导新的结构化字段，不补造 `recommendations`，不改变诊断结果的事实来源。
- 不实现或启用长期记忆、RAG、向量检索、MCP 或任意文件系统访问。
- 不新增公开 API，不新增数据库字段或迁移，不改变会话、Run、Trace 和结果的既有公开字段契约。
- 不新增任意 SQL、Shell、DDL、DML、网络访问或高风险动作能力。
- 不以 Prompt 调优后的主观观感代替确定性验收，不把一次真实外部环境验证作为唯一评测基线。

## 功能需求

### 1. 角色与工具边界一致

- **输入**：mock 模式下由 Coordinator 分派给任一现有领域 Agent 的调查任务，以及该 Agent 当前获准的工具集合。
- **行为**：每个领域 Agent 只能选择自身获准的工具；不属于当前 Agent 的工具不得被请求。跨领域调查中的每个参与 Agent 仍独立遵守自己的工具边界，某一角色没有适用工具时应返回无适用工具或无证据状态。
- **输出**：按角色归属的工具调用记录、脱敏证据摘要和领域结论；不存在跨角色假调用。

### 2. mock 场景结果与证据一致

- **输入**：明确的 mock 场景、用户问题和服务上下文。
- **行为**：路由、参与角色、工具调用顺序、证据类别和结论必须与场景事实一致。DB、Server、Log、Knowledge 的输出应可区分，不得复用与当前角色无关的固定数据库结论。场景未提供某项事实时，应返回未知、无证据或不可用，不得自行补造。
- **输出**：可复现的角色化模拟调查结果，并能从结论追溯到对应的模拟证据。

### 3. 质量节点如实运行

- **输入**：单 Agent 或多 Agent 产生的领域结论与可用证据。
- **行为**：只有满足既有触发条件时，冲突检查、Debate、Reflection 才进入执行；进入执行后必须基于本次场景的结论与证据产生确定性结果，不得无条件判定“无冲突”或“审核通过”。未触发、缺少前置证据或执行失败时，应如实表达未执行、不可用或失败，不得伪装成成功完成。
- **输出**：与实际执行状态一致的安全 Trace 和最终报告状态；不得暴露内部推理过程。

### 4. 数据源不可用时诚实降级

- **输入**：real 模式下现有 Agent 工具所依赖的采集库缺失、数据源未配置、连接失败、超时或采集异常。
- **行为**：返回明确且中性的未配置、不可用、超时或失败状态；不得返回固定指标、模拟证据或看似真实的健康结论。mock 场景数据与 real 采集结果必须保持语义隔离。
- **输出**：安全的降级状态和必要的用户可理解说明，不包含原始异常、连接细节或凭据。

### 5. Agent 行为评测基线

- **输入**：无需真实外部服务即可运行的确定性场景集合。
- **行为**：评测至少覆盖 DB、Server、Log、Knowledge 四个单领域场景，一个跨领域协作场景，一个无匹配或无适用工具场景，以及一个工具拒绝或不可用场景；现有 direct、chain、parallel 三种路由策略均至少有一个确定性场景覆盖。评测逐项核验路由结果、参与角色、工具边界、证据归属、质量节点状态、最终输出和安全投影。相同场景重复执行时，除运行 ID、时间和耗时外的关键行为应保持一致。
- **输出**：机器可判定的通过或失败结果；任一跨角色工具调用、伪造数据、无条件质量通过或敏感信息暴露都必须使评测失败。

### 6. 公开输出安全

- **输入**：Agent 运行产生的工具调用、内部状态、异常、证据与报告。
- **行为**：公开 Trace 和结果只保留角色、阶段、状态、耗时、工具类别及脱敏证据摘要；模型思考过程、系统 Prompt、工具实参、原始工具输出、原始异常、原始 SQL、文件路径和凭据不得进入公开输出。内部执行失败应映射为安全、可理解的状态。
- **输出**：符合既有公开契约的安全 Trace 与诊断结果。

## 非功能需求

- **确定性**：同一 mock 场景在相同配置下重复运行，关键路由、工具选择、证据类别、质量状态和结论语义一致；不以时间、随机数或外部网络决定结果。
- **安全**：不扩大任何 Agent、Tool 或 Connector 权限；公开输出继续满足脱敏、最小披露和无 CoT 要求。
- **诚实性**：mock 数据必须可识别为模拟场景；real 数据不可用时不得回退为未标注的模拟值。
- **可靠性**：单个 Agent、工具或质量节点失败时应受控降级，不得导致其他 Run 状态污染或留下虚假成功状态。
- **可维护性**：评测失败应能定位到路由、角色、工具、证据、质量节点或公开投影中的具体一类，不只比较整段报告文本。

## 数据与接口影响

- 数据：无新增持久化，无数据库迁移；不得写入真实外部服务。
- 接口：无新增公开 API，既有会话、Run、Trace 和结果字段契约不变；仅修正现有字段所表达的事实与状态。

## 验收标准

- [ ] AC1: 当 mock 数据库场景触发 DB Agent 时，应只调用 DB Agent 获准的工具，并产出可追溯到数据库模拟证据的结论。
- [ ] AC2: 当 mock 主机、日志或知识场景分别触发 Server、Log、Knowledge Agent 时，各 Agent 应只调用自身获准的工具，且不得请求数据库工具或返回固定数据库结论。
- [ ] AC3: 当跨领域场景触发多个 Agent 时，每个 Agent 应独立遵守工具边界，最终结果中的证据应能区分角色与来源。
- [ ] AC4: 当某个 Agent 没有适用工具或场景没有对应事实时，应返回无适用工具、无证据或未知状态，不得补造工具调用、指标或结论。
- [ ] AC5: 当 mock 场景满足冲突检查、Debate 或 Reflection 的既有触发条件时，对应节点应基于本次结论和证据产生可复现结果，不得无条件通过。
- [ ] AC6: 当质量节点未满足触发条件、缺少前置证据或执行失败时，公开状态应如实表示未执行、不可用或失败，不得显示为已成功复核。
- [ ] AC7: 当 real 模式下主机采集依赖不可用或采集失败时，应返回不可用状态，不得返回固定 CPU、内存、磁盘、进程或网络数值。
- [ ] AC8: 当同一 mock 场景连续运行至少两次时，剔除运行 ID、时间和耗时后，路由、参与角色、工具类别、脱敏证据、质量节点状态和最终公开结果组成的评测快照应完全一致。
- [ ] AC9: 当评测场景发生跨角色工具调用、未标注模拟值、伪造成功状态或证据与结论不一致时，评测应失败并指出对应行为类别。
- [ ] AC10: 当查看任一评测 Run 的公开 Trace 与结果时，不得出现模型思考过程、系统 Prompt、工具实参、原始工具输出、原始异常、原始 SQL、受管目录路径、DSN、API Key 或其他凭据。
- [ ] AC11: 当执行既有数据库真实工具、知识检索、主机指标和 ToolGateway 相关回归测试时，应全部通过；real 模式既有受控访问与权限边界不变。
- [ ] AC12: 当交付本需求时，`docs/完善清单.md` P0-3、P1-2 与 `docs/跑通验证.md` C3 应按实测结果同步状态和验证证据，不得仅因代码完成标为已修复。
- [ ] AC13: 当检查本需求的数据与接口变更时，应确认没有新增公开 API、数据库迁移、Connector、真实外部访问或高风险动作能力。

## 边界与约束

- 安全边界：所有工具继续通过既有受控注册、参数校验、超时、脱敏和审计边界；模型不得获得任意 SQL、Shell、DDL、DML、文件或网络访问能力。
- 降级策略：未配置 → 未配置；无适用事实 → 无证据或未知；采集失败或超时 → 不可用或失败；质量节点未触发 → 未执行。任何降级均不得用固定假值代替。
- 兼容性：既有公开 API 与持久化结构不变；real 模式现有路由和编排顺序不变；现有 mock 场景允许修正失真行为，但必须保持确定性和可离线运行。
- 工程闸门：本 PRD 会修正 mock 下的多 Agent 与质量节点行为，实施前须经 `arch-design` 明确场景契约、状态语义和回归边界，再经 Review 与用户确认。
