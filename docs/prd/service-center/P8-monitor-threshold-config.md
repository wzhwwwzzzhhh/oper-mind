# 监控阈值与关注项配置——采样点异常判定规则可调 · PRD

## 背景

服务中心负责服务接入、服务状态、监控和调查入口（`docs/产品定义.md` §2.3/§4）。监控已有只读快照 + 定时采样历史 + 概览聚合（`GET /services/{id}/monitor/history`、`GET /monitor/overview`，P5/P6/P7 已交付）。但**"采样点异常"的判定规则写死在后端**，用户不能调（`docs/接口清单.md` 第二大模块"缺少"表："监控阈值 / 关注项配置：「采样点异常」的判定规则写死在后端，用户不能调。❌ 欠账"）。

现状：`backend/src/application/monitoring.py` 的 `_trend_summary()` 硬编码了异常判定——Redis 看 `slowlog_count > 0`，PG 看 `slow_query_count > 0 or timeout_count > 0`，另加"可用性状态变化"计为异常采样点；阈值、关注项（哪些指标算异常）、判定窗口均不可配置。P8 服务注册 PRD（`docs/prd/service-center/P8-service-registration.md`）明确把"运行时可编辑的监控阈值/关注项配置"排除在外（"接口清单欠账，另行排期"），本 PRD 即该欠账的落地。

关联：`docs/接口清单.md`（第二大模块缺表）、`docs/prd/service-center/P8-service-registration.md`（#53，明确排除本项）、`docs/prd/monitor/P5-monitor-trends.md` / `P7-monitoring-overview-page.md`（趋势/概览已交付）、`docs/产品定义.md` §5（监控必须区分快照/历史/不可用，不得伪造实时性）、`docs/开发规范.md` §5（监控语义）。

## 目标

1. 运维能为服务**配置监控关注项与阈值**：哪些指标视为异常（慢查询/超时/Redis 慢日志），阈值多少，判定窗口多长。
2. 配置**持久化**（应用库），重启不丢；未配置时沿用既有内置默认判定（行为不变）。
3. 配置对**既有只读监控链路生效**：`GET /services/{id}/monitor/history` 与 `GET /monitor/overview` 的异常采样点计数按配置判定，前端概览/趋势展示一致。

## 用户故事

作为运维工程师，我的 PG 实例慢查询阈值默认是"出现即异常"，太敏感，应能把它调成"窗口内出现 ≥3 条慢查询才算异常"——以便监控概览不再被个例刷屏，能真实反映需要关注的异常。

## 范围

### 做什么
- 新增阈值配置接口：`GET /services/{id}/monitor/thresholds`（读）+ `PUT /services/{id}/monitor/thresholds`（写），按服务维度配置。
- 配置项：关注指标（如慢查询计数 / 超时计数 / Redis 慢日志计数）、判定阈值（数量下限）、判定窗口（时间窗）、是否把"可用性变化"计为异常。
- 配置持久化到应用库（涉及迁移），未配置时返回/使用内置默认（与现有一致）。
- 异常判定引擎改为**读配置**：`_trend_summary` 不再硬编码，按服务配置计算异常采样点；前端趋势/概览/历史如实反映。
- 前端服务中心详情页新增"监控阈值"配置区（只读回显 + 可编辑保存），诚实展示当前生效规则（内置默认 vs 已配置）。

### 不做什么（明确排除）
- 不做**全局/跨服务**阈值（按服务维度配置；全局默认由内置默认承担，不做全局覆盖）。
- 不做告警通道/通知（页面内告警已决，`docs/接口清单.md` 告警通道刻意不做）。
- 不改变采样本身（采样间隔、保留期不动）；配置只影响"异常判定"这一层。
- 不做复杂规则引擎（阈值只做数值下限 + 窗口 + 关注指标开关，不做表达式）。
- 不暴露凭据/DSN/原始异常详情；配置接口与判定结果不含敏感连接细节。
- 不改变既有 `GET /services`、`GET /monitor/overview` 的**契约**（返回字段不变，仅异常计数的语义按配置计算）。

## 功能需求

### 1. 读取阈值配置（GET /services/{id}/monitor/thresholds）
- **输入**：服务 ID。
- **行为**：返回该服务的监控阈值配置：关注指标开关、判定阈值、判定窗口、可用性变化是否计异常；未配置时返回内置默认并如实标注"默认"。
- **输出**：阈值配置安全视图（含 `configured: bool` 或等效标注），服务不存在 → 404。

### 2. 写入阈值配置（PUT /services/{id}/monitor/thresholds）
- **输入**：服务 ID + 配置（关注指标、阈值、窗口等）。
- **行为**：校验合法性（阈值 ≥ 0、窗口合理范围、指标名受白名单约束）；合法则持久化；非法 → 422 明确错误。服务不存在 → 404。
- **输出**：保存后的配置视图（与 GET 同构），保存即生效。

### 3. 判定引擎读配置
- **输入**：服务配置（或内置默认）+ 采样样本序列。
- **行为**：按配置计算异常采样点（关注指标超过阈值计异常；是否计入可用性变化按配置），替代现有硬编码判定；未配置服务行为与现状一致。
- **输出**：`MonitorTrendSummaryData` 的 `anomaly_sample_count` 按配置计算，前端趋势/概览/历史展示一致。

### 4. 前端配置区
- **输入**：服务中心详情页。
- **行为**：展示当前生效规则（默认/已配置，诚实标注来源）；提供编辑保存；保存失败/校验失败诚实提示；空态/加载态正常。
- **输出**：可读写的监控阈值配置区，与后端配置一致。

## 非功能需求
- **安全**：配置接口只接受白名单指标与数值约束；不暴露凭据/DSN/异常详情；配置值不做任意表达式执行。
- **诚实**：未配置时明确标注"内置默认"；配置保存后如实反映"已配置"；不伪造实时性。
- **性能**：判定为内存计算（采样序列已加载），配置读取为单行查询；不引入额外采样放大。
- **可靠**：配置损坏/非法时回退内置默认并如实标注；配置不影响采样写入。
- **兼容性**：未配置服务行为与现状完全一致；既有接口契约字段不变。

## 数据与接口影响
- 数据：新增阈值配置持久化（应用库表或键值，Design 定），涉及数据库迁移；未配置不产生记录。
- 接口：新增 `GET/PUT /services/{id}/monitor/thresholds`；既有 `GET /services/{id}/monitor/history`、`GET /monitor/overview` 契约不变（异常计数语义按配置计算）。

## 验收标准
- [ ] AC1: 当 GET 读取未配置服务的阈值时，应返回内置默认值并如实标注"默认"。
- [ ] AC2: 当 PUT 保存合法阈值配置时，应返回保存后的配置视图，且 GET 可读回一致值。
- [ ] AC3: 当 PUT 提交非法配置（阈值 < 0 / 未知指标 / 窗口越界）时，应返回 422 明确错误，不落库。
- [ ] AC4: 当请求不存在的服务阈值时，应返回 404。
- [ ] AC5: 当服务配置了阈值后，`GET /services/{id}/monitor/history` 与 `GET /monitor/overview` 的异常采样点计数应按配置计算。
- [ ] AC6: 当服务未配置时，异常采样点计数应与配置前一致（内置默认行为不变）。
- [ ] AC7: 当配置持久化后重启进程，应能读回同一配置（重启不丢）。
- [ ] AC8: 配置接口与响应不得包含凭据、DSN、`sk-` 或原始异常详情。
- [ ] AC9: 前端详情页应展示当前生效规则（默认/已配置，诚实标注），支持编辑保存，失败/校验错误诚实提示。
- [ ] AC10: 回归 —— 既有 `test_monitor_*` / `test_service_center` 相关全绿；前端 `typecheck`/`test`/`build` 通过。

## 边界与约束
- 安全边界：白名单指标、数值约束、无表达式执行；只读默认；配置不触碰采样与凭据。
- 降级策略：未配置 → 内置默认；配置损坏 → 回退默认并标注；服务不存在 → 404。
- 兼容性：未配置行为不变；既有监控接口契约不变；mock 采样不受影响。

## 开放问题
1. **配置粒度**：按服务维度（推荐）还是按"服务类型 + 服务"两级？推荐按服务，Design 定。
2. **指标白名单**：首版支持哪些指标？推荐与现有 `_trend_summary` 对齐（slow_query_count / timeout_count / Redis slowlog_count / 可用性变化开关），Design 定。
3. **窗口语义**：判定窗口如何定义（如"窗口内计数阈值" vs "连续 N 个采样点"）？推荐"时间窗内计数 ≥ 阈值"，Design 定。
4. **默认值暴露**：内置默认是否在 GET 未配置时完整暴露？推荐暴露并标注"默认"，便于前端如实展示。
