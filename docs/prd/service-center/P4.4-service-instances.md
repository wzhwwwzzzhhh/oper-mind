# 服务中心多服务实例接入 · PRD

## 背景
P4 已把服务中心从「空 ServiceRegistry」变真为「1 个 PostgreSQL 只读实例」（`postgres-production`），
快照/健康检查/只读连接已跑通。但实例是**代码内写死**的：`dependencies.py` 里
`ServiceRegistry((PostgresServiceConnector(load_service_settings().pg_dsn),))` 固定单实例，
凭据只用单一 `OPERMIND_PG_DSN` 环境变量。

运维接入第二个数据库实例（如 `postgres-staging`）需要改代码 + 新增第二个 DSN 环境变量，
且 `load_service_settings()` 只返回一个 `pg_dsn`，无法表达多实例。服务接入能力（多实例、
能力声明）尚未真正落地——这是路线图第二阶段服务中心的明确缺口。

关联：`docs/design/service-center/P4.4服务中心接入与凭据Design.md`（已确认：凭据方案 A = 环境变量命名空间化、
配置驱动、首版只 PG 多实例）、`docs/路线图.md`（第二阶段"服务中心：接入、连接状态与能力声明"）、
`docs/design/service-center/P4服务中心变真Design.md`（P4 单实例已确认方案）。

## 目标
1. 服务中心支持**多个 PostgreSQL 实例**接入，各自有独立身份、能力声明、连接状态。
2. 凭据只用**环境变量命名空间化**（`OPERMIND_SERVICE_<INSTANCE_ID>_DSN`），零落库。
3. 复用 P4 已验证的只读快照/连接测试/降级机制，不重复造。

## 用户故事
作为运维工程师，我需要接入第二个 PostgreSQL 数据库实例（staging / production 分开），
在服务中心看到每个实例各自的状态，而不是代码里写死一个——以便按实例做只读调查，互不串扰。

## 范围

### 做什么
- 服务实例从代码内写死改为**配置/元数据驱动**（多实例，PG 优先）。
- 凭据方案：环境变量命名空间化，每实例一个 DSN env，缺省显示 not_configured。
- 复用 `ServiceDefinitionData` / `ServiceSnapshotData` / `ServiceConnector` 协议，多实例各一份。
- 连接测试复用 P4 `health_snapshot()`（连通性 + 有限指标）。
- 前端服务中心列表/详情页自动展示多实例，复用既有接口契约。

### 不做什么（明确排除）
- 不新增 MySQL / Redis 真实 Connector（框架预留，本阶段只做 PG 多实例）。
- 不做运行时动态增删实例的完整 CRUD（首版配置驱动，重启生效）。
- 不做凭据编辑表单/UI 保存（首版凭据只走环境变量）。
- 不做历史监控趋势 / 告警（P6+）。
- 不引入 DML/DDL/写操作（纯只读）。
- 不做方案 B（加密落库）——已确认后续阶段，需单独批准放宽"不落库"硬规则。

## 功能需求

### 1. 多实例注册（配置驱动）
- **输入**：代码/配置声明的实例 id 列表（如 `postgres-production`、`postgres-staging`）。
- **行为**：按类型模板（PostgreSQL）+ 实例 id 派生各实例的只读 Connector，注册进 `ServiceRegistry`；
  实例 id 唯一校验保留。
- **输出**：多实例注册的服务注册表。

### 2. 凭据命名空间化（环境变量）
- **输入**：实例 id 对应环境变量 `OPERMIND_SERVICE_<INSTANCE_ID>_DSN`。
- **行为**：Connector 构造时解析对应实例的 DSN env；缺省 → 该实例 `not_configured`。
  凭据绝不进入日志/Trace/结果/前端/应用库。
- **输出**：各实例按各自 env 配置的只读连接；未配置实例诚实降级。

### 3. 连接测试与快照（复用 P4）
- **输入**：对指定实例发起健康检查。
- **行为**：复用 P4 `health_snapshot()` 只读机制（`SELECT 1` + 有限指标 + 3s 超时 + 只读事务）；
  各实例独立快照，互不串扰。
- **输出**：各实例的 `ServiceSnapshotData`（healthy/unhealthy/unavailable/not_configured）。

### 4. 前端多实例展示
- **输入**：服务中心列表页 / 详情页挂载。
- **行为**：从 `GET /services` 读取多实例并展示，各自状态正确；未配置实例显示"未配置"空态。
- **输出**：多实例服务中心界面，复用既有接口契约。

## 非功能需求
- **安全**：凭据只走环境变量；脱敏硬约束；无凭据/DSN/env 名进日志、Trace、结果、前端、应用库。
- **可靠**：各实例独立降级，一个实例不可用不影响其他实例。
- **诚实**：未配置实例显示 not_configured 空态，不伪造。
- **性能**：复用 P4 快照限时机制（3s），不阻塞。

## 数据与接口影响
- 数据：无新增持久化，无数据库迁移（实例元数据代码/配置驱动，凭据在环境变量）。
- 接口：`GET /services`、`GET /services/{id}`、`/services/{id}/activities` 结构不变；
  返回值数量随多实例增加。无新增公开接口。

## 验收标准
- [ ] AC1: 当声明 `postgres-production` 与 `postgres-staging` 两个实例时，`GET /services` 应返回两个服务，各自 id 正确。
- [ ] AC2: 当某实例未设置对应 `OPERMIND_SERVICE_<ID>_DSN` env 时，该实例应返回 `availability=not_configured`，不崩溃、不伪造。
- [ ] AC3: 当某实例 DSN 连接失败/超时（假连接抛 OperationalError）时，该实例应返回 `availability=unavailable`，不把异常详情外泄。
- [ ] AC4: 两个实例应各自读取各自的 env，互不串扰（一个实例的 DSN 不泄漏到另一个实例）。
- [ ] AC5: 多实例注册表应保持实例 id 唯一；重复 id 应被拒绝。
- [ ] AC6: 快照/列表/详情响应中不得出现 DSN 明文、`OPERMIND_SERVICE_` env 名、密码或 `sk-` 内容。
- [ ] AC7: 前端服务中心列表应展示多实例，各自状态正确；未配置实例显示"未配置"。
- [ ] AC8: 连接测试复用 `health_snapshot()`，不新增独立测试接口。
- [ ] AC9: 回归 —— `test_p4_service_center.py`、`test_postgres_connector.py`、`test_agent_gateway.py`、`test_tool_gateway.py` 全绿。
- [ ] AC10: 前端 `typecheck` / `test` / `build` 通过（若涉及前端改动）。

## 边界与约束
- 安全边界：纯只读，无写路径；凭据只走环境变量；无凭据/env 名进日志、Trace、结果、前端、应用库。
- 降级策略：未配置 → not_configured；连接失败/超时 → unavailable；各实例独立，互不拖累。
- 兼容性：mock 模式行为不变；既有接口契约不变；MySQL/Redis 框架预留，不实现 Connector。
