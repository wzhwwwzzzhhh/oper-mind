# OperMind 产品定义

> 事实源。更新：2026-10-26（文档清洗：结构与表述重写，事实与边界不变）。
> 配套：阶段见 `路线图.md`，架构约束见 `架构与开发路径.md`，工程规则见 `开发规范.md`。

## 1. 产品是什么

OperMind 是一个面向研发与运维人员的**会话式多 Agent DevOps Copilot**。

用户像使用 DeepSeek 一样，在会话里提问、追问、下达受控指令。系统结合已接入的服务、监控数据、受控工具和多个 Agent，完成调查、给出建议；高风险动作经审批后执行并验证。

产品默认进入会话工作台。会话、服务上下文、证据、审批和执行结果都在这里呈现。

## 2. 目标形态：V2 替换 V1

- **V1（过渡基线）**：运维调查与受控动作。已有 PostgreSQL、MySQL、Redis 只读接入、监控、知识检索、模型设置和审批执行链路。V1 是 V2 达到能力对等前的过渡实现，不是并行的长期产品。
- **V2（目标形态）**：主 Agent 用 ReAct 循环执行；所有外部能力收口到一份 Capability 契约，内部装 Skill、Tool 或 Workflow。目标是把底座做成可换业务的平台；具体业务尚未选定。

V1 和 V2 共用同一套会话、Run、工具网关、安全事件和 Trace，不复制产品控制面。当前运行链默认走 V1；V2 入口为显式切换。迁移顺序是：V2 完成能力对等并通过验收后，V1 调查入口与 Coordinator 路径逐步下线，会话主入口切到 V2。

V2 的能力分两类：知识型（只装 Skill，不调用外部工具）和执行型（装 Tool/Workflow，经网关访问资源）。首切片只批准了一个验证性执行型能力：**显式文本字面比较**（`text.literal_compare@1`）。它不接业务服务、不判断语义。

V2 有两条轴：

- **执行轴**：直答 → 知识型能力 → 执行型能力 → ReAct 多轮。
- **协作轴**：单主 Agent → 子 Agent 委派（上下文隔离、长任务）→ 多主 Agent 协作（业务独立）。

四种组合分别属于这两条轴：

| 形态 | 所属轴 | 用途 |
|---|---|---|
| 单主 Agent | 执行轴的基础形态 | 基于会话上下文完成任务 |
| 主 Agent + 能力包 | 执行轴 | 装配知识或执行受控能力 |
| 主 Agent + 子 Agent | 协作轴 | 委派边界明确的子任务，隔离上下文 |
| 主 Agent ↔ 主 Agent | 协作轴 | 多个独立业务主体协作 |

这四种是同一底座的组合方式，不是四套运行时，也不是能力等级。任务复杂度决定是否派子 Agent；业务独立性决定是否用多个主 Agent。子 Agent 与多主 Agent 都不默认启用。

## 3. 用户看到的产品

### 3.1 会话工作台（主入口）

用户可以在会话中：

- 新建和管理多个会话；
- 持续追问某个服务或故障；
- 询问状态、故障原因、排查建议和受控操作；
- 选择或关联已接入的服务；
- 查看回答、证据摘要、建议、审批状态、执行结果和验证结果。

交互形态接近现代对话产品：左侧会话列表，中间对话区，按需展示服务上下文和可展开详情。

### 3.2 服务中心

服务中心负责服务接入、状态和监控：

- 支持 PostgreSQL、MySQL、Redis 等服务类型；
- 展示服务身份、类型、连接状态和权限边界；
- 提供每个服务的监控/状态页面；
- 从服务页直接进入带服务上下文的调查会话；
- 保存服务相关的调查、审批、执行和验证记录。

接入表单、凭据保存、连接测试、权限模型和监控指标仍在逐步定稿，属于设计范围，不能临时拼接。

### 3.3 过程视图（Trace）

前端展示用户能理解的简要过程：

```text
问题理解 → 角色分工 → 受控读取 → 证据汇总 → 结论 / 提案 / 验证
```

每一步显示角色、阶段、状态、耗时、工具类别和脱敏证据摘要。展开内容是可审计的依据，不包含模型推理链、Prompt、原始异常、原始日志、原始 SQL 或凭据。

## 4. 主链路

```text
用户会话
→ 理解问题与服务上下文
→ 多 Agent 分工
→ 受控 Tool / Connector 读取事实
→ 结构化结论与证据摘要
→ 高风险操作提案
→ 人工审批
→ 白名单执行
→ 执行后验证
→ 会话与服务页留痕
```

审批与执行只在满足白名单和审批条件时发生，不是每次回答的必经步骤。

慢查询处理是这条链路的第一个技术切片。服务模型扩展后，它成为其中一项能力，不再决定产品边界。

V2 沿用同一条主脊：主 Agent 选择普通回答、材料追问或已注册能力；纯计算工具不接外部 Connector，结果为结构化交付。新业务仍需要自己的数据语义、权限、工具和验收。

## 5. 模块边界

| 模块 | 责任 |
|---|---|
| 会话工作台 | 会话、消息、服务上下文、回答、简要 Trace、证据、审批和执行反馈 |
| 服务中心 | 服务注册、服务详情、连接状态、监控、服务调查入口和留痕 |
| Agent 运行层 | 协调、任务分派、状态图、结果汇总和可审计 Trace |
| Connector / Tool 层 | 对 PostgreSQL、MySQL、Redis、服务指标、日志和后续知识源进行受控访问 |
| 安全治理层 | 凭据、权限、允许资源、只读边界、审批、白名单执行、验证和审计 |
| 前后端 API | 稳定的产品契约；前端不绕过后端直连用户服务 |

## 6. 安全与诚实性边界（不可妥协）

1. 模型没有任意 SQL、Shell、DDL、DML 或网络访问能力。
2. 所有 Connector 和 Tool 由后端显式注册，并经过参数校验、超时、脱敏和权限边界。
3. 用户服务凭据不进入代码、Git、日志、Trace、接口响应、截图或前端状态。
4. 高风险动作由服务器生成提案，经人工审批、固定白名单执行和验证；模型、前端或聊天文本不能直接执行。
5. 监控页面区分当前读取、历史记录、模拟数据、不可用和未知状态，不伪造实时性或健康结论。
6. 尚未实现的服务类型、知识库、模型设置、MCP 能力或操作权限，标注为“未启用”。

## 8. 未决事项

以下事项需要先完成产品与技术设计，再写代码：

- 身份、租户、角色和审批人模型（当前无登录体系，用户信息为演示占位）；
- 超出 P12 受限只读范围的 MySQL 调查与动作能力；
- Trace 的统一事件模型、保留策略与展示粒度（当前为 Run 事件的安全投影）；
- RAG、向量检索、MCP 的产品边界与接入时机；
- 除固定联合索引重建外，还有哪些操作可被提案、审批、执行和验证；
- 长期记忆的存储与检索方案（当前 v1 链路默认关闭，见 `docs/归档/完善清单.md` P1-8）；
- 高危 SQL 审批是否重新设计并接入 ToolGateway 执行链（旧的 CLI 审批死代码已删除）。
