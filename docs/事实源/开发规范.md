# OperMind 开发规范

> 事实源。更新：2026-10-26（文档清洗：规则归类重写，约束不变）。

## 1. 通用工程规则

- 中文注释、文档和用户可见日志；公开函数必须有类型标注。
- 跨层数据使用 Pydantic 或 TypedDict；禁止裸 `except`、新增生产 `print` 和隐式跨层字典协议。
- 前端和后端都是正式产品代码：API 契约明确、错误可安全展示、状态可恢复、测试覆盖关键用户路径。
- 一个工作包包含 1–3 个紧密切片；完成后集中 Test → Review → Commit。
- 以下改动必须先 Design → Review → 用户确认：架构、公开 API、数据库迁移、Connector、外部连接、凭据、监控、权限、审批/执行安全、破坏性改动。
- 不直推 `main`；commit 使用 `<类型>: <中文描述>`；只暂存指定文件，禁止 `git add .`。

## 2. 会话、Agent 与 Trace

- 会话是产品主入口。服务上下文、消息、调查、提案和执行结果必须能安全关联和恢复。
- LLM Agent 继承 `BaseAgent`，复用约定运行接口；Tool 继承 `Tool`，实现受控 `execute`；状态图使用显式状态模型。
- 确定性 Connector / Collector 通过显式 Application port 或 Executor 注入，返回结构化事实，不做成可任意调用的 Agent。
- 前端 Trace 只展示角色、阶段、状态、耗时、工具类别和脱敏证据摘要；不展示 CoT、系统 Prompt、原始工具输出、原始异常或凭据。
- V1 领域 mock Agent 从互斥角色工具白名单和显式冻结场景事实生成行为；空、未知或混合工具菜单失败关闭；缺少事实时返回未知/无证据，不读取场景外数据或补造指标。
- V2 主 Agent 使用独立的显式决策场景，不放宽 V1 菜单，不用关键词冒充模型判断。
- V2 主 Agent 的目标执行内核是 ReAct 循环：模型决策、受控工具、观察结果、再决策；步数、工具调用数、超时和预算由程序限制。首切片的有界决策图是过渡实现，不扩展成第二套长期内核。
- V2 的语义选择（意图理解、能力选择、任务分派）使用一次可校验的结构化模型决策。注册、资源归属、格式、预算、状态和已确定流程由程序验证。正则可用于格式/凭据识别，不能代替语义路由。
- 同一 Run 有一个事实 writer。`runtime_kind` 只区分执行形态，不授权新资源，也不另造会话/Run 控制面。纯计算 Tool 可以没有 Connector；外部访问仍必须经过批准的 Connector/Tool 接缝。
- 用户显式提供的非敏感原文和合法引文只进入对应输入/结果区域，不进入 Trace、日志、审计或 usage。凭据在接纳前拒绝；不能静默改写后声称字面一致。
- Tool 的结构化 `unavailable`、质量节点的 `skipped/attention/error` 原样穿过 Gateway、Run 事件和 Trace 投影；未执行、不可用或失败不渲染为成功。
- Debate 只在有来源的结论存在实质根因冲突时执行；Reflection 检查证据前置条件，不在 mock 下无条件通过。Agent 行为变更需要确定性双跑快照和至少一个能被分类门禁捕获的负向样例。

## 3. 服务与 Connector

- 前端不直接连接 PostgreSQL、MySQL、Redis、日志系统或任何用户服务；所有访问经后端 Connector/Tool。
- 每种服务类型明确身份、允许资源、只读能力、超时、参数化方式、脱敏规则、mock 策略、监控语义和错误映射。
- 未经 Design/Review/用户确认的 Connector、端口、协议、服务类型和真实资源不接入。
- 已有技术切片可以保留和复用；其硬编码限制不阻止正式多服务模型的设计。

## 4. 凭据、隐私与隔离

- 凭据只能从当前进程环境或经批准的安全密钥引用取得；不写入仓库、文档、日志、数据库普通字段、事件、Trace、结果、截图或 Git。
- API 和 UI 不返回密码、连接串、原始 host/port 等敏感连接细节；未来 Design 明确展示要求和脱敏规则时除外。
- 所有服务访问有服务级隔离、权限校验和目标边界；不为诊断或监控枚举、探测或访问未授权资源。
- 应用元数据、用户服务数据和测试/演示资源相互隔离；清理动作只清理专用项目资源，不删除用户数据库或服务。

## 5. 调查、行动与监控

- 默认调查只读、参数化、限时、可审计、可 mock；模型不能自由生成并执行 SQL、Shell、DDL、DML 或网络命令。
- 高风险动作由服务器生成受控提案，经人工审批、严格白名单执行和独立验证；禁止自动批准、通用执行器和聊天文本直接执行。
- 监控区分当前快照、历史记录、模拟数据、不可用与未知；一次读取不伪装成长期实时监控，历史验证不伪装成当前健康。
- 未实现能力如实标注“未启用”。

## 6. 测试与提交

- 每个新增关键路径有后端单元/API 测试和前端交互测试；迁移验证 upgrade/downgrade 与约束。
- 真实外部依赖提供确定性 mock；mock 不冒充真实执行或真实监控。
- 真实资源测试只在用户明确授权、边界校验通过后运行；凭据不进入测试输出或 Git。
- 提交前运行相关测试和 `git diff --check`，检查暂存范围和敏感字面量；不提交 `.env`、`*.local.yaml`、凭据或 `sk-` 内容。

## 7. 完善类改动的轻流程

V1 的体验完善采用轻流程，工作地图归档在 `docs/归档/完善清单.md`；V2 新能力按其 PRD、Design 和 Workpack 实施。

满足全部条件才算完善类：不新增公开 API、数据库迁移、Connector 或服务类型；不扩大执行/审批能力；不新增真实外部连接；不改变产品对用户的能力承诺。

典型范围：修 bug、接线已有路由与按钮、补渲染已返回字段、删除死代码、更新过时注释、把假数据改为诚实降级、UI 打磨。

流程：认领清单条目 → worktree 开发 → 相关测试 + 前端 `typecheck`/`test`/`build` → 回写状态与验证方式 → PR。

触及以下任一项时，即使登记在完善清单里，也先出 Design 并完成 Review 与用户确认：

- 审批与执行边界（如高危 SQL 是否接入 ToolGateway 执行链）；
- 结构化结果的事实来源变更（如 assembler 是否从报告正文提炼结构化字段）；
- 记忆、检索、向量或 MCP 相关方案；
- 多 Agent 编排语义变更（如 knowledge 是否进 chain 顺序）；
- 页面从“展示”变为“控制后端行为”（如模型设置页开关接后端装配）。

清单状态只有三种：`—` 未修、`⏳` 在修或部分修、`✅` 已修复。标 `✅` 必须同时写日期与验证方式；代码改完但端到端未复验的，标 `⏳`。修复涉及 `docs/归档/跑通验证.md` 的卡点时同步更新，不留两处矛盾记录。

## 8. 并行开发与合并冲突处理

多个 issue 同时开工时，开发阶段可全并行（worktree 隔离）；冲突只在合并回 `main` 时出现，按本节处理。

### 8.1 共享文件冲突

以下文件几乎每个 issue 都会改，冲突是追加式文本冲突，合并时逐段保留两边：

| 文件 | 每个 issue 的改法 | 冲突特征 |
|---|---|---|
| `backend/src/api/v1/routes.py` | 追加路由 | 追加式，冲突点少 |
| `backend/src/api/v1/schemas.py` | 追加资源/请求 schema | 追加式 |
| `frontend/src/api/v1/client.ts` | 追加调用函数 | 追加式 |
| `frontend/src/api/v1/queries.ts` | 追加 query 键 | 追加式 |
| `frontend/src/test/handlers.ts` | 追加 mock | 追加式 |

### 8.2 `generated.ts` 不手解

`frontend/src/api/v1/generated.ts` 是 `npm run generate:api` 的生成产物，禁止手工编辑。合并冲突时任选一边后重新生成覆盖，不在冲突标记里手拼。生成方式见 `CLAUDE.md` 常用命令。

### 8.3 迁移链串行

alembic 是单链（`backend/migrations/versions/*.py` 的 `down_revision` 顺序）。多个带迁移的 issue 并行时，迁移文件按合并顺序排队：

1. 第一个带迁移的 PR 直接合；
2. 后续每个带迁移的 PR 在合并 `main` 后，把新迁移的 `down_revision` 指向最新 head（rebase 或手动改）再合；
3. 或全部合完后用 `alembic merge` 生成合并迁移，收口多个 head；
4. 禁止多个分支基于同一旧 head 各自建迁移直接合入。

判定：新增表、新增列、改约束 = 带迁移；纯接口新增 = 无迁移，可随时合。

### 8.4 合前检查

- push 前 `git fetch origin main && git merge origin/main`（或 rebase），在本地解冲突；
- `generated.ts` 冲突重新生成；
- 解完冲突重跑相关测试（后端 `pytest`、前端 `typecheck`/`test`/`build`）；
- 用 `git diff origin/main...HEAD --name-only` 确认 PR diff 只含本工作包文件；
- `git diff --check` 干净后 push / 建 PR。

### 8.5 分组与合并顺序

- 无迁移的 issue 与有迁移的 issue 可以同时开工；
- 合并时，无迁移的随时合，有迁移的按 8.3 排队；
- 前端页面互不重叠，共享文件按 8.1 处理。
