## 2. 产品方向

### 2.1 V1：运维调查与受控动作

用户在主入口会话中提问、追问、下达受控指令。系统在已授权服务范围内，由多 Agent 协作调查，给出结论、证据、简要 Trace，以及必要时的审批、执行和验证反馈。

慢查询是穿越产品全链路的第一个简单验证问题，不是产品边界。

### 2.2 V2：一契约 + 两轴

V2 是目标形态，替换 V1。目标是把底座做成可换业务的平台：主 Agent 承担任务，所有外部能力收口到一份 Capability 契约，子 Agent 和独立主 Agent 作为复杂场景的选项。具体业务尚未选定。

- **一个契约**：Capability 是主 Agent 唯一看到的能力单元，声明输入、输出、版本、资源、权限和失败语义；内部装 Skill、Tool 或 Workflow。知识型能力只装 Skill；执行型能力装 Tool/Workflow。
- **执行轴**：直答 → 知识型能力 → 执行型能力 → ReAct 多轮。主 Agent 的正式执行内核是 ReAct 循环，受步数、工具调用数、超时和预算限制。首闭环的一次性决策图只用于验证 Run 接缝，不是目标形态。
- **协作轴**：子 Agent 委派解决上下文隔离与长任务；多主 Agent 协作解决业务独立性。两者平行，不默认启用。

四种组合（单主 Agent / 主 Agent + 能力包 / 主 Agent + 子 Agent / 主 Agent ↔ 主 Agent）分别属于这两条轴，不是能力等级。

### 2.3 V2 的平台化方向

2026-09-13 确认、现已收敛为 V2 的方向：产品内核从“路由 + 窄专家”转为“单主 Agent 默认执行”——主 Agent 通过 ReAct 循环感知问题、调用受控工具、观察结果、继续判断并回答，Trace 全程可见。领域包以工具/知识挂载进主 Agent 工具面；独立子 Agent 仅在深域长查、强隔离、并行调查时启用。

框架策略沿用 P9 结论：控制面自研，运行时为可替换 Adapter（LangGraph 为首个），能力件按需借用。

当时引用的 `MainAgent执行形态决策Design.md` 未落盘，不作为实施锚点。正式方案以 V2 计划骨架和首闭环 PRD/Design 为准。

## 4. V2 推进顺序

以下为建议阶段，不分配 P 编号，不代表已批准实施队列。每阶段进入前仍须 Design → Review → 用户确认。

| 阶段 | 结果 | 状态 |
|---|---|---|
| V2-0 首闭环收口 | 三项遗留已裁决；实现与验证完成 | 已合入（#135） |
| V2-1 单主 Agent 地基 | Capability 契约 + 注册表 + ReAct 内核 + 知识型能力；`text_compare` 迁移为回归样本 | 未开始 |
| V2-2 执行型能力与插件性 | 至少两个不同领域的执行型能力复用现有 Connector/工具；加能力不改内核；首批高频只读调查达到 V1 对等，未覆盖项列明 | 未开始 |
| V2-3 子 Agent 委派 | 复杂/长任务按需隔离上下文；父子关联、取消、超时、成本与失败传播可用 | 未开始 |
| V2-4 多主 Agent 协作 | 独立业务主 Agent 按需协作，复用同一 Capability 注册表 | 未开始 |
| V2-5 业务深化 | 选定业务后补数据源、结果表现与评测；不属于平台阶段 | 未开始 |

首闭环只做主 Agent 的直答、材料追问和显式文本字面比较（`text.literal_compare@1`），复用同一 Run 控制面。它是 V2-0 的收口对象，不作为 V2-1 之后的执行形态。

## 6. 研发与产品边界

- 测试、mock、Trace、评测和开发脚本是研发或产品底座资产，不是用户产品的中心。
- 不以靶场、固定订单服务、旧阶段编号或演示脚本作为产品叙事。
- 每个实现工作包服务于上述阶段之一；架构、公开 API、迁移、Connector、凭据、真实服务访问、监控和高风险执行仍需先完成 Design → Review → 用户确认。
