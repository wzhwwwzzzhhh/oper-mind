# OperMind 架构与开发路径

> 事实源。更新：2026-10-26（文档清洗：删去与路线图重复的阶段历史，规则不变）。
> 配套：产品边界见 `产品定义.md`，阶段与进度见 `路线图.md`，工程规则见 `开发规范.md`。

## 一个视角：受控事实机器

OperMind 的核心是底下这台机器（聊天和多 Agent 是它对外的交互方式）：

**把人的问题变成有出处、脱敏、被治理的事实；拿到许可后，再变成被治理的动作。**

聊天和多 Agent 是产品对外的脸；工具网关是它的约束点。

判断一项改动是否跑偏，看一句话：**它是不是插在这台机器上的一个插件？** 不是，就跑题了。

## 一条主脊（产品宪法）

```text
消息 → Run → 大脑（协调 → 领域 Agent → 质检 → 报告） → 工具网关 → Connector → 证据 → 结果 → Trace
→（高风险）提案 → 审批 → 执行 → 验证 → 留痕
```

产品模块沿用 Java 参考项目的形状：会话 / 服务连接 / 监控 / 自愈审批 / 模型设置 / 知识库。所有模块挂在这一条脊上，不为每种服务复制一套 Controller/Dashboard。

## 两条硬规则

1. **一条主脊，能力即插件**：能力经显式注册和受控 Tool 接入；涉及外部资源才需要 Connector 绑定，纯计算 Tool 不造虚拟 Connector。不为每项业务复制独立的会话、Run 或控制流程。经批准的 API 契约演进可以发生；V2 的 `runtime_kind` 是同一 Run 的执行形态判别，不是第二个产品控制面。
2. **每阶段必须在前端摸得到**：能在浏览器里亲手做一件新事、看到真实结果，才算完成。后端完成而前端零变化，视为未完成。

## 不可妥协的边界

- **工具网关是最先要做对的接缝**：模型和 Agent 不直接接触 DB、Shell 或网络。网关校验权限、schema、时限和脱敏，Agent 只看到允许的工具菜单。MCP 将来只是网关下受同样策略约束的适配器。
- **智能与权力分离**：只读事实经网关流动；动作不由 LLM 执行。LLM 只能从白名单模板提议，由确定性策略引擎、人工审批、白名单执行和独立验证完成。
- **能力即诚实锁**：服务按真正接通的能力渲染；未接通显示“未启用”，Agent 那里也没有对应工具。
- **大脑薄且对基础设施无知**：Agent 只接收 AgentTask（目标、允许工具、绑定服务、已有证据），返回 findings、证据引用和安全摘要。Debate/Reflection 仅在跨域证据冲突时触发。
- **模拟运行也必须真实**：mock 只消费显式场景事实，按角色白名单决定工具调用；无事实即未知，混合菜单失败关闭。真实采集失败以结构化 `unavailable` 进入 Gateway、事件和 UI；质量节点用 `skipped/attention/error` 表达真实执行状态。
- **凭据与 Trace**：凭据明文不进入普通字段、日志或 Trace；仅按已批准的服务/模型设计保存专用加密凭据，主密钥由环境注入。Trace 是 Run 事件的安全只读投影，不含 CoT、Prompt 或原始数据。用户显式提供的非敏感原文只出现在对应输入/结果区域，不进入审计和 usage。

## 开发节奏

每阶段：半页小设计 → 用户确认 → 实现 → 用户在浏览器验证 → Test/Review → 单独提交（可回滚）。短循环，用户在环里。

## 已确认的架构决策

| 决策 | 结论 |
|---|---|
| 一个 Run 是否跨多服务 | 不跨。会话承载多服务，每服务一个 Run，前端按服务分组聚合 |
| 凭据存储 | 静态服务 DSN 可用环境变量；动态服务凭据和模型 Key 加密保存；明文不进普通字段，主密钥在环境变量 |
| 框架策略 | 控制面自研（契约、审计、审批、脱敏）；运行时是可替换 Adapter（LangGraph 为首个）；能力件按需借用 |
| Agent 执行形态 | 主 Agent 为默认执行单元；领域能力以工具/知识挂载；子 Agent 在深域长查、强隔离、并行调查时按需启用 |

## 仍待设计的事项

- MCP 接入时机与产品边界；
- 除固定联合索引重建外，每种高风险动作的白名单、审批和验证规则；
- 高危 SQL 审批是否重新设计并接入 ToolGateway 执行链；
- 长期记忆的存储与检索方案；
- 身份、租户、角色与审批人模型。
