# 产品定位复核研究 — 会话、监控与 Agent 过程的关系

> 日期：2026-07-29　|　状态：研究完成；产品决策已在 `治理-个人AI运维助手产品重定位/` 收口，仍未授权实现
>
> 研究触发：用户认为当前 P3 更像 Run/诊断技术工作台，而不像可持续使用的产品；要求先研究同类产品并拷打既有计划，不能仓促确定前端方向。

## 1. 本研究要回答的问题

OperMind 的主产品到底应以什么为用户可见的“第一对象”？当前存在三种候选：

1. **会话优先的 AI 运维助手**：用户先与 AI 持续沟通，系统按需创建 Run；
2. **监控优先的可观测性工作台**：用户从异常、服务和仪表盘进入，AI 是上下文助手；
3. **Incident 优先的协同响应工作区**：用户从事件、值班和多人协作进入，AI 是共同响应者。

本研究在形成时不假定其中任一项正确。用户随后确认“个人长期多轮会话优先、主动/监控/告警汇聚会话、Agent 渐进披露、处理受控”的 R1 方向；最终决策见 `docs/开发/治理-个人AI运维助手产品重定位/`。本研究仍不能直接转化为 UI、路由、Mock 数据或后端资源改动。

## 2. 外部产品研究摘要（官方公开资料）

研究了 Datadog Bits AI、New Relic AI、Grafana Assistant/Investigations、Dynatrace Davis CoPilot、Azure Copilot 与 Incident/ChatOps 公开资料。共同信号不是“所有产品都以聊天为首页”，而是：

- 自然语言助手承担提问、解释、追问、查询与调查入口；
- 监控、日志、Trace、告警、Incident 和权限上下文决定 AI 答复是否可信；
- 长时调查通常有明确的进度、证据、假设或报告视图，不等于把原始 Agent 步骤默认塞进对话；
- 复杂调查往往可从监控/告警/Incident 发起，也可从对话发起；
- 因此市场存在“对话入口”“上下文侧栏”“调查工作区”并存的混合形态，而不是单一固定导航。

这些产品依赖成熟的真实遥测、权限、服务目录、告警和团队协作条件。OperMind 不能复制其页面数量或品牌表面，也不能在 P4/P5 前伪造监控、Incident、审批或知识能力。

## 3. 对当前计划的肯定

当前 P0–P3 并非方向全错，已完成的底层能力是未来产品的必要条件：

- P2 将 Session、Message、Run、RunEvent、Result、幂等、刷新恢复和安全错误拆开并持久化；
- `POST /sessions/{session_id}/runs` 在同一短事务内创建 user Message 与 Run（`backend/src/application/services.py:207-245`）；
- 成功 Run 原子写入结构化 Result 与关联的 assistant Message（同文件 `344-383`）；
- P3 已把非终态、失败、取消、协议错误和归档历史收口，避免 UI 用假状态冒充真实执行；
- `report/` 与主产品隔离，避免把研发 Trace 误当产品默认界面。

这些是“会话/监控/事件”任何一种产品定位都需要的可信执行底座，不应推倒。

## 4. 对当前计划的核心质疑

### 4.1 用户可见对象与内部执行对象倒置

P3 当前路由和页面恢复顺序以 `Session → Runs → Message → 选定 Run` 为中心，页面上突出 Run 列表、状态、事件与 Result。它适合验证 P2 合同，却让用户需要理解内部执行对象才能完成一次普通沟通。

应验证的不是“能否把 Run 隐藏”，而是：用户在连续排障中到底把什么视为主线——对话、服务异常，还是 Incident。

### 4.2 “结果优先”被误实现为“结果卡优先”

P0/P3 正确地把完整 Trace 从主界面移走，但当前 Result 面板仍以技术资源结构呈现：根因、证据、Run ID。产品还缺少将结果组织为用户答复的叙事：当前发生什么、影响谁、为什么可信、下一步何为安全、是否可以继续追问。

### 4.3 监控被放在后期，却没有定义它与会话的关系

P4 是 Environment/DataSource/Knowledge，P5 才有 Alert/Incident/Approval。这个顺序可降低真实资源风险，但产品主流程既写“选择环境或告警事件”，又尚未说明：监控异常如何创建会话、会话如何引用指标、用户如何在没有真实数据时理解边界。若不先定义该关系，后续很容易得到一个聊天页和一个孤立大盘。

### 4.4 当前 P2 能支持“诊断对话”，但不是完整通用聊天产品

已有事实是：提交诊断会创建 user Message，成功后创建内容为 Result summary 的 assistant Message；Message 也带 `run_id` 关联。这足够支撑“用户提问 → 系统调查 → 助手答复”的最小连续性。

但尚未有产品级决策或契约来定义：

- 哪些用户消息需要创建 Run，哪些是澄清、总结或纯问答；
- failed/cancelled Run 在对话中应如何形成可追问的 assistant 消息；
- assistant Message 应只保存 summary，还是保存结构化 Result 的呈现引用、版本与引用证据；
- 多轮上下文、草稿、撤回、重试、并行 Run、用户切换会话时的可见规则；
- 监控/告警上下文如何作为 Message 或 Session 的受控附件进入诊断。

因此“先把当前输入框画成 ChatGPT”会制造假聊天，必须先做契约和体验 Design。

### 4.5 计划分期按资源建设合理，但缺少产品假设验证门

P0–P7 当前主要按工程资源展开：持久化、会话闭环、前端、数据源、告警、报告、生产加固。它缺一个比实现更早的门：**产品的主用户、主触发场景、主对象和价值承诺是否被验证**。

在该门缺失时，继续堆 P4/P5 很可能得到功能齐全但入口混乱的“运维控制台”。

## 5. 三种候选定位与待验证风险

| 候选 | 主入口 | AI 的位置 | 适合的首场景 | 最大风险 |
|---|---|---|---|---|
| A. 会话优先助手 | 会话列表 / 新建对话 | 主界面 | 用户主动描述异常、追问、总结排障 | 没有真实监控上下文时容易沦为普通聊天壳 |
| B. 监控优先工作台 | 服务、异常、仪表盘 | 右侧/浮层/调查入口 | 用户已从指标或告警看到异常 | P4/P5 前没有真实数据，容易做出假大盘 |
| C. Incident 协同工作区 | Incident / 值班事件 | 共同响应者 | 多人处理明确生产事件 | 当前没有事件、协作、权限与审计能力，过早实施会失真 |

当前最有依据的**研究假设**是混合模式，而不是结论：

```text
日常主动求助：会话入口
发现异常：监控/告警入口创建或打开会话
复杂调查：会话中的按需调查卡与进度
内部 Agent/Trace：默认收起，受控深度查看
```

是否把 A 作为默认首页、B 作为默认首页，仍需依据目标用户和首个真实场景决定。

## 6. 不可妥协的产品原则（研究结论，不是 UI 方案）

1. 用户不应为了提问而理解 Run、SSE 或 Agent 拓扑；
2. Agent 不应成为黑盒：默认只给进度与公开证据，必要时按层展开；
3. 任何 AI 答复必须可回到受控的 Result、Evidence、Run/Message 关联，不能只靠前端 Markdown；
4. 监控、环境、告警、Incident 和审批在真实资源未接入前只能诚实空置，不能用假数据决定产品方向；
5. `report/` 继续仅作研发/Trace 边界，不能成为主产品的逃生舱；
6. 产品设计必须先确定“用户为什么打开 OperMind”，再讨论导航、卡片和视觉风格。

## 7. 下一轮 Design 前必须回答的决策题

1. 第一付费/核心用户是日常运维工程师、值班 SRE，还是 Incident 指挥者？
2. 首个必须做好的触发场景是“我有一个问题想问 AI”、 “监控发现异常”，还是“正在处理 Incident”？
3. OperMind 是独立可观测性平台，还是覆盖在现有监控系统之上的 AI 调查层？
4. 一段 Session 是个人连续对话、一次诊断任务，还是多人 Incident 记录？
5. 什么证据、权限和数据源到位前，AI 才允许给出影响和建议？
6. 需要验证的 MVP 成功指标是什么：首次结论时间、追问完成率、调查采纳率、告警到结论时间，还是复盘可用性？

## 8. 建议的后续工作，不等于前端定稿

用户已完成方向选择。下一步应是 `治理-个人AI运维助手产品重定位/step1-个人会话主体验设计.md` 所定义的 **P3.5 产品 Design**，不是直接把当前 Workbench 改成聊天 UI。后续交付应包括：

- 三种候选定位各自的一页用户旅程和主界面草图；
- 对一个真实首场景的任务流、失败流与可信边界；
- Message/Run/Result/Monitor/Incident 的领域关系图；
- P2 API 可复用项、必须新增的 API 与绝不伪造的能力；
- 用户决策评审：选择一个候选或保留混合假设。

在该评审完成前：不修改 React 路由、导航、Mock 业务语义、后端 API 或 `report/`。
