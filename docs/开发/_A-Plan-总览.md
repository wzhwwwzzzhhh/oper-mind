## 一、目标转向

项目定位不变（多智能体运维故障诊断系统）。**驱动目标从「毕设冲高分」调整为「A-Plan」——服务于求职竞争力，目标岗位为「全栈 + agent」。**

由此带来两处翻转：

- **前端从「可选」升为核心交付物**（空目录是真短板）。最高杠杆形态是「把多 Agent 编排过程可视化」：路由决策 → Agent 链路 → 辩论 → 反思 → 报告 + ECharts 指标看板。
- **论文级严谨降级**（大样本统计、κ 人工抽检、消融广度、论文撰写），只保留「有一个站得住的数字」的最低限度。

> 旧路线图 `docs/开发路线图与规划.md` 第三节的 M5/M6/M2'–M4' 定义**已被本计划覆盖**，那份仅作历史参考。

## 三、执行顺序（含一处对初版的调整）

```
M5 多Agent对比  →  M6 后端SSE  →  M7 前端  →  M8 打磨+材料
（已完成）          （已完成）        （下一个）      （后续）
（最早验证核心风险）  （解锁前端）    （最大块）   （留 buffer）
```

**调整说明**：初版把「后端服务化」排在 M5、「对比实验」排在 M6。现**对调**——因为「多 Agent 到底赢不赢单模型」是整个项目最大的风险（文献显示辩论常常无益甚至有害，见 arXiv 2510.20963）。这个结论必须**最早拿到**，一旦是「没全面赢」，要尽早把 pitch 改成「量化了它在哪类场景有用」，而不是等做完前端才发现核心卖点悬空。对比实验复用 M4 已建的 `single_agent`/`full` 条件切换，不依赖 SSE，可独立先行。

时间线：9 月首面，实打实工时约 3–4 周。真 MySQL、大样本统计等只在有 buffer 时才做。

## 四、明确砍掉/降级清单

- 大样本统计显著性检验、多标注者 κ 抽检 —— 论文级，A-Plan 不做。
- 真实 MySQL 集成 —— 降为 M8 可选 step，有余力才做（全栈 demo 靠可跑通的 UI+API+流式证明"真产品"）。
- 大规模评测数据集 —— M5 只造够跑出可信对比数字的精简区分度集，非论文规模。
- M6 旧义「深度机制增强」（多轮 debate、领域化 reflection）—— 不作为独立目标。

## 五、目录与分层约定

- **开发日志**（代码改动快照）在 `docs/开发/M<N>-<名>/`，两级结构：
  - `design.md`（design 层：目标/范围/关键决策/step 分解/验收，带 `状态:` 字段）
  - `stepN-<名>.md`（step=md 层：**每份含多文件改动**，Step+Code+Test 合一）
  - `review.md`（验收 + 已知限制）
  - 仅当某 step 膨胀时才升为子文件夹，默认扁平两级。
- **对外材料**（pitch、面试应答）在 `docs/A-Plan/`，与开发日志**分离**（性质不同：一个是代码快照，一个是对外叙事）。
- 每新里程碑**开新分支**，别继续在 `feat/m2-harness` 上叠（已漂移）。
