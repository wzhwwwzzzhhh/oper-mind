## 1. 当前产品方向

OperMind 是面向研发与运维人员的**多 Agent DevOps Copilot**。它不是通用聊天，也不是独立的多 Agent 实验系统：系统要在受控环境中完成故障调查、证据化判断、修复提案、人工审批、白名单执行和验证闭环。

当前只承诺一个可复现 MVP 场景：订单服务因缺失索引而出现慢 SQL 和接口延迟。产品主流程是：

```text
用户报告服务异常
→ Coordinator 调度 DB / Log / Server Agent 做只读调查
→ 汇总证据、根因、不确定性与受限修复提案
→ 用户明确审批
→ 白名单执行器在受控靶场执行
→ Verify 复查前后证据并给出结论
```

多 Agent 路由、并行、Debate、Reflection、Trace 和评测继续保留：前五者服务诊断可信度，评测服务毕业设计与技术验证；它们都不取代产品闭环。

- `frontend/`：主产品，展示调查、证据、提案、审批、执行和验证。
- `report/`：研发、Trace 回放、评测和毕业设计实验控制台；保留，不作为主产品入口。

当前产品设计入口为 `docs/开发/治理-DevOps-Copilot-MVP重定位/`。

## 6. Work 1 真实验收事实

2026-07-30 的首次完整 smoke（300,000 条确定性 demo 订单、10 次样本）结果：

| 阶段 | 核心事实 |
|---|---|
| baseline | `Index Scan` 使用 `idx_orders_user_created`；P95 `60.539 ms`、P50 `53.809 ms`；无慢查询日志。 |
| degraded | 删除固定索引后为 `Seq Scan`；P95 `84.127 ms`；P50 比 baseline 高 `24.749 ms`、比例 `1.460`；10/10 匹配慢查询日志。 |
| recovered | 重建固定索引后回到 `Index Scan`；P95 `61.451 ms`、P50 `53.985 ms`；无慢查询日志。 |
| clean | `opermind_demo` schema 已删除，`runtime/` 已清理；专用数据库保留为空库。 |

故障延迟门以 P50 的比例和绝对增量判定，避免 10 个样本下单个隧道抖动放大 P95；P95 仍完整记录用于审计。上述数字是隧道环境的实际测量，不是产品 SLA，也不应外推到生产。

## 7. 执行与安全原则

- 先完成一个完整故障纵向切片，再扩展平台能力或故障数量。
- 调查工具默认只读、参数化、限时；应用元数据与诊断数据源分离。
- 仅隔离靶场中的独立执行器可在人工审批后执行严格白名单动作；LLM 无权直接执行任意 SQL 或 Shell。
- `api_key="mock"` 和确定性 mock fallback 继续是一等公民；靶场数据必须显式标识为 demo，而非伪装成生产监控。
- P4 以工作包收口：工作包完成时集中 Test → Review → Commit；架构、公开契约、真实数据源、审批/执行安全和破坏性改动仍先独立设计与审查。
