# 产品总设计 — 会话式 DevOps Copilot 的单问题端到端 MVP

> 日期：2026-07-30　|　状态：**P4.1 / P4.2 已完成；P4.3 Design/Review 已完成，等待用户实现授权**
>
> 本文是当前产品蓝图。P4.0 靶场设计仍描述已完成的目标环境；本文决定后续产品骨架、范围和迭代顺序。

## 1. 一句话定位

OperMind 是一个面向研发和运维人员的**会话式 DevOps Copilot**：用户在一个会话里描述问题、查看可信证据、确认高风险动作，并获得执行后验证结果。

它不是“把多个 Agent 的思考过程展示出来”的实验台，也不是一开始就接入所有中间件的监控平台。秋招 MVP 先把**订单服务缺失联合索引导致慢查询**这一个真实问题做成完整、可使用、可解释、可回收的闭环。

## 2. 第一条真实用户路径

```text
创建或进入会话
→ 输入“订单服务变慢，帮我排查慢查询”
→ 系统识别为已支持的订单慢查询调查
→ DB / Log / Server 三个受控角色并行采集只读证据
→ 对话中显示简要进度，右侧/展开区显示证据、根因和不确定性
→ 服务器基于严格证据生成固定修复 Proposal
→ local_operator 明确审批与二次确认
→ 白名单执行器仅在隔离靶场执行预定义索引修复
→ 独立 Verify 复查并将前后事实写回该会话
```

第一版只支持这一条调查/修复路径。遇到不支持的问题，产品应明确回答“当前 MVP 只支持订单慢查询调查”，而不是编造诊断、监控或动作能力。

## 3. 产品界面骨架

### 3.1 会话工作台是主入口

采用类似聊天产品的结构，但语义是运维工作流：

- **左侧**：会话列表；后续可加入服务列表入口。
- **中间**：用户问题、助手结论、行动请求与审批反馈。用户从这里启动调查。
- **右侧或可展开详情**：调查时间线、证据、根因、风险、审批和执行/验证事实。
- **服务页**（后续）：接入服务的健康、监控和最近调查记录；MVP 先展示一个已注册的 `order-service` 靶场服务。

现有 `frontend/src/features/workbench/` 的会话、Run、SSE、结构化 Result 读取能力是实现起点；需要改造成上述产品文案和层次，而不是重做另一个实验控制台。

### 3.2 “思考”只展示可审计过程，不展示 CoT

用户能看到：角色名称、开始/完成状态、耗时、读取的证据类别、结论摘要、失败/不确定性和关联证据编号。

用户不能看到：模型隐藏推理链、系统 Prompt、原始 SQL、原始日志、HTTP body、连接串、密钥、绝对路径或未脱敏异常。展开详情展示的是**证据与决策依据**，不是内部思维逐字稿。

### 3.3 三种交互意图

| 意图 | 当前 MVP 行为 | 后续扩展 |
|---|---|---|
| 运维问答 | 只回答已有 Markdown 知识命中的内容，附来源；无命中时诚实说明 | LLM 归纳、多轮澄清、RAG |
| 调查请求 | 只路由订单慢查询这一已支持场景，创建 Run 并采集证据 | 更多故障类型、更多服务 |
| 操作请求 | P4.2 已支持一个固定动作 Proposal，必须 local_operator 审批、二次确认与独立 Verify | 更多白名单 action、验证策略 |

## 4. 多 Agent、工具、记忆与 MCP 的正确位置

### 多 Agent 与工具

产品对用户呈现 DB、Log、Server 三个调查角色；它们分别对独立事实源负责。P4.1 的真实采集器是确定性、只读、限时的 Collector，由产品执行器编排；不能让模型自由生成 SQL 或 Shell。

现有 ReAct/LangGraph Agent、Debate、Reflection 继续保留为推理和毕业设计能力。只有在输入、工具参数、输出和失败策略都被收紧后，才可参与产品决策；它们不替代受控采集和白名单执行器。

### 记忆

当前只把**会话历史、调查 Run、结果、审批和验证记录**当作产品记忆，并且可回放、可审计。Agent 长期记忆不作为真实靶场结论依据，避免旧经验污染本次证据。

### MCP

当前没有把外部 MCP Server 当作生产关键路径。服务接入先使用仓库内受控 Adapter/Port；未来若接 MCP，也必须映射到同一份能力声明、只读/执行权限、超时、脱敏、审批和审计规则，不能把 MCP 当作绕开安全边界的通道。

## 5. 服务接入与监控框架

先设计统一连接器能力，而非先接一堆中间件：

```text
ServiceConnector
├── identity()              # 服务身份和类型
├── health_snapshot()       # 健康快照
├── collect_evidence()      # 只读、受控、结构化事实
├── supported_actions()     # 可提出的固定 action ID
└── verify_action()         # 执行后的只读验证
```

第一实现只有 `PostgresOrdersSlowQueryConnector`，服务页也只展示 `order-service` 靶场。MySQL、Redis 等后续通过各自 Connector 接入；没有 Connector、权限说明、mock fallback、目标隔离和验收 smoke 的服务，不能出现在“已接入”列表中。

监控页先展示真实且有限的健康、P50/P95、慢查询计数、调查记录。它不是承诺全量指标平台、告警中心或实时生产观测。

## 6. 知识库的最小方案与升级门槛

第一阶段不引入向量库、Agentic RAG、知识图谱、Wiki 平台或不清楚边界的“GBrain”。先建立一个受控 Markdown 知识目录：

```text
knowledge/
├── orders-slow-query.md
└── runbooks/
    └── index-repair.md
```

实现 `MarkdownKnowledgeSearcher`：只在允许目录内读取 `.md`，以关键词/全文匹配（等价于受控 grep）返回有限片段、文件名和行号。检索由程序完成，模型不能调用任意 Shell 或扫描用户磁盘。初期文档由仓库维护；“上传文件”在专门工作包中加入文件类型、大小、隔离存储、解析失败和权限设计后才开放。

升级条件明确后再做：

1. Markdown 数量或长度使全文扫描不足；
2. 用户需要语义召回、跨文档总结或来源重排；
3. 有可评测的问答集和引用正确率指标。

届时再评估向量检索/RAG；只有知识实体、关系维护和运维收益明确时才考虑 Wiki 或知识图谱。

## 7. 模型配置边界

MVP 保留服务端环境变量配置与确定性 mock fallback。用户提供 API Key 是后续产品能力，不在 P4.1 中假实现：它需要身份边界、加密存储/密钥托管、脱敏、连通性测试、模型能力声明、速率/成本限制和删除机制。

代码层现在只保留可替换的 LLM Provider 边界；界面在能力未实现前必须显示未启用，不能放一个保存后无安全语义的“API Key 输入框”。

## 8. 迭代顺序：先骨架，再扩展问题

| 工作包 | 交付 | 明确不做 |
|---|---|---|
| P4.0 | 隔离 PostgreSQL 慢查询靶场与真实 smoke | 产品运行时代码 |
| P4.1 | 会话触发的只读慢查询调查、证据 Result、简要过程与展开详情 | 修复执行、第二问题、知识库上传 |
| P4.2 | 固定修复提案、审批、白名单执行和 Verify | 任意 SQL/Shell、自动批准 |
| P4.3 | 一个服务中心/监控页、已注册靶场服务和调查入口 | 多服务生产接入、告警平台 |
| P5.0 | Markdown 知识库、受控全文检索、引用展示 | 向量库、Agentic RAG、知识图谱 |
| P5.1 | 模型 Provider 设置与第二类 Connector 的设计/实现 | 多租户密钥平台、泛化运维平台 |
| P6+ | 第二故障、Redis/MySQL、评测、毕业设计和部署增强 | 无验收条件的功能堆叠 |

每个工作包结束后先做真实/Mock 验收，再增加故障种类或复杂度。这样项目从第一天就是产品骨架，而不是“不断增加实验按钮”。

## 9. 本次设计的决策

- **通过**：一个慢查询问题打通会话、证据、审批、执行、验证、服务页与基础知识检索框架。
- **通过**：P4.1 复用既有会话工作台，把“用户问题 → 证据化结果”作为首个可见纵向切片。
- **不通过**：现在接 Redis、MySQL、Kubernetes、任意 MCP、向量库、Agentic RAG、用户 API Key 或多故障分类。
- **不通过**：用假监控、伪造 CoT、无实际安全语义的配置页制造“框架已完成”的观感。

P4.1 / P4.2 已完成，P4.3 已完成 Design/Review。当前必须等待用户明确授权，才能实施 P4.3 的服务中心、有限监控快照与调查入口。
