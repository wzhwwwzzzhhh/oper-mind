# P4.0 Design — 受控订单慢查询靶场与产品闭环边界

> 日期：2026-07-29　|　更新：2026-07-30　|　状态：**Work 1 已完成；产品后续以 `product-blueprint.md` 为准**

## 1. P4.0 的作用

P4.0 不试图先实现一个“大而全”的运维平台，而是为第一个用户可见闭环提供真实、隔离、可回收的事实源：订单服务的联合索引缺失会导致固定订单查询退化为慢查询。

该靶场是产品能力的受控验证环境，不是生产连接，也不是演示用的假指标来源。

## 2. 固定边界

| 维度 | 决策 |
|---|---|
| 目标 | 用户授权的本地隧道 PostgreSQL 专用数据库 `opermind_demo`。 |
| 数据对象 | 仅 `opermind_demo.orders` 与预定义索引 `idx_orders_user_created`。 |
| 服务 | 仅本机固定订单服务与其受控 JSONL 日志。 |
| 调查证据 | 固定执行计划、受控日志聚合、服务健康与窗口性能。 |
| 写入 | Work 1 脚本只为准备/注入/修复/清理服务；产品运行时 P4.1 只读。 |
| 禁止 | 其他数据库、schema、表、端口、生产资源、任意 SQL/Shell、任意模型 Tool 参数。 |

## 3. 产品闭环对靶场的使用

```text
P4.1：会话触发只读调查，读取靶场事实
P4.2：固定修复提案、审批、白名单动作与 Verify
P4.3：把已注册靶场服务展示在服务中心/监控页
P5.0：为该问题增加 Markdown runbook 检索与引用
```

这份分层确保“先搭框架”不等于“先接所有系统”：一个 Connector、一个问题、一个明确 action 就足以验证产品骨架。

## 4. Work 1 验收结论

Work 1 已完成真实 `start → inject → verify → repair → verify → clean` smoke：正常与恢复阶段为 `Index Scan`，故障阶段为 `Seq Scan`，并有性能和慢日志交叉证据。完整数据见 `../P4-DevOps-Copilot-MVP/work1-受控订单慢SQL靶场.md`。

## 5. 安全不变量

- 产品元数据与诊断靶场使用不同数据库 URL；
- 所有连接参数只由环境变量提供，目标不匹配立即拒绝；
- 不读取、写入、列举、探测或清理 `gongkar`；
- 凭证、原始 SQL、日志、响应 body、路径和未脱敏异常不进入文档、事件、结果或前端；
- 调查不调用会改变负载窗口的 `diagnostic-probe`；
- **历史 P4.0 边界说明**：P4.2 实施前不存在产品写入动作；当前唯一写入动作已在 P4.2 以独立审批、白名单与 Verify 约束交付，具体事实以 `../P4-DevOps-Copilot-MVP/p4.2-implementation.md` 为准。
