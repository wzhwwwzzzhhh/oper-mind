# OperMind DevOps Copilot MVP 重定位

> 生效日期：2026-07-29　|　Work 1 更新：2026-07-30
>
> **当前定位：做一个可落地的多 Agent DevOps Copilot 产品，不是独立的多 Agent 实验系统。**

## 1. 产品问题

研发或运维人员发现订单服务变慢时，需要跨数据库、日志和服务指标整理证据，判断根因，提出安全修复并验证结果。OperMind 的价值是把这些步骤做成可审计的 Copilot 闭环，而不是生成一段看似合理的回答。

第一个 MVP 场景固定为：`orders(user_id, created_at)` 联合索引缺失造成订单查询慢。用户能看到调查过程、证据、修复提案、审批、执行与验证结论。

## 2. 产品闭环

```text
异常报告 → 多 Agent 只读调查 → 证据与根因 → 受限修复提案
→ 人工审批 → 白名单执行 → Verify 前后证据 → 可追溯结果
```

- 多 Agent：并行收集 DB、日志、服务三类不同证据；不是为了堆 Agent 数量。
- 可观测：让用户和开发者知道每个结论依据什么；不是单独的 Trace 产品。
- 可评测：验证推理、工具和流程的可靠性；服务毕业设计和回归，不取代产品价值。
- 可演示：让面试或毕设场景可重复复现，证明闭环可落地；不是用 mock 演戏。

## 3. 当前已完成的 Work 1

Work 1 已在用户授权的 PostgreSQL 专用靶场上真实跑通：

| 能力 | 事实 |
|---|---|
| 故障靶场 | 本地隧道 `127.0.0.1:5433` 上独立的 `opermind_demo` 数据库；仅 `opermind_demo.orders`。 |
| 故障注入 | 只删除固定索引 `idx_orders_user_created`，没有任意 SQL。 |
| 真实证据 | PostgreSQL `EXPLAIN`、订单服务真实耗时与 JSONL 查询日志。 |
| 修复与验证 | 只重建同一索引，并检查索引、计划、性能窗口和日志窗口。 |
| 清理 | 删除专用 schema 和靶场运行时文件，不删除数据库；不触碰 `gongkar`。 |

真实 smoke 的数据在 `P4-DevOps-Copilot-MVP/work1-受控订单慢SQL靶场.md`；Work 1 仍未接入产品 Agent/API/前端。

## 4. 路线

1. **P4.0 / Work 1（完成）**：受控靶场和真实 smoke；
2. **P4.1（未授权）**：DB、Log、Server 只读调查适配与结构化证据；
3. **P4.2**：提案、审批、白名单执行和 Verify；
4. **P4.3**：API/SSE、前端主流程与演示收口；
5. **P5+**：按产品价值扩展第二故障、可靠性和毕业设计验证。

## 5. 非目标与安全红线

- 不连接生产资源，不用模型执行任意 SQL/Shell；
- 不访问用户已有的 `gongkar` 或其他非专用数据库；
- 不把会话/SSE/Trace/评测当成当前主产品主线；
- 不伪造监控、告警、执行成功或验证结果；
- 不因 Work 1 通过而自动开始 P4.1。
