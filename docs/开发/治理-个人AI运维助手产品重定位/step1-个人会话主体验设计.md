# P3.5a Step1 — 个人长期会话主体验设计

> 日期：2026-07-29　|　状态：✅ Design 完成，未授权实现　|　基线：`37317e7 feat: 完成P3.4c结构化结果Mock契约验收`
>
> 上位产品决策：`docs/开发/治理-个人AI运维助手产品重定位/design.md`

## Design

本 Step 把 R1 的产品定位收敛为首个可验证场景：**一个个人用户在既有或新建会话内，围绕一个运维问题持续提问；系统在需要时执行调查，并用可继续追问的答复呈现结论。**

这不是“把现有工作台换成聊天皮肤”。P2 已交付的 `Session`、`Message`、`DiagnosisRun`、`RunEvent`、`DiagnosisResult` 和持久化 SSE 是可信事实；P3.5 只重新定义它们在用户体验中的层级：

```text
用户看到：会话 → 消息 → 调查摘要 → 结论 / 证据 / 建议
内部保持：Session → Message → DiagnosisRun → RunEvent / DiagnosisResult
```

本 Step 不修改 React、MSW、独立 Mock、`/api/v1`、后端服务、数据库、`report/` 或真实资源。

## 1. 首个用户旅程

### 1.1 主动发起的调查型对话

```text
会话列表
→ 新建会话或打开既有会话
→ 用户输入一个运维问题并发送
→ 页面立即把该文本作为“发送中”的用户消息显示
→ 服务器以 P2 幂等 Run 受理确认后，消息成为已送达，出现调查摘要卡
→ Agent 调查期间只显示可理解的进度、已发现事实和是否需要用户补充
→ 成功后在原消息流中显示助手答复；结构化 Result 展开为证据、影响、建议和风险
→ 用户在同一会话继续追问
```

用户不需要接触 `run_id`、`trace_id`、`Last-Event-ID`、事件序号或 Agent 拓扑。它们仅在“调查详情”按需出现，且完整 Trace 仍只受控跳转到 `report/`。

### 1.2 首个场景的文字示例

```text
用户：订单服务这 15 分钟变慢了，可能是什么原因？

OperMind：我会先核对延迟变化、错误信号与依赖关系。
[正在调查：已开始核对服务与数据库信号]

OperMind：初步判断是数据库连接池接近耗尽。
影响：订单写入请求可能排队；当前结论置信度中等。
证据：……
建议：先检查连接泄漏与池大小；此建议不会自动执行任何操作。
你可以继续问：“哪些实例受影响？”
```

上例仅定义信息层级，不能被当作已接入真实指标、数据库或自动修复的声明。

## 2. 页面与信息层级（目标交互，不等于当前路由）

```text
左栏：个人会话历史
  - 新建会话
  - 活跃会话（按最近活动排序）
  - 归档会话入口

中栏：当前会话
  - 会话标题 / 归档状态
  - 按时间升序的消息流
  - 每个用户问题后的调查摘要或助手答复
  - 底部输入框、发送按钮、当前发送/调查提示

右侧抽屉或行内展开：调查详情
  - 安全的调查状态、已发现、耗时、关联 ID
  - 结构化 Result 的根因、证据、影响、建议、风险
  - 受控的完整 Trace 入口
```

首个实现不应重新引入永久三栏 Run 控制台。窄屏下左栏可折叠；调查详情必须是当前消息流的从属信息，而不是单独“选定 Run”主面板。

## 3. 消息、调查与答复的可见状态机

### 3.1 本地发送状态

```text
草稿
→ 正在提交（只存在本地）
→ 已受理 / 调查排队（已获得 P2 Run）
→ 调查中
→ 成功答复已到达

正在提交
→ 网络结果未知（保留同一 Idempotency-Key，可重试同一请求）
→ 明确受理失败（不把本地草稿伪装成已持久化 Message）
```

- “正在提交”只代表浏览器尚未得到受理结果；刷新前可在本地恢复草稿，但不能把它写成服务端历史。
- 网络超时或断开时，客户端必须以**相同** `Idempotency-Key` 重试 `POST /sessions/{session_id}/runs`，不能重新生成 key 造成重复调查。
- 一旦收到 P2 `202` Run，用户消息以服务端 `input_message_id` 为准；本地临时消息必须替换/合并，不能重复显示。

### 3.2 已受理 Investigation 状态

| P2 Run 状态 | 用户可见文案 | 消息流行为 | 禁止行为 |
|---|---|---|---|
| `queued` | 已收到，准备开始调查 | 在关联用户消息下显示简短调查卡 | 不显示内部队列号或假进度 |
| `running` | 正在核对…… | 只合并安全事件摘要和已发现事实 | 不把原始 SSE payload/工具参数直接展示 |
| `succeeded` | 助手答复已完成 | 读取关联 assistant Message；Result 可按层展开 | 不用前端拼 Markdown 伪造 Result 字段 |
| `failed` | 调查未完成 | 在关联用户消息下显示安全失败卡和“重新发起调查”入口 | 不伪造 assistant Message、根因或解决方案 |
| `cancelled` | 调查已取消 | 保留已持久化进度，允许用户重新描述或新发起调查 | 不编造取消原因、继续执行或已修复 |

当前 P2 仅在成功时持久化 assistant Message（内容为 `DiagnosisResult.summary`）；失败/取消没有助手消息。这是必须如实保留的 API 边界，不能靠前端插入一个看似已经保存的助手答复。

### 3.3 会话级交互限制

首个个人 MVP 采用**每个当前会话一次只允许一个由界面发起的未终态 Investigation**：发送后输入框显示“当前正在调查，可等待完成、切换会话或新建会话”。

这是一条 UI 可理解性限制，不是服务端并发保证。刷新恢复时若发现历史或其他客户端留下多个非终态 Run，客户端仍必须逐个恢复它们的事件和终态，而不能只恢复最近一个。

## 4. 助手答复的固定叙事

成功 Result 的页面表达顺序是：

1. **当前判断**：用 `result.summary` 说明发生了什么；
2. **影响与不确定性**：severity、confidence、impact，明确哪些仍待确认；
3. **证据**：引用受控 `evidence`，不展示敏感原文；
4. **建议**：`recommendations` 与 `risks`；若 `requires_approval=true`，明确“当前只给出建议，尚不能执行”；
5. **继续追问**：引导下一条自然语言问题；
6. **调查详情**：仅按需展开 `agent_summary`、安全事件摘要、关联 ID 和 `report/` 受控入口。

`report_markdown` 只能做展示补充，不能替代结构化字段，也不成为普通会话的默认答复文本。

## 5. 空、错误、归档与恢复

| 场景 | 页面诚实表达 | 允许动作 |
|---|---|---|
| 没有会话 | 解释会话会保存后续追问与调查记录 | 新建首个会话 |
| 会话没有消息 | 说明可描述一个运维问题；不展示假示例调查 | 输入问题 |
| 会话已归档 | 显示历史只读/归档状态 | 查看、恢复到列表；是否重新激活由后续 API Design 决定 |
| 消息读取失败 | 显示请求/trace 关联信息与重试读取 | 重试读取；不伪造历史 |
| Run 读取失败 | 与 P2 `run_failed` 区分为读取/协议错误 | 重试读取；不声称调查失败 |
| SSE 断开 | 显示“连接已中断，正在按已保存进度恢复” | 先拉取 events，再恢复订阅 |
| 无真实监控/告警 | 不展示指标大盘或虚假提醒 | 只保留未来能力的诚实边界 |

## 6. P2 契约复用与 P3.5 API 差距

### 可直接复用

- `GET /api/v1/sessions`、详情、更新、归档：个人会话历史；
- `GET /api/v1/sessions/{id}/messages`：消息流事实；
- `POST /api/v1/sessions/{id}/runs` + `Idempotency-Key`：首个“调查型对话”发送；
- `GET /api/v1/sessions/{id}/runs`、`GET /runs/{id}`：关联 Investigation 的恢复；
- `GET /runs/{id}/events`、SSE + `Last-Event-ID`：调查进度恢复；
- `DiagnosisResult`：成功答复的结构化事实；
- `X-Request-Id`、`X-Trace-Id`、UTC `Z`、cursor 和安全错误体：仍完整保留。

### 必须在下一 Step 明确的差距

1. 当前消息列表按创建时间正序和单向 cursor 暴露；长期会话需要“先到最新消息、向前加载更早历史”的稳定契约，不能仅靠前端猜测 cursor 方向；
2. 当前每次 P2 受理都创建 DiagnosisRun，尚无“无需调查的普通 assistant 回复”受理语义；
3. Message 只带 `run_id`，未表达结构化 Result 的引用、失败/取消的可追问助手状态或消息级状态；
4. 当前没有会话级“正在输入/调查”、发送撤销、消息编辑或并行 turn 的产品契约；首个 MVP 不假装具有这些能力；
5. 未来 Monitor/Alert/Action 如何以系统消息和受控引用进入会话尚无资源/API。

这些差距进入 `step2-会话契约与恢复设计.md`，在那之前不改 API，也不以 React 状态掩盖缺口。

## 7. 实现前验收

后续 P3.6 获单独授权前，必须能用状态图和 Mock 验证：

- 一个用户不理解内部 Run 仍能完成“问题 → 调查 → 答复 → 追问”；
- 同 key 重试不重复创建用户消息/调查；
- 成功、失败、取消、读取错误、SSE 断线和归档均有不同且诚实的页面语义；
- 恢复优先以 Message 流呈现，同时不遗漏任何未终态 Run 的事件恢复；
- 无 Monitor/Alert/Action 资源时页面没有假数据；
- 完整 Trace 仍只通过 `report/` 受控跳转。

## Review

本 Step 的独立审查结论见 `review.md`。结论：体验层级已经收敛，但 cursor、普通对话受理与 Message/Result 关联仍是实现阻塞的 API 设计问题；不得直接开始 P3.6。
