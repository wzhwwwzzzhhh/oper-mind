## 1. 已确认的产品决策

### 1.1 用户与规模

OperMind V1 服务于**个人用户的轻量、日常运维使用**。目标不是一开始成为企业级全栈可观测性平台，也不是多人 Incident 协同系统。

V1 的会话模型是：**一个用户拥有多个长期、多轮的个人会话**，体验应接近常见 Web AI 对话产品的历史会话与持续追问，而不是“一次 Run 等于一个页面”。多人共享、协作讨论、团队成员和 RBAC 是后续独立决策，当前明确排除。

### 1.2 产品承诺与诚实边界

用户期望的主闭环为：

```text
发现问题 → 解释问题和证据 → 提出解决方法 → 经授权处理 → 验证结果
```

这是产品方向，不是当前已交付能力。V1 必须按能力分层表达：

| 层级 | 产品可表达的目标 | 当前边界 |
|---|---|---|
| 主动咨询 | 用户描述问题，AI 回答、追问或发起调查 | P2 已能持久化诊断型会话，但不是通用对话 API |
| 自动发现 | 监控发现异常并生成可解释提醒 | 尚无真实监控/数据源，不得伪造 |
| 告警进入 | 外部或内部告警带上下文进入会话 | 尚无 Alert 资源，不得伪造 |
| 调查 | Agent 收集证据、形成结构化结论 | P2 Run/Result/SSE 已有可信技术基础 |
| 解决建议 | 给出风险、条件和可验证的建议 | 可由结构化 Result 承载，但尚未形成会话产品语义 |
| 处理与验证 | 生成动作提议、获得明确授权、执行并验证 | 未实现；不得声称已能自动修复真实系统 |

### 1.3 可见对象与内部对象

```text
用户可见主对象
Conversation / 会话
  └── Message / 消息（用户、助手、系统提醒）
        └── Investigation / 调查卡（按需出现）
              └── Finding / 结构化发现、证据、建议、风险
                    └── Action proposal / 处理提议（未来、受控）

内部实现对象
DiagnosisRun、RunEvent、SSE sequence、trace_id、Agent 编排
```

已有 `DiagnosisRun` 不删除、不降级可信性；它从“主页面主对象”转为**一次 Investigation 的内部执行记录**。普通用户默认看见调查摘要、发现、证据和状态；需要时才展开步骤、关联 ID、事件和受控 Trace。

## 2. 产品信息架构（目标，不等于已实现路由）

```text
主导航
├── 会话                         # V1 首要入口
│   ├── 历史会话列表 / 新建会话
│   ├── 多轮消息流
│   ├── 对话内调查卡、发现与建议
│   └── 展开后的调查详情
├── 监控                         # P4 后才可进入；当前不得造页面或数据
│   ├── 关注对象 / 健康概览
│   └── 异常发现
├── 提醒与告警                   # P5 后才可进入；当前不得造页面或数据
│   └── 进入或创建相关会话
├── 处理记录                     # Action/Approval/验证以后才可进入
└── 设置与连接                   # 数据源、偏好、模型与安全边界以后分步进入
```

主导航不是当前实现任务。其目的是约束后续资源不再变成互不关联的“聊天页、监控大盘、告警页”。

## 3. 三条统一入口旅程

### 3.1 主动对话（首个验证场景）

```text
打开会话历史
→ 进入既有会话或创建新会话
→ 用户自然语言描述问题并持续追问
→ 助手先给可理解答复；需要证据时创建 Investigation
→ 会话内显示“正在调查什么 / 已发现什么 / 是否需要用户操作”
→ 助手以结论、证据、影响、不确定性、建议和下一问组织回复
→ 用户继续追问，或在未来对处理提议明确授权
```

首个场景必须让用户能在不理解 Run、SSE、Agent、Trace 的前提下完成一次连续沟通。

### 3.2 自动发现（后续 P4/P5 的入口）

```text
真实监控信号发现异常
→ 生成可解释提醒（含来源、时间、置信与影响范围）
→ 用户打开提醒
→ 创建新会话或进入关联会话
→ 带入受控上下文，按需发起 Investigation
```

自动发现只能在已确认的真实或明确声明的确定性测试数据源上实现。没有数据源前，UI 只可呈现诚实空状态，不能展示“在线监控指标”“模拟异常”来冒充能力。

### 3.3 告警进入（后续 P5 的入口）

```text
收到已接入的 Alert
→ 显示其来源和证据边界
→ 进入已有会话或创建新会话
→ 会话内继续调查、建议、授权和验证
```

Alert、Conversation、Investigation 之间的关联必须可恢复、可审计，不能只靠前端临时状态拼接。

## 4. 会话内的信息层级

### 默认可见：回答而不是调度细节

一条助手回复应优先组织为：

```text
当前判断：发生了什么
影响与紧急程度：谁可能受影响、确定性如何
证据：来自何处、有哪些关键事实
建议：下一步安全做什么
继续：用户可以问什么 / 是否需要授权
```

### 按需展开：调查摘要

若该回复发起了 Investigation，显示简短卡片：

```text
调查状态：正在核对数据库连接和错误日志
已发现：连接池使用率异常
下一步：等待日志证据或需要用户补充环境
```

不直接显示 Run ID、`Last-Event-ID`、SSE sequence、内部 Agent 名称或原始工具参数。

### 深度查看：技术与研发边界

- 技术用户可展开 Investigation，查看安全的步骤摘要、耗时、发现和关联 ID；
- 完整 Trace、Replay、实验指标继续受控跳转 `report/`；
- 不从主产品自动加载 `report/`，不将其假装为用户对话的一部分。

## 5. 已有 P2/P3 能力的继承与差距

| 能力 | 可直接继承 | R1 后的不足 / 后续设计问题 |
|---|---|---|
| Session | 列表、详情、更新、归档、cursor 恢复 | 需要确认标题、归档、会话排序是否符合长期个人对话 |
| Message | user/assistant/system 消息、关联 `run_id` | 没有“普通非诊断对话”的明确受理语义；失败/取消后用户可理解的 assistant 回复尚未定义 |
| Investigation | `POST /sessions/{id}/runs` 幂等创建、Run/Result、SSE 恢复 | 应改用产品术语承载；不能让每次发送天然等于技术 Run |
| Result | 根因、证据、影响、建议、风险、审批需求 | 需要映射为一条可追问的助手答复，而非独立资源卡主导界面 |
| 运行过程 | RunEvent、持久化 SSE、`Last-Event-ID` 恢复 | 仍需保留，但仅为调查卡与展开详情服务 |
| report | 完整 Trace 研发观察 | 保持受控边界，不能作为主产品默认视图 |

### 5.1 后续 API 设计的硬问题（本轮不改 API）

在开始会话优先实现前，必须单独完成 API / 状态机 Design，至少决定：

1. 用户发送一条普通消息是否创建 Investigation；若不创建，助手回答如何持久化；
2. 一条 Message 与多个 Investigation、一次失败/取消、后续追问之间的关联；
3. assistant Message 如何关联结构化 Finding/Result，而不复制或伪造字段；
4. 会话恢复如何以消息流为主，同时恢复未终态 Investigation 的 SSE；
5. 自动发现和 Alert 如何产生 system Message、引用来源并保持审计；
6. Action proposal、用户授权、执行结果与验证如何进入同一会话，不绕过审批。

在此之前，**不得仅重排 React 页面来伪造会话优先产品。**

## 6. 后续阶段的重排原则

现有 P0–P3.4c 作为技术基线保留；其“Run/Result 工作台”页面假设不再约束新体验。此后按以下逻辑推进，而不抢跑真实能力：

```text
R1 产品重定位（本轮）
→ P3.5 会话优先体验与 API 差距设计
→ P3.6 会话优先的最小前端/Mock 切片（仅在设计批准后）
→ P4 监控与数据源基础：先定义独立监控对象、连接条件和诚实空状态
→ P5 提醒/告警进入会话、调查关联和处理提议/授权
→ P6 受控处理验证、报告、搜索与个人偏好
→ P7 安全、回归、部署和生产加固
```

“独立监控”是产品目标，不表示当前应自建完整指标平台。每一类真实数据源、探测、告警规则和自动动作都必须先确认目标、最小权限、数据边界、回退和验收场景。

## 7. 非目标与安全红线

- 不是通用聊天机器人；运维语境、调查证据和安全处理才是差异化；
- 不是在无真实数据源时展示虚假监控大盘；
- 不是在无明确权限与审批时执行重启、配置修改、DDL/DML 或其他生产操作；
- 不是在 V1 引入多人实时协作；
- 不是让前端把 Run/Trace 等内部信息编造为用户可见事实；
- 不连接真实数据库、真实数据源、真实认证或运行在线 Alembic，直到后续用户明确授权并完成安全前置核对。

## 8. R1 结论

OperMind 的产品主线从“诊断工作台展示一次 Run 的结果”调整为：

> **让个人用户以长期、多轮会话为主线，通过 AI 和可逐层展开的调查能力，发现问题、理解证据、获得安全建议，并在未来完成受控处理与验证。**

当前只完成这一产品方向和实施前的设计边界；下一步不是编码，而是完成 P3.5 的会话体验与 API 差距 Design 审阅。
