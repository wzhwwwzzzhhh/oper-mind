# P4.1 Design — 会话触发的订单慢查询只读调查

> 日期：2026-07-30　|　状态：**Design/Review 完成，等待用户明确实施授权**
>
> 产品上位设计：`../治理-DevOps-Copilot-MVP重定位/product-blueprint.md`

## 1. 用户价值与边界

用户在现有会话工作台输入“订单服务变慢，帮我排查慢查询”后，OperMind 针对唯一已支持的订单慢查询场景，协调 DB、Log、Server 三个受控调查角色，输出可引用的结构化证据、根因或证据不足说明。

P4.1 是第一条“会话问题 → 真实受控证据 → 结果展示”的产品切片；**不**生成修复提案、不请求审批、不执行任何 DDL/DML、不增加第二故障或知识库上传。

## 2. 输入、路由与失败语义

- 复用 P2 的 Session、Message、Run、RunEvent、Result 与 SSE，不新增公开 endpoint、迁移或 Result 表。
- 首版只由明确的订单慢查询意图/演示样例路由至 P4.1；不支持或含糊的输入保持 legacy 安全回答，不能假称已调查。
- 新增 `OPERMIND_DEMO_ORDERS_EVIDENCE_MODE`：`disabled`（默认，不改变既有装配）、`mock`（确定性 fixture）、`target`（固定靶场真实只读读取）。
- `target` 必须同时通过固定 host、port、数据库、schema、表、索引和应用元数据库隔离校验；不匹配即安全失败，绝不回退连接其他库。

## 3. 受控调查角色

```text
Conversation / Run
→ DemoOrdersInvestigationExecutor
   ├── DbEvidenceCollector
   ├── LogEvidenceCollector
   └── ServerEvidenceCollector
→ Deterministic EvidenceResultAssembler
→ 已有 Result / Message / RunEvent / SSE
```

Collector 是确定性只读基础设施，不是假装成可自由调用 Tool 的 ReAct Agent；对用户仍展示为 DB、Log、Server 调查角色。每个外部依赖必须有同契约 deterministic mock fallback。

- DB：固定 `pg_indexes` 与固定 `EXPLAIN (FORMAT JSON)`，只判断索引存在和目标表 `Seq Scan`；没有模型/用户 SQL。
- Log：只读固定 JSONL 的有限窗口，只输出聚合计数。
- Server：只读 `/health`、`/internal/diagnostic/metrics`；不能调用会污染窗口的 probe/reset/calibrate。
- 所有读取均有限时、脱敏；原始 SQL、日志、HTTP body、绝对路径、异常详情和凭证不进入 API、Result 或事件。

## 4. 结果规则

唯一可确认根因是：DB 同时证明目标索引缺失且固定订单查询计划对 `opermind_demo.orders` 使用 `Seq Scan`，并且 Log 或 Server 至少一方支持慢查询/延迟异常。

| 证据状态 | 输出 |
|---|---|
| DB + Log + Server 支持 | `severity=high`、`confidence=0.95` 的缺失索引根因。 |
| DB 支持、另两源不足/部分失败 | 高风险线索，`confidence<=0.70`，写明不确定性。 |
| DB 不支持或不可用 | 不得生成“缺失索引”根因。 |
| 全部源不可用或 target 非法 | 安全失败，不伪造 Result。 |

`recommendations=[]`、`requires_approval=false` 固定为 P4.1 边界。

## 5. 最小产品展示

复用 `frontend/src/features/workbench/`，不重建实验控制台：

1. 会话中有用户问题与当前 Run 状态；
2. 运行中只显示“DB/日志/服务正在收集证据”等角色状态、耗时和安全摘要；
3. 完成后显示结论、置信度和风险；“展开详情”展示证据、来源、指标与根因引用；
4. 没有可用数据时显示失败/不支持/未启用，不生成假监控；
5. 不渲染 CoT、Prompt、原始读取或敏感异常。

前端仅消费既有 API/SSE/Result；若实施中发现需要改公开契约或迁移，立即停止并新建 Design/Review，不在 P4.1 偷渡修改。

## 6. 建议代码结构

```text
backend/src/
├── domain/evidence.py
├── infrastructure/diagnosis/demo_orders/
│   ├── settings.py
│   ├── models.py
│   ├── postgres_reader.py
│   ├── service_reader.py
│   ├── log_reader.py
│   ├── collectors.py
│   ├── executor.py
│   └── result_assembler.py
```

跨层使用 Pydantic：`EvidenceFact`、`RootCauseFact`、`AgentInvestigationSummary`、`EvidenceInvestigationResult`。应用层仍负责事务、持久化、幂等与 SSE 事件提交。

## 7. 验收

### 默认 mock 测试

1. settings 拒绝非固定目标、`gongkar`、外部 URL、靶场外路径和元数据库复用；
2. 三个 reader 用 fake 依赖返回脱敏标量事实；
3. executor 覆盖并行、部分失败、全部失败及根因/置信度规则；
4. assembler 的结果可通过已有 API schema；
5. legacy disabled mode、Run/Result/RunEvent/SSE 与 Workbench 回归通过。

### 真实靶场 smoke

1. Work 1 脚本准备 `start → inject`，产品代码不得负责故障注入；
2. 使用独立 SQLite 应用元数据库与 `target` mode；
3. 经现有 API 和工作台创建 Session/Run，等待终态；
4. 断言 Result 有 db/log/server 证据、缺失索引根因、可重放事件和展开详情；
5. Work 1 `repair → clean` 回收，确认未触碰 `gongkar`。

## 8. 实施切片与停止点

1. 受控 settings/readers/Pydantic evidence 与 mock 测试；
2. 并行 executor、source failure、根因规则、ResultAssembler 与应用装配；
3. 复用 Workbench 的最小过程/详情展示、API/SSE 回归和真实 smoke。

完成后集中 Test → Review → Commit，停止并为 P4.2 单独设计审批/执行/验证。
