# P4.2 Implementation — 固定修复审批、执行与独立 Verify

> 实施完成：2026-07-30　|　状态：**完成并已验证**
>
> 设计与审查：`p4.2-固定修复审批执行验证-design.md` / `p4.2-固定修复审批执行验证-review.md`

## 1. 已实现的完整产品闭环

P4.2 将 P4.1 的已确认订单慢查询 Result 收敛为一条完整、受控的产品路径：

```text
high / 0.95 三源确认 Result
→ 不可编辑的固定 Proposal
→ local_operator 明确审批或拒绝
→ 批准后第二次确认异步执行
→ 固定索引白名单执行器
→ 独立 Verify
→ Proposal 快照、轮询 action events 与 Workbench 展示
```

唯一动作仍为 `postgres.orders.rebuild_missing_user_created_index.v1`。API、UI、事件、Result 与日志不会接受或显示 SQL、表名/索引参数、Shell、连接串、凭据、原始日志、内部 request ID 或模型 CoT。

## 2. 关键实现取舍

- **提案资格**：服务器重新校验 Result 的 `severity=high`、`confidence=0.95`、固定根因、database/log/metric 三类证据，以及数据库缺索引+Seq Scan、日志/指标异常事实。0.70 线索、手工 Recommendation 与失败 Run 都没有 Proposal。
- **审批与幂等**：审批 actor 固定为 `local_operator`，如实表达当前尚无 RBAC。审批与执行 POST 都要求 UUID `Idempotency-Key`；同键不同语义返回 409，`approved → executing` 由数据库状态 CAS 抢占。
- **执行隔离**：新增独立 `PostgresOrdersIndexRepairExecutor`，不导入/调用 Work 1 CLI 或 `subprocess`。target 模式每次重新检查固定 host/port/database、`current_database()`、目标表、索引缺失与 Seq Scan 后，才执行代码内唯一 `CREATE INDEX` 常量。
- **Verify**：DDL 成功不等于成功。独立 Verify 检查索引与固定计划，固定调用 `/orders/diagnostic-probe` 恰好 3 次，并只按内部 request ID 聚合受限 JSONL；公开资源只保存脱敏标量。Verify 失败会留下 `failed` 记录，明确不自动 `DROP INDEX`。
- **UI 与可观测性**：Workbench 的 Result 展开区包含 `ActionProposalPanel`，展示固定边界、本地审批限制、二次确认、状态、Verify 标量及持久化 action events。P4.2 不新增 action SSE。
