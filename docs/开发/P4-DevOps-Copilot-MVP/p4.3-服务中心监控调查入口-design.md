# P4.3 Design — 已注册服务中心、有限监控与调查入口

> 日期：2026-07-30　|　状态：**Design/Review 已完成，等待用户实施授权**
>
> 上位产品蓝图：`../治理-DevOps-Copilot-MVP重定位/product-blueprint.md`
>
> 前置事实：P4.0 靶场、P4.1 只读调查、P4.2 固定修复审批—执行—Verify 已完成并通过 target smoke。

> **历史说明（2026-07-31）**：本文记录实施前的 Design/Review 停止点。用户随后已授权实施；P4.3 的代码、回归、实现审查与真实 target smoke 已于 2026-07-31 完成。当前状态只以 `../_A-Plan-总览.md` 和 P4.3 HANDOFF 为准。

## 1. 工作包目标

P4.3 不增加第二种故障，而是把已有的“会话调查 → Proposal → 审批 → 固定执行 → Verify”放入真实产品入口：

```text
服务中心
→ 订单服务靶场详情 / 有限监控快照
→ 创建带服务上下文的调查会话
→ 用户确认后发起现有慢查询调查
→ P4.1 证据结果与 P4.2 修复闭环
→ 服务页读取最近调查 / Verify 留痕
```

用户能先知道“正在管理哪一个服务、当前读到了什么有限事实、之前发生过什么调查/修复”，再进入会话；它不是再做一个实验控制台，也不是把聊天页面伪装成监控平台。

## 2. 严格范围与非目标

### 2.1 本工作包只交付

| 项目 | P4.3 决策 |
|---|---|
| 已注册服务 | 唯一固定服务 `order-service`，语义名为“订单服务靶场”。 |
| 连接器 | 唯一 `PostgresOrdersSlowQueryConnector`，仅复用 P4.1 已审查的固定 PostgreSQL、订单服务健康/指标读取器。 |
| 服务中心 | 服务列表页、服务详情页、有限指标快照、最近调查/修复摘要。 |
| 调查入口 | 从服务详情创建一个 `service_id=order-service` 的会话，预填固定慢查询调查语句；用户仍需点击“开始调查”才会创建 Message/Run。 |
| 会话关联 | `sessions.service_id` 新增可空字段；P4.3 服务入口创建的会话必须绑定 `order-service`。既有会话保持 `NULL`，完全兼容。 |
| 监控数据 | 当前请求时受控读取的健康、P50/P95、窗口大小、慢查询/超时计数，以及受控数据库索引/计划状态；另读应用元数据中的最近 Run/Proposal/Verify 摘要。 |
| 更新方式 | 服务详情仅在页面打开、用户手动刷新及前端可见时的固定间隔轮询读取快照；不新增服务级 SSE、WebSocket、后台巡检、告警或时序采集。 |

### 2.2 明确不做

- 不接入 MySQL、Redis、Kubernetes、第二个服务或第二类故障；
- 不提供“添加服务”、连接串录入、用户凭据、Connector 市场、MCP Server 配置或真实生产资源；
- 不复用 `environment_id` 冒充服务关联，不修改既有 `environment_id` / `incident_id` 语义；
- 不新增 Prometheus、Grafana、告警规则、时序数据库、自动巡检、自动修复、通用执行页；
- 不让监控页调用 `/orders/diagnostic-probe`、reset、calibrate、故障注入、DDL/DML 或 P4.2 action executor；
- 不让服务页显示原始 SQL、表名/索引名参数、原始日志、HTTP body、路径、request ID、凭据或模型 CoT；
- 不把 `target` unavailable 时回退成 mock，也不把历史 Verify 伪装为实时健康结论。

## 3. 已注册服务与连接器边界

### 3.1 P4.3 采用代码内静态注册表，而非用户可写配置表

P4.3 只有一个经过 target smoke 的服务。服务身份、能力和目标边界由代码内不可编辑 `ServiceRegistry` 声明：

| 字段 | 固定值 / 规则 |
|---|---|
| `service_id` | `order-service` |
| 展示名 | `订单服务靶场` |
| 类型 | `postgres_orders_demo` |
| 调查能力 | `orders_slow_query.v1`，固定展示语义为“调查订单慢查询”。 |
| 修复能力 | 仅说明“固定索引修复需人工审批”；真实 action 仍只能由 P4.2 Proposal 产生。 |
| target 边界 | 仍限用户已授权的专用靶场；不返回 host、port、数据库名、schema、表或连接信息。 |

不建立可由数据库、API 或前端修改的服务配置表，原因是当前没有身份、凭据托管、连接测试、权限、删除与验收协议。未来增加第二个 Connector 时，必须单独完成“服务注册/连接配置”工作包；不能只往当前注册表塞字符串。

### 3.2 连接器职责

P4.3 新增受控端口，而不是把页面直接连到数据库或订单服务：

```text
ServiceRegistry
└── PostgresOrdersSlowQueryConnector
    ├── definition()          # 固定身份、展示能力、固定调查入口
    └── health_snapshot()     # 只读、有限、脱敏的当前快照

ServiceCenterApplicationService
├── list/get_service()
├── read_health_snapshot()
├── list_recent_activity()
└── create_service_session()
```

`health_snapshot()` 在 `target` 模式只允许：

1. P4.1 已审查的固定 `/health` 与 `/internal/diagnostic/metrics` GET；
2. P4.1 已审查的固定 PostgreSQL 当前库确认、目标索引存在性和固定计划读取。

它不读取日志文件、不调用 P4.1 调查 executor、不创建 Result/RunEvent，不产生订单探测流量，也不使用 P4.2 executor。连接、超时、目标校验、脱敏和应用元数据库隔离规则必须继承 P4.1 settings/reader；不得重新实现一个宽松连接路径。

### 3.3 模式与失败语义

| 模式 | 快照语义 |
|---|---|
| `disabled` | 服务仍显示为“已注册”，但快照为 `not_configured`，不建立任何外部连接。 |
| `mock` | 返回确定性、明确标记 `mode=mock` 的演示快照；它不能声称访问了真实服务或执行过真实 DDL。mock 的“已恢复”只可引用已持久化的 mock Verify 结果，并必须显示“模拟”。 |
| `target` | 只读取固定靶场；任何来源不可用、响应非法或目标校验失败只返回受控 `unavailable/insufficient_data`，绝不读取其他资源或回退 mock。 |

服务可用性、数据库状态与慢查询信号必须分开，并使用以下固定判断规则：

| 字段 | 固定规则 |
|---|---|
| `availability` | `healthy` 仅表示 `/health` 返回经校验的订单服务健康响应；`unhealthy` 表示端点可读但健康字段不满足规则；`unavailable` 表示健康端点不可用、响应非法或 target 校验失败；`not_configured` 仅用于 `disabled`。 |
| `database_signal` | `missing_index_seq_scan_detected` 仅在固定 DB 读取同时确认目标库、索引缺失与 `Seq Scan`；`index_and_plan_confirmed` 仅在确认索引存在且固定计划使用目标索引；其他可读但不能形成上述结论的组合为 `insufficient_data`；来源失败为 `unavailable`，`disabled` 为 `not_configured`。 |
| `performance_signal` | `slow_query_detected` 仅在 `database_signal=missing_index_seq_scan_detected` 且服务指标可读并有 `slow_query_count>0` 或 `timeout_count>0`；`no_slow_query_detected` 仅在 `database_signal=index_and_plan_confirmed`、服务指标窗口 `window_size>0` 且慢查询/超时计数均为 0；一个来源可读但条件不足为 `insufficient_data`；两个来源均不可读为 `unavailable`；`disabled` 为 `not_configured`。 |

- `/health`、指标或数据库来源可独立失败；服务 API 仍返回脱敏的 source status 与其余可读事实，不泄露下游异常，也不以部分数据补成“正常”。
- **最近 Verify**是历史审计事实，显示“最近一次验证于某时完成”，不能替代当前快照，也不能保证服务持续正常。
- `mock` 的快照是确定性演示快照，必须标注“模拟”；它不根据历史 Verify 篡改当前快照语义。

这样 P4.2 修复后，用户可以同时看到“当前快照”与“最近 Verify”；两者不一致时必须诚实保留，而不是强行拼成绿色状态。

## 4. 产品界面与用户路径

### 4.1 路由和导航

新增以下主产品路由：

```text
/services                       # 服务中心
/services/order-service         # 唯一服务详情 / 监控页
/workbench/sessions/{session_id}?intent=orders_slow_query.v1
```

左侧导航在“我的会话”旁增加“服务中心”。`/services` 是服务入口，不替代会话工作台；历史 `/workbench` 路由保持可用。

### 4.2 服务中心页

服务中心只展示一张“订单服务靶场”服务卡，包含：

- 服务名称、类型、`mode` 和“仅限受控靶场”语义；
- 当前可用性、性能信号、最近快照时间；
- 有限指标：P50/P95、窗口大小、慢查询/超时计数；
- 最近一次调查/Proposal/Verify 的脱敏状态摘要；
- “查看服务详情”入口。

无快照、disabled、target unavailable 都是正常可展示状态；禁止用本地假数据补成正常。

### 4.3 服务详情页

详情页包含四个固定区块：

1. **当前有限快照**：服务可用性、性能信号、数据源 mode、快照时间、指标与数据库计划/索引的高层状态；显示“页面轮询，不是实时监控平台”。
2. **支持的调查与动作边界**：只显示“调查订单慢查询”和“若证据确认，固定修复需人工审批”的产品语义；不显示 SQL 或可编辑动作参数。
3. **发起调查**：按钮“创建订单慢查询调查会话”。点击只创建绑定服务的 Session，随后跳转到 Workbench 并预填固定问题；按钮、跳转页和 Composer 必须写清“尚未开始调查，确认后才提交”。
4. **最近调查与修复留痕**：按 Run 倒序显示该服务绑定会话中的 Run 状态、结论风险/置信度摘要、Proposal 状态和 Verify 状态；点进会话或 Run 复用现有 Workbench/Proposal 面板。

前端在服务详情可见且页面未隐藏时最多每 15 秒读取一次快照；用户可手动刷新。轮询只影响该页，不创建 SSE，也不保持后台读取。

### 4.4 服务上下文会话

点击“创建订单慢查询调查会话”后：

1. 前端调用服务专属创建会话接口；
2. 服务器只允许 `order-service`，创建 `service_id=order-service`、状态为 active 的 Session；通用 `POST /sessions` 不接受用户写入 `service_id`；
3. 前端跳转 Workbench，呈现“订单服务靶场”上下文标签，并预填固定问题“订单服务变慢，帮我排查慢查询。”；
4. 在用户点击现有“开始调查”前，不创建 Message、Run、Result、Proposal 或外部读取；
5. 用户可修改问题，但后端仍按 P4.1 已有意图/范围规则执行，不能因 URL、service ID 或前端标签绕过支持范围。

P4.3 不承诺 Session 创建的跨请求幂等。客户端创建期间必须禁用重复点击；若网络结果未知，不得静默再次创建或声称已进入会话，应提示用户从服务的最近调查/会话列表恢复确认。该操作不访问 target，也不具有审批或执行语义。

## 5. 领域、持久化与读取模型

### 5.1 会话关联迁移

P4.3 使用显式 Alembic 迁移：

```text
sessions
└── service_id VARCHAR(64) NULL
    ├── 仅允许 NULL 或 'order-service'
    └── 建立 (service_id, updated_at, id) 读取索引
```

- `SessionData`、Session ORM、Repository、资源 Schema 和生成的 TypeScript 类型同步增加只读 `service_id`；
- `CreateSessionRequest` 不增加 `service_id`，防止客户端伪造关联；服务专属 Application Service 通过静态注册表写入；
- `environment_id` 与 `incident_id` 原样保留，绝不借用为服务字段；
- 历史行保持 `service_id=NULL`，历史 Session、Run、SSE、Proposal 均不迁移语义、不丢失读取能力；
- migration 必须覆盖 SQLite 与 PostgreSQL 应用元数据库的 upgrade/downgrade；运行时禁止 `create_all()`。

### 5.2 不持久化“监控曲线”

P4.3 不新增 snapshot、metrics、alert 或 timeseries 表。当前健康快照是一次受控读取，响应里带 `observed_at` 与 source 状态；历史留痕继续来自已有的 Session、Run、Result、ActionProposal、ActionExecution、ActionVerification 与 ActionEvent。

这避免把少量点查询伪装成监控平台，也避免在没有数据保留/采样/告警设计前引入不可信时序数据。

### 5.3 服务活动只读模型

新增只读 `ServiceActivityReader` port/实现，从应用元数据按服务绑定会话关联读取：

```text
Session(service_id)
→ DiagnosisRun
→ DiagnosisResult（可选）
→ ActionProposal / ActionVerification（可选）
```

活动资源仅包含：`session_id`、`session_title`、`run_id`、Run 状态、创建/结束时间、结论摘要、严重度、置信度、Proposal 状态、Verify 状态。按 `Run.created_at DESC, Run.id DESC` cursor 分页。

不得在该 read model 中透传证据 JSON、原始错误、事件 data、SQL、日志、request ID、连接信息或 action digest；详情跳转后才由现有受控资源展示已有安全字段。

## 6. API 契约

P4.3 是新的公开 API 与迁移工作包；实现前必须先完成本 Design 的 Review 和用户授权。拟定契约如下：

| 接口 | 行为 |
|---|---|
| `GET /api/v1/services` | 返回静态注册服务及其当前安全快照摘要；P4.3 仅一项。 |
| `GET /api/v1/services/{service_id}` | 返回服务身份、能力边界和当前有限快照。未知/未注册服务返回 `SERVICE_NOT_FOUND`。 |
| `GET /api/v1/services/{service_id}/activities` | cursor 分页读取该服务关联会话下的 Run/Proposal/Verify 安全摘要。 |
| `POST /api/v1/services/{service_id}/sessions` | 为已注册服务创建绑定上下文的 active Session，返回 `201`；无动作参数、无 SQL、无凭据、无 target 副作用。 |

建议的公开结构：

```text
ServiceResource
├── id, title, kind, mode
├── supported_investigations[]       # 固定 intent id、标题、用户可见描述
├── action_boundary                  # “固定修复须审批”的语义说明
└── snapshot
    ├── observed_at, availability, performance_signal, mode
    ├── server_metrics               # P50/P95/window/slow/timeout 的受控标量
    ├── database_signal              # 可读性、索引/计划的高层状态
    └── source_statuses              # server/database 的 available/unavailable

ServiceActivityResource
└── session/run/result/proposal/verification 的安全状态摘要
```

所有响应沿用 `/api/v1` 的 UUID/UTC/cursor/`meta`/错误体约定；新增后端 Pydantic Schema 后必须重新生成 `frontend/src/api/v1/generated.ts`。服务详情/活动查询不新增 SSE。

## 7. P4.1 / P4.2 继承与一致性

- P4.1 仍是唯一真实调查路径，DB/Log/Server 三源证据、Result、RunEvent、SSE 和意图校验不因服务页面变化；服务快照不是 P4.1 Result 的替代品。
- P4.2 Proposal 仍只从严格 `high / 0.95` 结果生成；服务页只能读取其状态，不能批准、执行、重试、回滚或构造 action。
- P4.2 Verify 完成后，服务活动摘要可显示该历史结果；服务详情必须另行读取当前快照，不能把 Verify 结果伪装成持续健康。
- 新服务会话创建只是便利入口，现有会话/Run API 和既有未绑定历史数据必须保持兼容；不为服务中心复制一套诊断生命周期或 SSE。

## 8. 安全、隐私与诚实性清单

1. `service_id` 仅是静态服务键，不是 URL、数据库 DSN、host、端口或凭据的替代输入。
2. 所有 target 读取继承 P4.1 的 host/port/database/current database/schema/table/index 白名单、只读/超时与应用库隔离；`gongkar` 和其他资源绝无探测、回退、活动读取或写入路径。
3. 服务页的“正常/异常”只来自明确规则和数据源状态；未知、窗口为空、部分失败必须显示不足，不可显示绿色的“已恢复”。
4. mock 必须显著标注，target 不可用时不生成 mock 结果；disabled 不发外部请求。
5. 服务活动和 UI 只展示脱敏事实，不显示 CoT、Prompt、SQL、日志、HTTP body、绝对路径、内部 request ID、action digest 或凭据。
6. P4.3 不新增任何 DDL/DML；唯一 P4.2 白名单动作、人工审批、二次确认与独立 Verify 的安全边界不变。

## 9. 实施切片与验收

P4.3 获得用户实现授权后，按一个纵向工作包连续完成，最后集中 Test → 实现后 Review → Commit：

1. **服务领域与迁移**：静态 ServiceRegistry/Connector port、`sessions.service_id` 迁移、Repository/read model、服务快照 Pydantic 合同；
2. **后端 API**：服务列表/详情/活动/服务会话创建，mock/disabled/target 装配与 OpenAPI/TypeScript 生成；
3. **前端入口**：导航、服务中心、详情快照、活动列表、创建并跳转服务会话、Workbench 服务上下文标签；
4. **验收与回归**：mock/API/UI/迁移回归与真实 target 全链路 smoke。

必须通过：

- 静态 registry 只接受 `order-service`；未知 ID、外部 URL、任意服务配置和伪造 `service_id` 都不能触发连接或创建绑定会话；
- `disabled` 零外部读取，`mock` 明示模拟，`target` 仅调用已许可的健康/指标/固定 DB 只读读取，失败不回退、不泄露异常；
- 快照不会调用 probe/log reader/action executor，也没有 DDL/DML；
- 历史未绑定 Session 与 P2/P4.1/P4.2 API、SSE、Proposal/执行回归通过；
- 服务活动只返回绑定 `order-service` 的安全摘要，cursor 排序稳定，不能越界读取其他服务/历史未绑定会话；
- 服务入口创建 Session 后，必须看到绑定服务标签和预填问题；在用户点击开始前，应用元数据中没有新增 Run/Message/Proposal；
- target smoke 固定为：

```text
start → inject / 构造既有退化信号 → GET 服务快照（受限异常事实）
→ 创建服务会话 → 用户确认发起 P4.1 调查 → P4.2 proposal / approve / execute / Verify
→ GET 服务快照与活动（当前事实 + 历史 verified）→ clean
```

真实 smoke 仍只使用 `opermind_demo`，并在 `finally` 执行 clean。
