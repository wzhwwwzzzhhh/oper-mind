## 1. 产品路径与范围

- [x] P4.2 已把 P4.1 的“已确认订单慢查询”接入用户可操作的产品路径：固定 Proposal、人工审批、二次确认、异步执行、独立 Verify 与 Workbench 审计时间线。

- [x] Proposal 只能由服务器重新校验后的 `high / 0.95` 三源证据生成；前端 Recommendation、用户输入和失败 Run 都不能伪造可执行资格。

## 2. 写入边界与安全审查

- [x] target 执行器在写入前重新校验固定 host/port/database、`current_database()`、schema/table、索引缺失与 `Seq Scan` 前置条件；失败即阻断，未发送 DDL。
- [x] 唯一 DDL 是代码内固定的联合索引创建常量；不接受 API SQL、表名、索引名、命令或连接参数。
- [x] 执行器校验 Proposal 的 action ID、mode、固定 target、固定 Verify 计划与 action digest，防止持久化 Proposal 被篡改后进入写入路径。
- [x] action 运行时不调用 Work 1 CLI 或 `subprocess`；应用元数据与诊断 target 仍保持隔离。
- [x] 专用 target smoke 仅访问 `opermind_demo`，完成后执行 clean；未访问 `gongkar`。

## 3. 状态、审批与 Verify 审查

- [x] 审批 actor 明确记录为 `local_operator`，审批与执行均要求幂等键，且通过条件更新保证 `approved → executing` 只会被一个请求抢占。
- [x] 过期、拒绝、前置条件不满足、执行失败和 Verify 失败均落为可读取终态；不自动重试 DDL，也不自动 `DROP INDEX`。
- [x] Verify 独立确认索引、固定执行计划、恰好 3 次固定探测和匹配日志聚合；公开 API/UI 只显示脱敏标量与语义事件，不泄露 SQL、原始日志、内部 request ID 或凭据。
- [x] 异步 action 使用持久化 events + 轮询，不新增第二套 SSE，也不改变 P4.1 Run/SSE 生命周期。
