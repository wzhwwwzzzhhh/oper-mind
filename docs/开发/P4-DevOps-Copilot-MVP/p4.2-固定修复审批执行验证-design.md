# P4.2 Design — 固定索引修复提案、人工审批、白名单执行与 Verify

> 日期：2026-07-30　|　状态：**设计完成，尚未实施**
>
> 上位设计：`../治理-DevOps-Copilot-MVP重定位/product-blueprint.md`　|　前置事实：`p4.1-implementation.md`

## 1. 目标与用户路径

P4.2 只补全订单慢查询这一条产品路径中 P4.1 之后的四个节点：**固定修复提案 → 人工审批 → 白名单执行 → 独立 Verify**。

```text
P4.1 成功 Run（high / 0.95 的缺失索引根因）
→ 服务器确定性生成一个不可编辑的固定提案
→ 本地操作者明确批准或拒绝
→ 已批准提案由用户再次确认后异步进入白名单执行器
→ 重新读取数据库、固定探测和匹配日志完成 Verify
→ 在原会话显示执行与验证事实，并保留审计事件
```

这不是“让模型执行 SQL”。模型、用户输入、HTTP 请求和前端都不能提供 SQL、表名、索引名、连接串、Shell 参数或动作参数。

## 2. 允许范围与明确禁止

### 2.1 唯一允许 action

| 字段 | 固定值 |
|---|---|
| `action_id` | `postgres.orders.rebuild_missing_user_created_index.v1` |
| 靶场服务 | `order-service` |
| 数据库 / schema / 表 | `opermind_demo` / `opermind_demo` / `orders` |
| 唯一索引 | `idx_orders_user_created` |
| 唯一写入语义 | 重建 `(user_id, created_at)` 联合索引 |
| Verify | 索引存在、固定计划使用目标索引、3 次固定订单探测均非慢查询/非超时、匹配日志无慢查询/超时 |

实际 DDL 只存在于后端的受控执行器常量中；API、事件、Result、日志和 UI 只显示“重建订单查询联合索引”的语义化描述，不返回原始 DDL。

### 2.2 P4.2 不做

- 任意 SQL、任意 Shell、任意数据库/表/索引、批量动作或 action 参数；
- 自动批准、批准后自动重复执行、自动回滚或删除索引；
- `gongkar`、其他数据库、真实生产资源、其他端口或用户配置的数据源；
- 多用户 RBAC、外部审批系统、Webhook、MCP 执行通道；
- 第二类故障、知识库、服务中心、多模型配置；
- 展示 CoT、Prompt、原始 SQL/日志/HTTP body/请求 ID/绝对路径/凭据或未脱敏异常。

现有 `core/approval.py` 是历史 CLI/通用 SQL 代码，含 `input()`、`print()` 和宽泛 SQL 判断，**P4.2 不得复用或导入它**。

## 3. 提案生成规则

### 3.1 严格前置条件

只有 P4.1 成功 Result 同时满足下列不可变条件，才在同一应用元数据事务中创建一个提案：

1. Run 状态为 `succeeded`；
2. Result 的 `severity=high`、`confidence=0.95`；
3. 存在“订单查询缺少复合索引”根因；
4. 已保存证据同时包含 database、log、metric 三类来源；
5. database 证据明确为“目标库已确认、目标索引不存在、固定计划出现 Seq Scan”；
6. log 与 metric 各自至少有一个慢查询或超时异常事实；
7. 该 Run 尚未拥有提案（一条 Run 最多一个提案）。

`high / 0.70` 线索、信息级结果、失败 Run、旧 Result、手工构造的 Recommendation 都不得生成提案。生成条件由服务器重新校验结构化事实，不能只相信 `requires_approval` 或前端字段。

### 3.2 不可编辑提案快照

提案创建时持久化：来源 Run、固定 action ID/version、非敏感目标描述、根因/证据 ID、风险说明、验证计划、由这些固定字段计算的 SHA-256 `action_digest`。审批与执行只按数据库中的 action ID 和 digest 重新构造动作；请求体没有可修改 action 的字段。

P4.1 的 Result 同步补充一条固定 Recommendation，并令 `requires_approval=true`，仅作为界面入口；真实执行权只由新 Proposal 资源授予。

## 4. 状态机、人工审批与幂等

### 4.1 提案状态机

```text
pending_approval --拒绝--> rejected（终态）
pending_approval --批准--> approved
approved --过期--> expired（终态）
approved --执行声明--> executing --Verify--> verifying
executing --前置条件不满足--> blocked（终态，无 DDL）
executing --DDL/连接失败--> failed（终态）
verifying --验证通过--> verified（终态）
verifying --验证失败--> failed（终态；明确“DDL 可能已提交，未自动回滚”）
```

- 批准有效期固定为 **15 分钟**；执行请求时才判定过期，过期后不得恢复、不得执行。
- `rejected`、`blocked`、`failed`、`expired`、`verified` 都不能重开或重试；用户必须重新发起调查，生成新的来源 Run 和新提案。
- `approved → executing` 使用数据库条件更新（CAS）声明，多个浏览器/重复请求最多一个获得执行权。

### 4.2 本地人工审批的诚实语义

当前项目尚无身份/RBAC。因此审批记录的 actor 固定为 `local_operator`：它证明“当前本地产品操作者明确确认过此提案”，**不伪装为企业级多人审批或身份认证**。界面必须展示这一限制。

审批 API 只接受：

```json
{"decision":"approve"}
```

或

```json
{"decision":"reject","comment":"可选，最多 500 字"}
```

批准和执行是两个明确动作：先批准，再在已批准页面中再次确认“执行固定修复”。拒绝不触发任何写入靶场的行为。

### 4.3 幂等

以下 POST 都强制 `Idempotency-Key: UUID`：

- `POST /api/v1/action-proposals/{proposal_id}/approval`
- `POST /api/v1/action-proposals/{proposal_id}/executions`

新增专用 action 幂等表，以 `proposal_id + endpoint + idempotency_key` 唯一约束；同键同语义返回已有资源，同键不同请求体返回 409。执行端点即使使用不同幂等键，也会被状态 CAS 拒绝重复执行。

## 5. 执行器与 Verify 安全协议

### 5.1 独立受控执行器

新增 `PostgresOrdersIndexRepairExecutor`，只能从已校验的 `DemoOrdersEvidenceSettings` 构造：

- `target` 模式：再次固定校验 `127.0.0.1:5433/opermind_demo`、服务端 `current_database()`、schema、表和目标索引名；应用元数据库仍不得复用靶场；
- `mock` 模式：使用确定性虚拟 action adapter，只用于测试/演示；资源明确带 `mode=mock`，不得声称真实 DDL；
- 其他模式：不创建/不执行 action。

target 执行前在独立短连接中重新读取固定前置条件：目标索引仍不存在、固定计划仍为目标表 `Seq Scan`。任何不满足、连接错误、超时或目标不匹配均写为 `blocked` 或 `failed`，且 **不发送 DDL**。

通过前置条件后才执行代码内固定的 `CREATE INDEX`。不使用 `IF NOT EXISTS`、用户输入、模型文本、动态标识符或字符串拼接参数。DDL 在事务失败时回滚；一旦提交成功，P4.2 不会通过 `DROP INDEX` 做自动回滚，因为删除可能破坏人工介入后的正确状态。

若并发人工修复导致执行期间索引已出现，固定 DDL 会失败并收敛为安全终态，不重试、不替换目标、不转连其他资源。

### 5.2 Verify 不是“DDL 成功”

DDL 返回成功后，执行器进入 `verifying`，使用独立的受控 Verify adapter：

1. 只读确认当前数据库、目标索引存在、固定 `EXPLAIN (FORMAT JSON)` 使用目标索引；
2. 调用固定 `/orders/diagnostic-probe` **恰好 3 次**，不接受用户路径/SQL；
3. 每次探测都必须 `slow_query=false` 且 `timeout=false`；
4. 只从受限 JSONL 中按这 3 个内部 request ID 聚合匹配记录，必须没有慢查询/超时；request ID 和原始日志不持久化到公开资源；
5. 把脱敏标量事实写入 verification 记录和 action event。

Verify 失败时 Proposal 为 `failed`，UI 需要明确“验证未通过；可能已提交固定索引，系统未自动回滚”，并禁止在该提案上再次执行。

## 6. 持久化模型与迁移

P4.2 引入显式 Alembic 迁移，绝不在运行时建表。应用元数据仍使用现有 SQLite/PostgreSQL 支持范围，且与诊断靶场隔离。

| 表 | 关键字段与约束 |
|---|---|
| `action_proposals` | `source_run_id` 唯一 FK；`action_id`、`action_digest`、`status`、安全 target JSON、风险/验证计划、批准/执行时间、安全失败码；状态 CheckConstraint。 |
| `action_approvals` | `proposal_id` 唯一 FK；`decision`、固定 actor、可选 comment、`action_digest`、时间；一条提案只允许一次决定。 |
| `action_executions` | `proposal_id` 唯一 FK；`mode`、状态、前置条件摘要、语义化动作摘要、开始/结束时间、安全失败码。 |
| `action_verifications` | `execution_id` 唯一 FK；`status`、脱敏 summary、固定标量 facts JSON、时间。 |
| `action_events` | `proposal_id + sequence` 唯一；受控 type、时间、最小安全 data，用于审批/执行/验证时间线。 |
| `action_idempotency_keys` | `proposal_id + endpoint + idempotency_key` 唯一；请求指纹、资源关联、过期时间。 |

所有 Repository port、ORM mapper、领域 Record 与公开 Schema 都使用显式 Pydantic/类型定义。事件 data 白名单仅允许节点、摘要、状态、mode、耗时和固定 action/verification 状态，不允许任意 JSON 透传。

## 7. API 契约

| 接口 | 行为 |
|---|---|
| `GET /api/v1/runs/{run_id}/action-proposal` | 返回该 Run 的 Proposal 或 `proposal: null`，用于 P4.1 结果旁展示。 |
| `GET /api/v1/action-proposals/{proposal_id}` | 返回提案、审批、执行、Verify 的当前安全快照。 |
| `GET /api/v1/action-proposals/{proposal_id}/events` | 分页读取已提交 action 审计事件。 |
| `POST /api/v1/action-proposals/{proposal_id}/approval` | 带幂等键，批准或拒绝 pending 提案。 |
| `POST /api/v1/action-proposals/{proposal_id}/executions` | 带幂等键，异步声明并执行已批准提案；返回 202。 |

P4.2 不为 action 另建 SSE。执行时间线以 action events 持久化、详情页轮询读取的方式展示，避免在未完成统一事件流设计时复制一套即时流协议。

## 8. 前端最小产品体验

在现有 Workbench 的 P4.1 Result 下增加 `ActionProposalPanel`：

- 只展示固定动作的语义、来源根因/证据、风险、前置条件与 Verify 计划；
- `pending_approval` 显示“批准”与“拒绝”；批准弹窗必须显示本地操作者限制；
- `approved` 显示第二次确认后的“执行固定修复”；
- `executing` / `verifying` 轮询 Proposal 与 action events，只展示状态、耗时和安全摘要；
- `verified` 显示前后事实与 Verify 标量；`mock` 明显标注“模拟，不含真实 DDL”；
- `blocked` / `failed` / `expired` / `rejected` 显示安全原因和“重新调查”提示；
- 不根据前端状态决定权限，所有服务端状态转换均重新校验。

## 9. 实施切片与验收

P4.2 在一个工作包内按紧密纵向切片连续实现，最终集中测试、Review、提交：

1. 领域/迁移/Repository/Proposal factory 与 API 读取；
2. 审批、幂等、action event、前端提案与批准状态；
3. 白名单 executor、独立 Verify、异步执行 API、前端执行/结果；
4. mock、API/SSE 回归（原 Run SSE 不退化）、真实 target smoke。

必须通过：

- Proposal 只从严格 P4.1 事实生成；0.70、未支持、失败、篡改 Recommendation 均无提案；
- 拒绝、过期、前置条件不满足、非法 target、重复 execute、并发 execute 都零 DDL；
- target 成功路径只写固定索引，Verify 通过后 `verified`；
- DDL 后 Verify 失败真实留痕且不自动回滚；
- mock 明确模拟且不建立真实连接；
- 新迁移 upgrade/downgrade、既有 P2/P4.1 API/SSE、后端/前端全量回归通过；
- target smoke 固定为：`start → inject → P4.1 调查 → proposal → approve → execute → Verify → clean`，并在 finally 清理靶场。

## 10. 实施前停止点

本 Design 只确定边界和契约，**尚未修改运行时代码、API、迁移或靶场状态**。独立 Review 通过后，仍需用户明确确认“按本 P4.2 Design 实施”，才能进入代码阶段。
