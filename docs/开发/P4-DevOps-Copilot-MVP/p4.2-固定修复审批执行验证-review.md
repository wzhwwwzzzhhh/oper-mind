# P4.2 Review — 固定索引修复提案、审批、白名单执行与 Verify

> 审查日期：2026-07-30　|　结论：**✅ 设计通过；尚未获得按本方案实施代码的确认**
>
> 审查对象：`p4.2-固定修复审批执行验证-design.md`

## 1. 范围与产品闭环审查

- [x] P4.2 只承接 P4.1 已确认的订单慢查询根因，不扩展第二故障、第二服务或知识库。
- [x] 用户路径完整覆盖“提案 → 人工决定 → 执行 → Verify → 会话留痕”，不是独立的 action 实验页。
- [x] 提案、审批、执行和验证均是应用元数据中的可读取资源；前端不凭局部状态伪造完成。
- [x] 执行与 Verify 事实与来源 Run 关联，满足会话产品记忆/审计需求。

## 2. 写入与目标隔离审查

- [x] 唯一 DDL 是固定 action ID 内部重建 `opermind_demo.orders` 的固定联合索引；没有 API SQL、动态表名、用户参数或 LLM 工具调用。
- [x] target 连接同时受 host、port、database、服务端 `current_database()`、schema/table/index、应用元数据库隔离约束；不满足即安全失败。
- [x] `gongkar`、非目标数据库、生产资源和其他端口没有回退/探测/执行路径。
- [x] 运行时 action 不调用 Work 1 CLI/`subprocess`；Work 1 脚本只允许由 smoke 准备与清理靶场，避免把实验脚本变成产品执行器。
- [x] 历史 `core/approval.py` 不可复用，避免 CLI `input()`/通用 SQL 规则绕开新白名单。

## 3. 人工审批、并发与失败审查

- [x] 提案基于服务器重新校验的 0.95 多源证据生成，不能由 Recommendation、前端字段或用户请求伪造。
- [x] 批准有效期、单次决策、POST 幂等键和 `approved → executing` 条件更新共同防止重复/延迟执行。
- [x] 当前没有身份体系时，审批明确记为 `local_operator`，不夸大为企业级 RBAC。
- [x] 任何非法 target、过期、拒绝、证据陈旧、前置条件不满足或竞争冲突都不发送 DDL。
- [x] DDL 提交后的 Verify 失败明确记录，且不执行危险的自动 `DROP INDEX` 回滚。

## 4. Verify 与可观测性审查

- [x] Verify 不把“CREATE INDEX 未报错”当成功：它重新验证索引、固定计划、3 次固定探测与匹配日志聚合。
- [x] P4.1 与 P4.2 读取职责分离：P4.1 保持不污染窗口的只读调查；P4.2 的 Verify 才允许固定探测，且不接收任意路径/SQL。
- [x] action events 和 UI 只传递状态、耗时、语义摘要、mode 与固定标量事实；不暴露 CoT、DDL、日志行、HTTP body、request ID、路径或凭据。
- [x] 不重复设计第二套 SSE；P4.2 先以持久化 action events + 轮询展示异步执行过程，边界更小且可审计。

## 5. 实施风险与必须遵守的细节

1. 迁移必须显式升级/降级，并覆盖 SQLite 与 PostgreSQL 应用元数据；运行时禁止 `create_all()`。
2. action 表写入、状态机、幂等键和 event sequence 必须在短事务中完成；外部 DDL/Verify 不得持有应用数据库事务。
3. target 执行器必须在**每一次写入前**重新确认服务器当前库和固定前置条件；不能仅相信 P4.1 的历史 Result。
4. target Verify 的 3 次探测产生 telemetry 是刻意且受控的验证行为；不得调用 reset/calibrate，也不得把内部 request ID 暴露给 API。
5. `mock` 是确定性模拟，不是“假装生产执行成功”；资源/UI/测试必须携带清晰 mode。
6. 执行完成后即使 Verify 失败，也不得在 P4.2 中添加“重试/回滚”按钮；需要新调查和后续工作包。
7. P4.1 的 RunEvent/SSE 契约、P2 迁移事实和既有前端读取器必须通过回归，不能为了 action 简化而污染诊断 Run 生命周期。

P4.2 设计在范围、审批语义、写入隔离、白名单、幂等、并发、Verify 和 UI 诚实性方面通过审查。
