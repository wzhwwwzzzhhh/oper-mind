## 一、项目的电梯演讲（30 秒）

> "我做了一个数据库智能诊断 Agent 项目。核心思路是用 ReAct 模式让 LLM 自主分析慢 SQL——Agent 收到 SQL 后，先调 EXPLAIN 看执行计划，再查表结构和索引，综合判断问题根因，最后给出优化建议。LLM 不可用时，自动降级到规则引擎保证基本可用。我一开始手写了 ReAct 循环理解本质，然后用 LangGraph 重构了第二版。项目覆盖慢 SQL、索引分析两个场景，手工测试了 7 个 case，诊断准确率在降级模式下也能达到 85% 以上。"

## 二、面试官必问的 10 个问题

### Q1：为什么选 ReAct 而不是 Plan-and-Execute？

```
回答：
数据库诊断的路径是不确定的。一条慢 SQL 的问题可能是没索引，也可能是
查询写法有问题，还可能是死锁导致的。诊断过程中需要不断根据上一步的
EXPLAIN 结果决定下一步做什么——Plan-and-Execute 需要预先规划所有步骤，
但在诊断场景下你根本不知道问题在哪，没法预规划。

ReAct 的"观察→推理→行动→再观察"循环更适合这种探索性任务。

给面试官挖坑的点：
如果你发现我这个问题回答得还可以，可以追问一个更深入的——"那你有没有遇到
过 ReAct 死循环的情况？怎么处理的？" 我准备了最大步数限制和重复动作检测。
```

### Q2：LLM 不可用时怎么处理？

```
回答：
我设计了双层降级。第一层：LLM 超时或报错时，自动切换到规则引擎。
规则引擎通过关键词匹配判断 SQL 类型——比如含 WHERE status 的就推荐加索引，
含 ORDER BY 的就推荐排序索引。虽然不如 LLM 智能，但 100% 可用。

第二层是安全降级：ALTER TABLE 和 KILL 等高危操作必须人工确认，
防止 Agent 误操作。
```

### Q3：为什么用 Python 不用 Java？

```
回答：
这个项目选择 Python 是因为 Agent 生态更成熟。LangChain/LangGraph、
Function Calling 的支持都是 Python 更完善。但我的主力语言是 Java，
秒杀项目里我用 Java 实现了高并发架构，这个 Agent 项目更多是探索 AI 能力。
后续如果集成到生产系统，我会用 Java 重写 Agent 引擎，通过 HTTP 调用 LLM。
```

### Q4：手写 ReAct 和 LangGraph 的区别是什么？

```
回答：
手写版核心是一个 while 循环，大约 60 行，逻辑清晰但扩展性有限。
LangGraph 版把循环拆成了图的节点和边，好处是状态流转更显式，
加新功能（比如多 Agent 协作）只需要加节点加边。

但如果只是单 Agent ReAct，手写版更轻量可控。我让我团队的人
先手写理解本质，再用框架看解决了什么问题，而不是一上来就上框架。
```

### Q5：Tool 怎么定义的？Function Calling 的原理是什么？

```
回答：
每个 Tool 包含 name、description、parameters，其中 parameters 是 JSON Schema
格式。LLM 看到 Tool 描述后，如果觉得需要调工具，会返回一个 tool_calls 对象，
包含工具名和参数。我这边解析后执行对应的 Tool 函数，把结果以 role="tool"
的消息喂回给 LLM，LLM 再基于结果继续推理。

关键是 description 要写清楚——它决定了 LLM 在什么场景下会调用这个工具。
比如 explain_sql 的 description 写了"返回访问类型、扫描行数、索引使用情况"，
LLM 看到需要性能分析就会调它。
```

### Q6：短期记忆和长期记忆分别怎么实现的？

```
回答：
短期记忆用 Sliding Window，只保留最近 5 轮对话，超过的部分裁剪掉。
System Prompt 始终保留在最前面。

长期记忆先把诊断记录保存到 JSON 文件，检索时用关键词匹配。
如果关键词匹配度超过阈值，把历史记录注入到当前对话中。

生产环境我会用向量数据库替代关键词匹配，但原理是一样的——
Embedding 转向量 → 语义检索 Top-K → 注入上下文。
```

### Q7：评估指标是什么？效果怎么样？

```
回答：
我手工准备了 7 个测试用例，覆盖全表扫描、文件排序、JOIN 优化、
索引失效、复合索引、正常 SQL、高危操作。规则引擎模式下全部有输出，
其中 6 个能给出针对性的优化建议（1 个正常 SQL 不需要优化）。
LLM 模式取决于模型能力，deepseek 基本都能正确诊断。

生产环境我会加三个指标：诊断准确率、平均耗时、人工接管率。
```

### Q8：项目最大的技术挑战是什么？

```
回答：
最大的挑战是 LLM 返回的不确定性。同一个 SQL，LLM 有时候一次调用就搞定，
有时候绕好几步。我花了比较多精力在异常处理上——LLM 返回不是合法 JSON 怎么办？
调用了不存在的工具怎么办？连续调同一个工具怎么办？

这些 edge case 的处理才是 Agent 工程化的核心，写 Demo 很容易，
上生产很难。
```

### Q9：怎么防止 Agent 误操作？

```
回答：
两层防护。第一，工具层面，所有 SQL 执行只读，ALTER/KILL/DROP 等操作
必须在 Tool 里显示声明，并走审批流程。第二，系统层面，LLM 不可用时
自动降级到规则引擎，规则引擎只能输出文本建议，不能执行任何操作。
```

### Q10：有什么可以改进的地方？

```
回答：
三个方向。第一，引入向量数据库做更精准的长期记忆检索。第二，增加
"假设验证"能力——让 Agent 提出优化方案后，自动在只读从库验证效果。
第三，支持多表关联分析和死锁诊断，目前只做了慢 SQL 和索引。
```
