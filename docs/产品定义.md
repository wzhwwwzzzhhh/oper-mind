# OperMind 产品定义

> 状态：当前产品事实源
>
> 更新：2026-07-31

## 1. 一句话定位

OperMind 是一个面向研发与运维人员的**会话式多 Agent DevOps Copilot**。用户像使用 DeepSeek 一样在会话中提问、追问和下达受控指令；系统结合已接入服务、监控数据、受控工具和多 Agent 协作完成调查、建议、审批执行与验证。

它不是一个多 Agent 实验台，也不是只处理一个硬编码 PostgreSQL 靶场的项目。

## 2. 用户看到的产品

### 2.1 会话是主入口

产品默认进入会话工作台，而不是测试脚本、靶场控制台或技术报告页。用户可以：

- 新建和管理多个会话；
- 在同一会话中持续追问某个服务或故障；
- 询问状态、故障原因、排查建议和受控操作；
- 选择或关联一个已接入服务；
- 查看回答、证据摘要、建议、审批状态、执行结果和验证结果。

交互形态应接近现代对话产品：左侧会话列表，中间对话区，必要时展示服务上下文和可展开详情。

### 2.2 多 Agent 是内部能力，也是可理解的产品反馈

系统可以由协调 Agent 将问题分派给数据库、缓存、服务、日志、监控或知识检索等角色。前端只展示用户需要理解的简要 Trace：

```text
问题理解 → 角色分工 → 受控读取 → 证据汇总 → 结论 / 提案 / 验证
```

每一步可显示角色、状态、耗时、工具类别和结构化证据摘要。展开内容是可审计的依据，**不是**模型隐藏推理链、Prompt、原始异常、原始日志、原始 SQL 或凭据。

### 2.3 服务中心是正式产品模块

用户应能在服务中心查看、接入和管理服务。产品目标包含：

- PostgreSQL、MySQL、Redis 等服务类型；
- 服务身份、类型、连接状态和权限边界；
- 每个服务的监控/状态页面；
- 从服务页直接进入带服务上下文的调查会话；
- 服务相关的调查、审批、执行和验证留痕。

“接入服务”的具体表单、凭据保存方式、连接测试、权限模型、监控指标和每类服务可支持的操作尚未定稿，必须先设计，不能临时拼接。

## 3. 系统应具备的主链路

```text
用户会话
→ 理解问题与服务上下文
→ 多 Agent 分工
→ 受控 Tool / Connector 读取事实
→ 结构化结论与证据摘要
→ 高风险操作提案
→ 人工审批
→ 白名单执行
→ 执行后验证
→ 会话与服务页留痕
```

第一条已存在的 PostgreSQL 慢查询处理能力，是这条主链路的一个技术切片；它应被逐步纳入正式服务模型，而不是继续决定产品只能支持什么。

## 4. 正式模块边界

| 模块                 | 责任                                            |
| ------------------ | --------------------------------------------- |
| 会话工作台              | 会话、消息、服务上下文、回答、简要 Trace、证据、审批和执行反馈。           |
| 服务中心               | 服务注册、服务详情、连接状态、监控、服务调查入口和留痕。                  |
| Agent 运行层          | 协调、任务分派、状态图、结果汇总和可审计 Trace。                   |
| Connector / Tool 层 | 对 PostgreSQL、MySQL、Redis、服务指标、日志和后续知识源进行受控访问。 |
| 安全治理层              | 凭据、权限、允许资源、只读边界、审批、白名单执行、验证和审计。               |
| 前后端 API            | 提供稳定的正式产品契约；前端不得绕过后端直接连接用户服务。                 |

## 5. 不可妥协的安全与诚实性

1. 模型不能获得任意 SQL、Shell、DDL、DML 或网络访问能力。
2. 所有 Connector 和 Tool 都必须由后端显式注册、参数校验、超时、脱敏和权限边界控制。
3. 用户服务凭据不能出现在代码、Git、日志、Trace、接口响应、截图或前端状态中。
4. 高风险动作不能由模型、前端或普通聊天文本直接执行；必须有提案、人工审批、固定动作白名单和验证。
5. 监控页面应明确区分当前读取、历史记录、模拟数据、不可用和未知状态，不能伪造实时性或健康结论。
6. 尚未实现的服务类型、知识库、模型设置、MCP 能力或操作权限必须如实标为未启用。

## 6. 当前尚未决策、不得擅自实现的事项

以下是正式产品需要解决的问题，但尚未由用户确认具体方案：

- 首批正式 Connector 的实现顺序：PostgreSQL、MySQL、Redis 如何排优先级；
- 用户接入服务时的凭据生命周期：临时使用、加密保存、外部密钥服务或其他方案；
- 身份、租户、角色和审批人模型；
- 监控数据来源、轮询/推送策略、历史保留与告警范围；
- Trace 的统一事件模型、保留策略和展示粒度；
- 知识库、文件、RAG、MCP、模型 Provider 和用户 API Key 的产品边界；
- 除现有固定技术切片外，哪些操作可被提案、审批、执行和验证。

这些决策必须通过下一轮产品与技术 Design 明确后再写代码。
