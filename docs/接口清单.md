### 缺少

| 缺什么 | 影响 | 判断 |
|---|---|---|
| 重跑 / 重新生成 | 答得不好只能重新打一遍问题，且会新建一个 Run，前后两次无关联。 | ❌ 欠账 |
| 全局 Run 列表 `GET /runs` | 只有 `/sessions/{id}/runs` 和 `/services/{id}/activities`，无法跨会话跨服务看「最近所有调查」。 | ❌ 欠账 |
| 会话搜索 | 会话多了只能靠 cursor 翻。侧栏那个 `Ctrl K` 提示目前是假的（`完善清单.md` P1-12）。 | ❌ 欠账 |
| 消息编辑 / 删除 | 发错了不能改。 | ❌ 欠账（优先级低） |
| 会话导出 | — | ❌ 欠账（优先级低） |

> 已交付（P8 会话工作台闭环，issue #54）：独立发消息 `POST /sessions/{id}/messages`、
> 取消 Run `POST /runs/{id}/cancel`、全局提案列表 `GET /action-proposals`。
> 普通消息只回轻量模板回复，不触发多 Agent 调查；调查意图由服务端权威判定并以 409 回退 Run 主链路。

### 已知缺陷（不是缺接口，是契约本身的问题）

- **`POST /approval` 没有审批人身份。** 当前无登录体系（`产品定义.md` §7），谁都能批，「人工审批」在安全叙事上是空的。这不是补一个字段能解决的，前置是身份模型。
- **可被审批执行的动作只有 1 个**：受控靶场固定联合索引重建（`approval/P5-controlled-action-real.md`）。接口是通用的，白名单是单条。

责任见 `产品定义.md` §4：服务注册、服务详情、连接状态、监控、服务调查入口和留痕。

### 缺少

| 缺什么 | 影响 | 判断 |
|---|---|---|
| **`POST /services` 注册服务** | 注册表硬编码在 `backend/src/api/v1/dependencies.py:113-137`（3 个 PostgreSQL + 1 个 Redis），DSN 走环境变量 `OPERMIND_SERVICE_<ID>_DSN`。**「服务注册」是本模块第一责任，接口完全不存在。** 页面上「服务接入能力将在后续工作包提供」是实话。 | ❌ **最大欠账** |
| **`PUT /services/{id}` 改服务** | 同上。改标题、换 DSN、调整能力声明都得改代码重启。 | ❌ 欠账 |
| **`DELETE /services/{id}` 移除服务** | 同上。 | ❌ 欠账 |
| `POST /services/{id}/test-connection` 显式连通性测试 | 页面上「刷新状态 / 重新检查」只是重新拉一遍 `GET /services`，不是真的探一次连接（`完善清单.md` P2-5）。 | ❌ 欠账 |
| 监控阈值 / 关注项配置 | 「采样点异常」的判定规则写死在后端，用户不能调。 | ❌ 欠账 |
| MySQL Connector 及其接口 | `产品定义.md` §7 明确列为未决事项，需先 Design。 | ⛔ 未决，非欠账 |
| 告警通道配置（邮件 / webhook） | 已决方案是「页面内告警」，没有外部通知通道。 | ⛔ 刻意不做 |

### 注册能力开工前必须先定的三件事

服务注册涉及新增公开 API + 凭据处理，按 `CLAUDE.md` 必须 PRD → Design → 用户确认。方案收敛前需要用户答：

1. **DSN 存哪。** 现在不落库。加 UI 注册就必须落库，否则刷新即失。可照搬模型 Provider 的成熟方案（AES-256-GCM 加密落库、主密钥走环境变量、接口只回 `has_api_key` + 掩码尾号，见 `model/P6-model-provider-key-management.md`）；或保持环境变量、UI 只声明服务 ID，凭据仍由运维注入。
2. **注册时是否立刻探连接。** 失败是拒绝创建，还是允许存为「未验证」态？后者更实用，但页面得多一个诚实的未验证状态。
3. **允许注册哪些类型。** PostgreSQL / Redis 有真 Connector；MySQL 没有。按 §5.6，未启用能力可以出现在下拉里但必须如实标注。

## 五、跨模块：建议但暂不开工的两个管理

用户 2026-08-09 确认：**先把上面四个做完，暂不铺第五个模块。** 以下记录理由与时机。

### 审计 / 操作记录

**推荐做，且风险最低。** `产品定义.md` §4 把「审计」写进安全治理层责任，但现在没有任何地方能回答「系统这周对我的服务做了什么、谁批的」——`/services/{id}/activities` 只能一个服务一个服务看。

优势：**几乎不需要新采集能力**，数据（runs + action events）已在库里，主要是加一层跨服务跨会话的列表与过滤接口。

需要的接口大致是：`GET /audit/activities`（跨服务跨会话，支持时间窗、服务、动作类型、结果过滤）。

### 身份 / 权限（RBAC）

`产品定义.md` §7 明确未决，排在第四阶段。但有一点必须记清：

> **没有身份体系，「人工审批」就没有真正的审批人。** 当前谁都能批，审批链在安全叙事上是空的。

这不只是「缺个登录页」,是审批机制本身的前提没落地。要不要提前，需用户决策。

### 不推荐的

| 想法 | 为什么不做 |
|---|---|
| 独立的「监控管理」模块 | 已并入服务中心；`产品定义.md` §4 把监控列为服务中心责任，单独成模块会在最左轨上重复一个入口。 |
| 「告警管理」模块 | 已决方案是页面内告警，没有任何外部通知通道。做了就是空壳。 |
| 「MCP / 插件管理」模块 | §7 明确未决。 |
