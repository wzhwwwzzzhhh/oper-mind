# 架构设计（OperMind 项目专属 · 轻量）

## 核心原则

**默认不写 Design。** 普通改动由 `dev-plan` 的任务卡承载（目标 / 只做 / 不做 / AC / 文件 / 风险）。任务卡就是设计——它短到能一眼看完，错了也改得动。

只有**五类闸门改动**才写例外 Design（≤60 行）：

1. 新 Connector / 新服务类型
2. 真实外部连接（真实 DB / 日志系统 / 网络）
3. 数据库迁移
4. 公开 API（新端点或改既有契约）
5. 审批 / 执行能力（任何写操作或高风险动作）

理由：这五类要么不可回滚，要么改变安全边界，要么会被后续代码长期引用。它们值得一份能被引用的短记录；其余不值得。

## 例外 Design 写什么

| 写 | 不写 |
|---|---|
| 决策：数据放哪层、校验在哪个时机、迁移的 down_revision 与约束名、回滚方式 | 类型字段清单、完整契约定义（直接写进代码） |
| 与既有链路的接点、文件级改动面 | 「将来可能」的通用抽象 |
| 安全边界、失败语义、诚实降级 | 切片拆解、验证命令（那是任务卡的事） |

三条判断：

1. **≤60 行**。超过就先问：是不是把多个切片塞进来了？
2. **不预设通用性**。新增抽象必须有 ≥2 个真实用例，否则写死。
3. **类型定义写代码，不写散文**。散文描述构造规则 = 靠人读来找矛盾，最贵且最不可靠。

## 横切边界（每条都核对）

1. **一条主脊，能力即插件**：新能力 = 新 Tool + Connector 绑定 + 注册，不新开端点/流程/页面。
2. **工具网关是接缝**：模型/Agent 永不直接碰 DB/Shell/网络。
3. **智能与权力分离**：动作只能白名单提议 → 人工审批 → 白名单执行 → 独立验证。
4. **能力即诚实锁**：未接通的能力显示「未启用」，Agent 那里也没有对应工具。
5. **大脑薄且对基础设施无知**：Agent 只收 AgentTask，回 findings + 证据引用。
6. **凭据永不落库/日志/Trace/响应**。
7. **跨层数据走 Pydantic / TypedDict**。

## 模式一：方向 triage（不产文档）

输入是想法而非已确认需求时用。对话内完成：

1. 澄清成一句话："想做 X，让用户能达成 Y"。
2. 过三问：**主脊**（是否在会话 / 服务中心 / 多 Agent 内核 / 受控 Connector / 安全治理上）、**可行**（真实连接、凭据、迁移、权限、写操作）、**切口**（能否切成 1–3 个可独立验收的切片）。
3. 产出**一句话结论**：合理 / 不合理 / 需收敛 + 2–4 条建议。
4. 不替用户拍板；用户确认后才进 PRD 或任务卡。

## 模式二：例外 Design（≤60 行）

位置 `docs/design/<域>/<阶段><功能>Design.md`。模板：

```markdown
# <阶段> <功能> · Design

> 状态：草稿
> 更新：<YYYY-MM-DD>

## 1. 决策
- <3–6 条真正需要拍板的决定：数据层、校验时机、迁移与回滚、接点>

## 2. 文件改动面
- <真实路径；迁移 / 公开契约变更特别标注>

## 3. 安全与失败语义
- 只读 / 最小权限 / 脱敏 / 限时 / 参数校验 / 凭据只走环境变量 / 降级

## 4. 风险与回滚
- <最可能坏的地方 + 回滚方式；无迁移/无公开 API 时写明「回滚即移除注册」>

## 5. 待确认
- <需要用户拍板的 1–3 条>
```

写完交给 `arch-review` 审 **1 轮**（P0/P1 才阻塞），用户确认后状态改「已确认」，再进 `dev-plan`。

## 关键纪律

1. 默认不写 Design；写了就 ≤60 行。
2. 边界 > 功能；不越界设计。
3. 不写实现，不写切片 / 验证 / 提交计划。
4. 诚实空态：未配置 / 不可用如实标注。
5. 安全默认：只读、最小权限、脱敏、限时、参数校验。
6. 不替用户拍板方向。

## 红灯（STOP）

- 五类闸门改动却跳过 Design / Review / 用户确认
- 设计让 Agent 直连外部、未授权写操作、凭据落库、未启用能力写成已支持
- Design 超过 60 行或混入切片 / 验证 / 提交计划
- 草稿 Design 被当作开工依据

**发现任一红灯 ⇒ 停下，修正或交用户确认前不继续。**
