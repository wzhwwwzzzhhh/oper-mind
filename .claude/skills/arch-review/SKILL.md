# 架构审查（OperMind 项目专属）

## 核心原则
审查不是审"设计写得好不好看"，而是审「**这份 Design 交出去，dev-plan 照着建会不会建出自毁 / 越界 / 破坏主脊的东西**」。

**写审分离**：arch-design 写，arch-review 审。审查者不得同时是设计者；除非独立子代理不可用且用户明确知情，否则不得冒充独立审查。

## 审查范围（只审这四件事）

审查的价值在于**拿设计去对真实代码和真实需求**，不在于校验设计内部措辞是否自洽。

| 审 | 怎么审 |
|---|---|
| **1. 越界** | 是否新端点 / 新流程 / 新模式 / Agent 直连外部 / 未授权写 / 凭据落库 / 把未启用写成已支持 |
| **2. 扩 PRD 范围** | 是否有用户可见行为变化、扩数据、扩权限，却没有回写 PRD |
| **3. 安全与诚实** | 只读 / 最小权限 / 限时 / 脱敏 / 诚实空态 / 失败语义是否如实 |
| **4. 与真实代码冲突** | 文件路径、符号名、调用点、协议 `isinstance` 面、迁移链、事件词表——**拿代码核对** |

## 明确不审（这些交给编译器和测试）

| 不审 | 谁来做 |
|---|---|
| 类型定义内部的构造规则是否自洽（`XxxSlot` 字段是否冲突、正则能否编译） | **写进代码跑 `import` / 单测**，一秒出结果 |
| 散文描述的类型系统内部矛盾 | 同上——这是编译器的工作，不是审查者的 |
| 命名、风格、文档完备性（P3） | 不值得占用审查轮次 |
| 实现细节的正确性（函数怎么写） | `dev-execute` 的代码审查 |

**判据**：如果一个问题的检测方式是「写 3 行代码跑一下」，它就**不是**审查该报的问题，而是实现阶段该有的测试。审查报这种问题，等于用最贵的方式做最便宜的检查。

## 何时用
- Design 文档写完后、交给 dev-plan 前（独立子代理只读审查，必须）。
- 大阶段验收时，核对架构方案是否落地、有无漂移。
- 用户要求确认某架构"对不对 / 合不合主脊"时。

**不用**：PRD 审查（那是 `prd-reviewing`）；代码审查（那是 `dev-execute` Phase 4）；写 Design（那是 `arch-design`）。

## 前置要求
- 基线：`docs/事实源/产品定义.md`、`docs/事实源/路线图.md`、`docs/事实源/开发规范.md`、`docs/事实源/架构与开发路径.md`。
- 被审 Design：`docs/design/<域>/*Design.md`（或用户指定路径）。
- 关联的已确认 PRD：`docs/prd/<域>/`。
- 关键实现锚点：`backend/src/core/`（tool_gateway / graph / bootstrap / coordinator）、`backend/src/agents/`、`backend/src/tools/`。

## 审查维度（逐条过）

### A. 越界（主脊与横切边界）
- [ ] 是否沿一条主脊（消息 → Run → 大脑 → 工具网关 → Connector → 证据 → 结果 → Trace）？
- [ ] 新能力是否「能力即插件」（新 Tool + 注册），而非新端点 / 新流程 / 新模式 / 新页面？
- [ ] 模型/Agent 是否永不直连 DB/Shell/网络？
- [ ] 凭据是否只走环境变量，不进文档 / 日志 / Trace / 响应 / 截图？

### B. 与 PRD 一致（需求锚定）
- [ ] 是否锚定唯一已确认 PRD？
- [ ] Design 是否**悄悄扩了 PRD 范围**（隐含改用户可见行为 / 扩数据 / 扩权限），却没回写 PRD？
- [ ] 「明确不做」是否与 PRD 一致？

### C. 安全与诚实
- [ ] 是否默认只读 / 最小权限 / 脱敏 / 限时 / 参数校验 / 审计摘要 / 诚实降级？
- [ ] 高风险动作是否只走白名单模板 → 提议 → 审批 → 白名单执行 → 独立验证？
- [ ] Trace 是否只含安全投影，不含 CoT/Prompt/原始数据/原始 SQL？
- [ ] 是否诚实空态（无数据 / 未配置 / 不可用如实标注，不伪造）？

### D. 与真实代码冲突（**最高价值的一项**）
- [ ] 文件级改动面的路径与符号是否真实存在？（拿代码核对，不靠印象）
- [ ] 新增/修改的协议是否扩大 `runtime_checkable` 的 `isinstance` 面，导致**装配期**失败？
- [ ] 封闭枚举（事件词表、失败码、交付 kind）是否**数清了几处**？（用 grep 数，不靠记忆）
- [ ] 迁移链是否接在唯一 head 之后？标识符长度是否在 alembic `String(32)` 内？
- [ ] 必填字段加进 `extra="forbid"` 模型时，既有调用点是否会 `ValidationError`？
- [ ] 是否有重复建设（同一事实出现第二套读取路径/模型）？

### E. Design / plan 分界与粒度
- [ ] Design 是否**没有**混入切片拆解 / 验证命令 / 提交计划？
- [ ] **是否只覆盖一个可独立交付的切片？** 超过 ~200 行或覆盖多个切片 → 报「粒度过大」，建议拆分而不是逐条审。

## 审查输出格式
```
# 架构审查：<Design 标题>
总体：PASS / FAIL（P0/P1 存在即 FAIL）
发现：
- [P0] A: 设计让 Agent 直连数据库 → 必须改走工具网关
- [P1] B: Design 隐含新增公开端点（<路径>），PRD「不做什么」未含 → 回写 PRD 并交用户确认
- [P2] D: 事件词表实际有 5 处（grep 结果：<文件:行>），Design 只列 3 处
结论：PASS / FAIL
```

## P0–P2 分级（取消 P3）
- **P0**：安全红线（凭据泄露、未授权写、Agent 直连外部、把未启用写成已支持、mock 冒充真实）。
- **P1**：扩 PRD 范围 / 违反横切边界 / 与真实代码冲突导致会建坏。
- **P2**：边界与降级缺失、与既有架构不一致、文件清单不完整。

**P0/P1 存在即 FAIL。P2 记录但不必回改重审**，由实现阶段处理——避免为小问题消耗一轮审查。

**不报 P3**。命名、风格、文档措辞不占审查轮次。

## 审查后动作
- FAIL → 回 arch-design 修，改完重审。
- **同一份 Design 最多审 2 轮**。第 2 轮仍 FAIL 且问题是同一类 → 不再要求出第 3 版，直接向用户说明「反复在同一处失败，建议砍范围或换方案」。
- PASS → 交用户确认设计决策清单；用户确认后，把 Design 顶部改为 `> 状态：已确认`，放行到 dev-plan。

## 独立子代理要求
- 用 readonly 子代理（独立视角，与设计者分离），输入：Design 路径、关联 PRD、基线文档、关键实现锚点。
- 子代理不得写文件、不得改代码；产出由主 agent 落盘。
- **给子代理的提示必须要求：拿代码核对，不靠印象；能 grep 的必须 grep 并给出行号。**
- 非本技能环境无法派子代理时 → 如实标注 `tooling_blocked` 交用户，不得冒充独立审查。

## 常见错误（审查者自己别犯）
| 错误 | 修正 |
|---|---|
| 只审写作质量，不审"建出来会不会出事" | 以"建出来会不会自毁"为第一问题 |
| 拿散文推断类型系统的内部矛盾 | 那是编译器的活；要求设计者写进代码跑 `import` |
| 报"字段 A 与规则 B 可能冲突"这类可一键验证的问题 | 写 3 行代码验证，不要占一轮审查 |
| 对悄悄扩 PRD 范围的设计放过 | 任何范围外推都要回写 PRD + 交用户 |
| 漏审安全边界 | 只读 / 最小权限 / 凭据 / 网关 / 脱敏逐条过 |
| 凭记忆数事件词表/失败码有几处 | grep 数，给行号 |
| 设计者审自己的设计 | 写审分离，用独立子代理 |
| 反复 FAIL 却仍要求出下一版 | 2 轮上限，停下交用户 |

## 红灯（STOP）
- 存在 P0 / P1
- 设计违反横切边界（Agent 直连 / 未授权写 / 凭据落库 / 未启用当已支持）
- Design 悄悄扩 PRD 范围未回写
- Design 混入切片 / 验证 / 提交计划
- 草稿状态 Design 被当作闸门依据
- 设计者自审或冒充独立审查

**发现任一红灯 ⇒ FAIL，修改后再审。**
