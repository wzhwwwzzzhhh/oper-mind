# OperMind 只读排查手册（内置）@1

本手册是仓库内置的静态知识，不读取任何实时指标、日志、SQL 结果或服务状态。它只提供排查思路；是否适用于当前环境，需要用户结合真实数据判断。

## 使用边界

- 先确认用户要排查的对象：慢查询、锁等待、连接池、服务健康或日志错误。
- 只提出只读、可回退、可观察的检查步骤；不提出写入、删除、重启、改配置或绕过权限的动作。
- 不猜测具体数值、进程号、SQL 文本或错误日志内容。
- 需要真实数据时，明确说明还需要用户提供或授权读取哪些信息。

## 1. 慢查询

1. 先确认慢的判定口径：单次耗时、平均耗时、P95/P99，以及发生在哪个时间窗口。
2. 区分数据库自身耗时与网络、连接建立、应用侧序列化的耗时。
3. 查看执行计划中的全表扫描、错误的连接顺序、缺少索引、隐式类型转换和函数包裹索引列。
4. 检查统计信息是否过期、数据分布是否变化、参数是否导致计划抖动。
5. 对比同一语句在快慢时段的计划差异；不要只看单次样本。
6. 建议动作：补充或调整索引、改写可等价优化的条件、更新统计信息；全部先以只读方式验证。

## 2. 锁等待与阻塞

1. 先判断是锁等待、死锁，还是长事务占用了资源。
2. 找出阻塞链：谁在等待、谁持有锁、持有多久、事务处于什么状态。
3. 区分行锁、表锁、间隙锁与意向锁；确认隔离级别是否放大了锁范围。
4. 检查是否存在未提交事务、应用侧连接泄漏、批量更新过大或事务内调用外部服务。
5. 不要建议直接终止会话；先确认业务影响与回滚代价，升级给有权限的人处理。

## 3. 连接池

1. 对比连接池上限、当前活跃连接、空闲连接和等待队列长度。
2. 区分连接耗尽、连接建立慢、连接泄漏和数据库端连接数上限。
3. 检查应用是否在请求结束后可靠归还连接，是否存在长时间占用连接的外部调用。
4. 检查数据库端是否因认证、网络或资源不足拒绝新连接。
5. 建议动作：缩短事务、修复泄漏、调整池大小；调整上限前先评估数据库承载能力。

## 4. 服务健康

1. 先确认症状：不可用、变慢、间歇失败，还是仅个别实例异常。
2. 对比各实例的存活状态、启动时间、资源使用和最近变更。
3. 检查依赖服务、DNS、证书、磁盘空间和文件描述符等基础条件。
4. 区分单实例故障与共享依赖故障；不要用单个样例代表整体。
5. 建议动作：隔离问题实例、回滚最近变更、观察依赖恢复；涉及重启或切流时升级处理。

## 5. 日志错误模式

1. 先按时间窗口、服务、实例和错误码聚合，不逐条猜测。
2. 区分首次错误、级联错误和重试噪声；优先定位最早的根因信号。
3. 检查错误是否与发布、配置变更、流量变化或依赖异常同时发生。
4. 关注超时、连接拒绝、认证失败、资源耗尽和反序列化失败等模式。
5. 不建议复制完整堆栈或敏感字段；只保留脱敏后的错误类型、时间与关联标识。

## 6. 只读原则与升级

- 默认只读：先观察、再假设、后验证；不直接修改生产数据或配置。
- 每个建议都说明验证方式、可能影响和回退办法。
- 证据不足时明确说“需要更多信息”，不要用常识补成事实。
- 涉及写操作、权限变更、数据修复、重启、切流或删除时，停止并升级给人工审批。
- 回答时说明知识来源是内置手册，没有读取当前环境的数据。
